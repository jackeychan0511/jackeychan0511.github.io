> **📌 한줄 요약:** **2026년 10월 9일**, **Anthropic(앤트로픽)** 이 **Claude Managed Agents(매니지드 에이전트)** 에서 **'동적 워크플로(dynamic workflows)'를 베타로 열었습니다.** 에이전트가 **스스로 프로그램(워크플로)을 작성**해 **여러 에이전트를 단계(phase)별로 묶어 백그라운드에서 실행**하고 **결과를 하나로 합칩니다.** 공식 문서 기준으로 **한 번의 실행(workflow run)당 총 1,000개 에이전트까지** 돌릴 수 있습니다. 켜는 방법은 **베타 헤더 `managed-agents-2026-04-01`** 과 **에이전트의 다중에이전트(multiagent) 설정**을 켜는 것뿐입니다. 한마디로 **"사람이 에이전트 여러 개를 나눠 부리는 단계"에서 "에이전트가 그 배분 자체를 코드로 써서 돌리는 단계"로 넘어간** 소식입니다.

문서 수백 건을 한 번에 훑어야 하거나, 수천 개 파일에 걸친 마이그레이션, 리포지토리 전체를 대상으로 하는 버그·보안 점검처럼 **"조각이 너무 많아 에이전트 한 마리로는 감당이 안 되는" 작업**을 다루는 분들이라면 한 번쯤 이런 벽을 만납니다. 에이전트 하나에 일을 몰아주면 **컨텍스트가 터지고**, 반대로 사람이 일일이 쪼개서 여러 에이전트에 나눠주면 **그 '나눠주는 일'이 다시 사람 손을 타죠.** 에이전트를 업무 파이프라인에 붙여 쓰는 입장에서 보면, 이 병목은 **자동화로 얻은 이득을 다시 사람이 까먹는 지점**이었습니다.

**2026년 10월 9일**, Anthropic이 바로 그 지점을 건드리는 기능을 열었습니다. Claude Managed Agents의 **'동적 워크플로(dynamic workflows)'** 베타입니다. 무엇이 바뀐 건지, 실제로 어디까지 돌아가는지, 그리고 **자동화 파이프라인을 운영하는 입장에서 어떤 의미인지** 정리해 봤습니다.

## 1. 이슈 요약 — 무엇이 열렸나

공식 Claude Platform 릴리스 노트(2026년 10월 9일)의 내용을 그대로 옮기면 이렇습니다.

- **에이전트가 워크플로를 스스로 쓴다:** Managed Agents 에이전트가 **동적 워크플로**를 사용할 수 있게 됐습니다(**베타**).
- **워크플로 = 프로그램:** "워크플로는 **여러 에이전트를 단계(phase)별로 실행하고 그 결과를 결합하는 프로그램**"입니다.
- **백그라운드 실행:** 서버가 이를 **워크플로 런(workflow run)** 하나로 **백그라운드에서** 돌립니다.
- **활성화 방법:** 에이전트의 **다중에이전트(multiagent) 필드**에 타입 **`multiagent_20261001`**, 그리고 **`workflows` = `enabled`** 를 지정합니다.
- **사용 조건:** **베타 헤더 `managed-agents-2026-04-01`** 이 필요합니다.
- **진행 추적:** 각 런은 세션 이벤트 스트림의 **`workflow_run.*` 이벤트**로 따라갑니다.
- **규모:** 공식 문서 기준 **런당 최대 1,000개 에이전트**까지.

여기서 중요한 건 **"에이전트가 에이전트를 부리는" 방식이 한 단계 더 추상화됐다**는 점입니다. 예전에는 리드 에이전트가 **턴(turn)마다** 다음에 뭘 할지 판단하며 서브에이전트를 붙였다 뗐다 했다면, 이제는 **그 배분 로직 자체를 에이전트가 코드(스크립트)로 써서** 런타임에 넘깁니다.

## 2. 상세 분석

### 2-1. 무엇이 달라졌나 — "턴마다 판단"에서 "계획을 코드로"로

Claude 플랫폼 문서는 한 세션이 다른 에이전트에 일을 넘기는 두 가지 방식을 나란히 설명합니다.

- **서브에이전트(subagents):** 에이전트가 **직접** 작업을 위임하고, 각 서브에이전트가 보고한 내용을 읽습니다. **위임은 한 단계 깊이**이고, 한 세션에 **동시에 최대 25개 자식 스레드**까지 둘 수 있습니다.
- **동적 워크플로(dynamic workflows):** 에이전트가 **워크플로를 작성**합니다. 곧 **여러 에이전트를 백그라운드에서 돌리고 결과를 결합하는 프로그램**입니다.

차이가 분명합니다. **서브에이전트는 "다음에 뭘 시킬지"를 에이전트가 매 턴 판단**하고, 중간 결과가 **에이전트의 컨텍스트 창**에 쌓입니다. 반대로 **동적 워크플로는 그 판단·분기·중간 결과를 스크립트가 들고 있고**, 메인 세션 스레드는 **사용자와 대화하고 진행 상황을 확인하는 데** 비워둘 수 있습니다. 공식 표현대로 **"컨텍스트와 결과가 에이전트에서 에이전트로 프로그램적으로 전달"**됩니다.

즉 이번 변화의 핵심은 **"에이전트를 몇 마리 부릴까"가 아니라 "그 배분을 누가 설계하는가"** 입니다. 사람 → 에이전트 → 스크립트로, **오케스트레이션의 주체가 한 칸 더 내려간** 셈입니다.

### 2-2. 실제 예시 — Claude Code에서는 이미 '정식' 기능

사실 **동적 워크플로는 Claude Code 쪽에서 먼저 자리를 잡았습니다.** Claude(Anthropic) 공식 아티클은 동적 워크플로를 **정식(일반 제공)** 으로 안내하며, 이렇게 설명합니다.

> "복잡한 레거시 코드베이스에서 **서비스 전체에 걸친 버그 사냥**, **수백 개 파일을 건드리는 마이그레이션**, 커밋 전에 **여러 각도에서 검증하고 싶은 계획** 같은 작업은 에이전트 한 번의 패스로는 너무 큽니다. 동적 워크플로는 이를 끝까지 처리합니다."

공식 아티클이 든 **대표 사례**가 인상적입니다. **Bun을 Zig에서 Rust로 옮긴 리라이트**에서 동적 워크플로가 쓰였고, **기존 테스트 스위트의 99.8% 통과**, **약 75만 줄의 Rust**, **첫 커밋에서 머지까지 11일**이 걸렸다고 합니다. 워크플로가 먼저 **모든 구조체 필드에 맞는 Rust 라이프타임을 매핑**하고, 다음 워크플로가 **수백 개 에이전트를 병렬로 돌려 각 파일을 동작 동일하게 포팅**(파일마다 리뷰어 2명)한 뒤, **빌드·테스트가 깨끗해질 때까지 수정 루프**를 돌렸다는 구조입니다.

Claude Code 쪽 동적 워크플로의 공식 안내는 다음과 같습니다.

| 항목 | 내용 |
|:----|:----|
| 형태 | 에이전트가 작성하는 **JavaScript 스크립트**(오케스트레이션) |
| 실행 | 런타임이 **백그라운드**에서 실행, 세션은 계속 반응 |
| 사용 가능 | **모든 유료 플랜**, **Anthropic API**, Amazon Bedrock, Google Cloud Agent Platform, Microsoft Foundry |
| 켜기(Pro) | `/config` 의 **Dynamic workflows** 항목 |
| 내장 워크플로 | **`/deep-research`** (여러 출처를 교차검증해 인용 보고서 생성) |
| 자동 모드 | **ultracode** 설정(에이전트가 알아서 워크플로 사용) |
| 규모 | **런당 수십~수백 개 에이전트** |

### 2-3. 규모와 한계 — "1,000개"의 실제 의미

공개 자료에서 가장 눈에 띄는 숫자는 **Managed Agents 문서의 "런당 총 1,000개 에이전트"** 입니다. 다만 이 숫자는 **"동시에 1,000마리가 한꺼번에 뛴다"는 뜻이 아닙니다.**

- **총량 상한:** 한 워크플로 런에서 쓸 수 있는 **에이전트 총합이 1,000개**입니다. 문서는 이 상한을 **"폭주하는 루프를 막기 위한"** 장치로 설명합니다.
- **단계(phase)로 나눠 실행:** 에이전트들이 **단계별로** 돌고, 각 단계의 결과가 결합됩니다.
- **백그라운드 단일 런:** 서버가 **워크플로 런 하나**로 돌리며, 진행 상황은 **`workflow_run.*` 이벤트**로 추적합니다.
- **서브에이전트와의 차이:** 서브에이전트는 **세션당 동시 25개** 한도가 있고 **위임이 한 단계 깊이**인 반면, 워크플로는 **런 단위로 확장**됩니다.

즉 **"1,000"은 머릿수가 아니라 상한(cap)** 이고, 실제로 몇 개가 동시에 도는지는 **워크플로가 어떤 구조로 짜였는지**에 달려 있습니다. 여기서 실무 감각이 중요해집니다.

### 2-4. 비용 구조 — "에이전트 수 = 토큰 수"

이번 기능에서 **가장 먼저 체크해야 할 부분은 성능이 아니라 비용**입니다. 공식 안내가 반복해서 강조하는 대목입니다.

- **"런 안의 모든 에이전트가 토큰을 씁니다."** 그래서 문서는 **세션 예산(session budget)** 을 설정해 지출을 상한으로 묶으라고 권합니다.
- Claude Code 쪽 안내도 **"동적 워크플로는 일반 세션보다 토큰을 상당히 더 소비할 수 있다"** 며, **범위가 좁은 작업으로 먼저 감을 잡고**, **auto 모드를 켜라**고 권합니다.
- **ultracode** 는 더 공격적입니다. 모든 작업에 대해 **① 코드를 이해하고 ② 변경하고 ③ 검증하는 워크플로를 연달아** 돌리기 때문에, **요청마다 토큰이 더 들고 더 오래 걸립니다.** 구독 플랜에서는 이 토큰이 **사용 한도**를 갉아먹습니다.

정리하면, 동적 워크플로는 **"돈과 시간을 더 써서 신뢰도를 사는" 도구**입니다. 작업이 작으면 그냥 에이전트 한 마리가 낫습니다.

## 3. 영향 — 사용자와 개발자에게 무엇이 달라지나

### 👤 사용자·조직 관점

- **"조각이 많은 작업"의 자동화 문턱이 내려갑니다.** 수백 건 문서 검토, 대량 마이그레이션, 전사 코드 점검처럼 **사람이 쪼개서 나눠주던 일**을, 이제 **에이전트가 계획을 코드로 세워** 처리하는 경로가 생겼습니다.
- **사람이 붙잡는 지점이 이동합니다.** 중간 과정을 사람이 일일이 넘겨주는 대신, **상한(예산·에이전트 수)과 검증 기준을 설계하는 일**이 남습니다. 관리자의 역할이 **"일 시키기"에서 "경계 긋기"** 로 옮겨가는 셈입니다.
- **비용 통제가 곧 운영 역량**이 됩니다. 에이전트를 많이 부릴수록 토큰이 선형으로 늘기 때문에, **세션 예산**을 습관처럼 걸어두는 팀이 유리합니다.

### 🧑‍💻 개발자·운영 관점

- **오케스트레이션을 '자산'으로 남길 수 있습니다.** 워크플로가 **스크립트**라는 건, 그 배분 로직을 **읽고 다시 실행(rerun)** 할 수 있다는 뜻입니다. 일회성 대화가 아니라 **재현 가능한 파이프라인**이 됩니다.
- **상태를 어디에 두는지가 설계 포인트입니다.** 서브에이전트는 중간 결과가 **컨텍스트 창**에 쌓이지만, 워크플로는 **스크립트 변수**에 담깁니다. 같은 작업도 **어느 쪽으로 짜느냐에 따라 비용·안정성이 달라집니다.**
- **검증을 구조에 심을 수 있습니다.** 공식 문서는 워크플로가 **"독립적인 에이전트가 서로의 발견을 적대적으로 검토한 뒤 보고"** 하거나 **"여러 각도에서 초안을 만들어 서로 견주는"** 품질 패턴을 넣을 수 있다고 설명합니다. 자동화 파이프라인에서 **검증 계층을 코드로 고정**할 수 있다는 의미입니다.
- **관측 가능성이 붙습니다.** `workflow_run.*` 이벤트와 `/workflows` 진행 뷰로 **각 단계의 에이전트 수와 발견 내용**을 따라갈 수 있어, 운영 중 **어디서 막히는지**가 보입니다.

## 4. 유의점 — 솔직히 짚어둘 부분

- **"많은 에이전트가 항상 낫다"는 아닙니다.** Anthropic 스스로 **"멀티에이전트가 맞는 문제와 아닌 문제"** 를 별도 문서로 정리해 둡니다. 조각이 적고 순차적이면 **단일 에이전트가 더 싸고 정확**합니다.
- **여전히 베타입니다.** Managed Agents의 동적 워크플로는 **베타 헤더**가 필요하고, **한도·동작이 바뀔 수 있습니다.** 프로덕션 의존은 신중하게.
- **비용이 '조용히' 늘 수 있습니다.** 에이전트를 부리는 만큼 토큰이 늘어나는데, 겉으로 보이는 건 **"결과 하나"** 뿐입니다. **예산 상한과 로그**를 함께 보지 않으면 지출을 놓치기 쉽습니다.
- **검증이 자동이라는 말과 정확성이 자동이라는 말은 다릅니다.** 교차검증 패턴은 **품질을 끌어올리는 장치**지, **틀린 답을 없애는 보증**이 아닙니다. 문서도 검증자가 확인하지 못한 주장은 **'미검증'으로 표시**한다고 밝히고 있습니다.
- **공식 문서의 표현과 헤드라인 숫자는 구분해서 보자.** "1,000개"는 **상한**이고, 실제 동시성·구조는 **워크플로 설계**에 달려 있습니다.

## 5. 전망

이번 발표는 **에이전트 경쟁의 초점이 '모델 성능'에서 '오케스트레이션'으로 옮겨가고 있다**는 신호로 읽힙니다. 주목할 지점은 셋입니다.

**① 오케스트레이션이 '코드'가 되는 흐름.** 계획을 스크립트로 굳히면 **재현성·감사 가능성·버전 관리**가 따라옵니다. "에이전트가 잘 하더라"가 아니라 **"파이프라인이 이렇게 돌더라"** 를 증명할 수 있게 되는 쪽으로 무게가 실립니다.

**② 비용·거버넌스 도구의 부상.** 에이전트를 많이 부릴수록 **세션 예산, 한도, 이벤트 스트림, Webhook** 같은 **통제 장치**가 중요해집니다. 기능이 늘어날수록 **"얼마나 쓰는지 보이게 하는 것"** 이 경쟁력이 됩니다.

**③ '언제 쓰지 말아야 하는가'의 정립.** Anthropic이 **"멀티에이전트를 쓰지 말아야 할 때"** 를 함께 문서화한다는 점은, 이 기술이 **과대광고 단계를 지나 실무 규율 단계로** 들어가고 있다는 뜻입니다.

결국 이번 한 주의 진짜 의미는 **"에이전트를 몇 마리까지 늘릴 수 있나"가 아니라 "그 배분을 코드로 옮겨 재현 가능하게 만들 수 있나"** 라는 질문을 Anthropic이 **플랫폼 차원에서 던졌다**는 데 있습니다.

## 마무리 — 이런 분께 추천

정리하면, 이번 소식은 **문서·코드처럼 '조각이 많은' 작업을 자동화 파이프라인에 얹어둔 팀**이라면 꼭 확인해볼 만합니다. 챙길 포인트는 세 가지입니다. **첫째**, 워크플로를 붙이기 전에 **세션 예산 상한**을 먼저 걸 것. **둘째**, 작업을 **'조각이 많고 병렬화가 되는가'** 기준으로 걸러 **단일 에이전트와 비교**할 것. **셋째**, 개선된 **교차검증 패턴**을 파이프라인 검증 계층에 반영할 것.

반대로 작업이 작고 순차적이라면, 지금은 **그냥 에이전트 한 마리**가 더 빠르고 저렴합니다. "기능이 늘었다"보다 **"어디에 쓸 때 이득인가"** 를 먼저 따져보시길 권합니다.
