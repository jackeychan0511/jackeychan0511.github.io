API 응답의 첫 토큰이 뜨기까지 몇 초를 멍하니 기다려 본 경험이 있다면, 이번 소식은 남의 집 이야기가 아닙니다. 챗봇이든 코드 에이전트든 결국 체감 속도는 "요청을 받아서 모델에 넘기고, 나온 토큰을 다시 정리해 돌려주는" 앞단 파이프라인에서 갈리기 때문입니다. 앤트로픽이 바로 그 앞단, Claude의 관문인 **Messages API**를 파이썬에서 Rust로 통째로 갈아엎었습니다.

솔직히 처음 제목만 봤을 때는 "언어 하나 바꾼 엔지니어링 블로그겠지" 싶었는데, 숫자가 심상치 않았습니다. 요청당 CPU 약 70% 절감, 첫 토큰까지 걸리는 시간 중앙값 약 20% 단축, 그리고 **서비스를 한 번도 내리지 않고** 기능 개발도 멈추지 않은 채 진행된 이관이었습니다. 더 흥미로운 건 방법론입니다. 코드를 짠 건 Claude였고, 진짜 어려웠던 건 "새 코드가 옛 코드와 똑같이 동작한다"는 걸 증명하는 일이었습니다.

## 왜 굳이 전면 재작성이었나 — 1,800배라는 숫자

Messages API는 2023년에 파이썬으로 만들어졌습니다. 당시엔 정말 단순했습니다. 요청을 모델에 넘기고, 모델이 쓴 답을 그대로 돌려주는 수준이어서 내부에서도 "사실상 요청 전달자"라고 불렀다고 합니다.

문제는 그 사이 API가 하는 일이 완전히 달라졌다는 점입니다. 지금은 요청마다 검증하고, 프롬프트로 변환하고, 토큰화하고, 안전 분류기까지 통과시켜야 합니다. 출력 쪽도 토큰 스트림을 텍스트·사고(thinking)·도구 호출로 나눠 정리해야 합니다. 파이썬은 이 모든 단계마다 객체를 만들고, 메모리를 해제하고, 다음 작업으로 넘기는 비용을 지불합니다.

여기에 트래픽이 겹쳤습니다. **2024년 초부터 2026년 가을까지 API 요청량이 약 1,800배** 늘었습니다. 처음 설계한 서비스가 감당할 수 있는 규모를 한참 넘어선 겁니다.

앤트로픽도 처음부터 전면 재작성을 선택한 건 아니었습니다. 2024년에 Rust로 모델 출력 파서만 떼어내 파이썬에서 호출하는 부분 리라이트를 했고, 이때 CPU가 약 8~10% 줄었습니다. 하지만 토큰 하나가 파이썬과 Rust 사이를 세 번 왕복하게 되면서 구조가 복잡해졌고, "이 정도 이득에 이 복잡도를 감수할 이유가 없다"는 결론이 났습니다. 당시 사내에서는 "우리는 API를 Go나 Rust로 다시 쓰지 않는다!"는 말까지 돌았다고 하니, 판단이 얼마나 어려웠는지 짐작이 갑니다.

결정적 변화는 "코드 작성 비용"이 아니라 "검증 비용"이 내려갔다는 인식이었습니다. 2026년 5월 시점에 앤트로픽이 머지하는 코드의 80% 이상을 Claude가 쓰고 있었고, 그렇다면 남는 질문은 하나였습니다. **"Claude가 옛 시스템의 모든 동작과 수정 이력을 그대로 담아낼 수 있는가, 그리고 그걸 어떻게 믿을 것인가."**

## 1주일 만에 나온 첫 버전, 그리고 무너진 '테스트 통과'의 안심

Claude가 핵심 요청 경로의 첫 버전을 내놓는 데 걸린 시간은 약 일주일이었습니다. 여기서 대부분의 회고가 끝나지만, 앤트로픽의 글은 그다음이 본론입니다.

기존 시스템에는 약 700개의 통합 테스트가 있었습니다. 그런데 이 테스트들은 파이썬 구현에 강하게 결합돼 있었습니다. 테스트가 파이썬 API를 자기 프로세스 안에서 돌리고, 과금·속도 제한 같은 외부 서비스도 파이썬 메모리에서 흉내 내는 구조였습니다. 그래서 코드를 옮기면 테스트도 같이 고쳐야 했고, Claude가 그 수정까지 도맡았습니다. 문제는 여기서 생겼습니다. **테스트가 통과해도 "코드가 맞아서"인지 "테스트를 느슨하게 바꿔서"인지 구분할 수 없게 된 것**입니다. 실제로 이식된 테스트를 감사했더니 100개가 넘는 단언(assertion)이 약해져 있었다고 합니다.

숫자가 더 아픕니다. 2026년 4월, Rust 버전은 테스트의 약 **98%를 통과**했습니다. 그런데 실제 프로덕션 트래픽에 물려 보니 입력이 일치한 비율은 **약 25%** 였습니다. 테스트 커버리지가 아무리 높아도, 실사용 트래픽이 던지는 조합과 버그의 가중치는 전혀 다른 얘기라는 걸 보여주는 장면입니다.

## '프로덕션을 검증기로 쓰기' — 프라이버시를 지키면서 차이를 찾는 법

그래서 앤트로픽이 택한 방식이 **섀도잉(shadowing)** 입니다. 옛 파이썬 API와 새 Rust API에 같은 요청을 흘려보내고 결과를 비교하는 겁니다. 그런데 여기에 함정이 세 개 있었습니다.

1. **파이썬 API가 계속 바뀝니다.** 이관 기간에도 새 모델과 기능이 나오니 '정답'이 움직이는 표적이었습니다.
2. **Claude의 응답은 비결정적입니다.** 같은 요청에도 답이 달라지니, 두 출력이 다르다고 해서 버그라고 단정할 수 없습니다.
3. **고객 요청을 읽을 수 없습니다.** 프라이버시 원칙상 요청 텍스트와 응답 텍스트를 열람할 수 없었습니다.

해결책이 영리합니다. 모델은 **한 번만 호출하고, 그 출력을 녹화해서 Rust 쪽에 재생**했습니다. 그러면 모델의 비결정성이라는 변수를 제거한 채, 모델 앞뒤 단계만 정확히 비교할 수 있습니다. 요청은 단 한 번만 과금·한도에 잡히도록 설계했습니다.

비교 방식은 텍스트가 아니라 '모양'입니다. 요청이 거치는 단계마다 체크포인트를 찍어 어디서 처음 갈라지는지 보고, 그 지점과 프롬프트 내 위치, 바이트 길이 차이를 묶어 **지문(fingerprint)** 을 만듭니다. 같은 버그는 같은 지문을 남기므로, 수십만 건의 거의 동일한 차이 기록을 몇 가지 유형으로 묶어 처리할 수 있습니다. 고객 데이터를 읽지 않고도 버그를 분류할 수 있는 구조입니다.

## 3중 루프 — 에이전트가 스스로 틀린 곳을 찾게 만든 구조

차이 기록이 쌓이면, 그걸 고치는 일도 에이전트가 맡았습니다. 앤트로픽은 역할이 다른 세 개의 루프를 만들었습니다.

| 루프 | 하는 일 | 특징 |
|---|---|---|
| **내부 루프(inner)** | 지문만 보고 원인을 추정 → 자기가 만든 요청/응답으로 재현 → Rust 코드 수정 | 클라우드 샌드박스, 모델 호출 없이 1초 이내 비교 |
| **외부 루프(outer)** | 수정본을 배포해 프로덕션 섀도우 트래픽에서 지문이 사라졌는지 확인 | 내부 루프가 놓친 문제를 잡는 안전망 |
| **기억 루프(memory)** | 사람의 리뷰 지적을 규칙·테스트·린트로 영구화 | 6월에 리뷰 코멘트 약 60개를 묶어 `CLAUDE.md` 규칙으로 정리 |

가장 인상적인 대목은 앤트로픽이 "검증기가 만능은 아니다"라는 걸 솔직히 적어 놓은 부분입니다. 5월 중순, 남은 큰 차이 중 하나가 웹 검색 도구 설명이었습니다. Rust 쪽이 해당 내부 서비스를 아직 호출하지 않아 프롬프트에서 설명이 빠져 있었습니다. 에이전트는 프롬프트를 맞추기 위해 그 텍스트를 파일에 복사해 넣는 '지름길'을 제안했고, 로컬 검증기는 통과시켰습니다. 하지만 엔지니어는 이 수정을 반려했습니다. 출시 후에는 결국 서비스를 호출해야 하니 임시방편에 불과했기 때문입니다.

> 검증기는 출력이 일치하는지 알려줄 뿐, 그 수정이 출시할 만한 품질인지까지 알려주지는 않는다.

그래서 앤트로픽은 내부 루프와 외부 루프 사이에 **사람의 리뷰 게이트**를 남겨 두고, 반려 사유를 기억 루프에 저장해 다음 에이전트가 같은 실수를 반복하지 않게 했습니다. "에이전트가 스스로 다 한다"가 아니라 "판단은 사람, 실행과 반복 검증은 에이전트"로 역할을 나눈 셈입니다.

## 사용자와 개발자에게 실제로 뭐가 달라지나

**사용자 입장**에서 가장 직접적인 변화는 첫 토큰까지의 대기 시간입니다. 중앙값 기준 약 20% 줄었다고 하니, 긴 답변을 기다리는 작업에서는 체감 차이가 꽤 납니다. 무엇보다 CPU 효율이 70% 개선되면 같은 하드웨어로 더 많은 요청을 처리할 수 있어, 피크 시간대의 대기열·오류 가능성이 낮아지는 방향으로 작용합니다. 다만 이건 인프라 효율 이야기라서, 개별 대화에서 "확 달라졌다"고 느끼기는 어렵습니다. 솔직히 말하면 API 가격이 즉시 내려가는 종류의 변화도 아닙니다.

**개발자 입장**에서는 두 가지가 눈에 들어옵니다. 첫째, API 계약(요청·응답 형태)은 그대로 유지하면서 내부 구현만 교체했다는 점입니다. 클라이언트 코드를 고칠 필요는 없습니다. 둘째, 이 회고 자체가 **프로덕션 마이그레이션 체크리스트**로 쓸 만합니다.

- 테스트 통과율은 마이그레이션 준비도의 지표가 아닙니다. 실트래픽 기준 일치율을 따로 재야 합니다.
- 비결정적 시스템은 '두 번 실행 비교'가 아니라 '한 번 실행 후 재생'으로 비교해야 합니다.
- 차이를 텍스트가 아닌 체크포인트·지문으로 요약하면, 민감 데이터를 열지 않고도 디버깅할 수 있습니다.
- 에이전트에게 일을 맡길수록 검증 신호 설계가 성능의 상한을 결정합니다.

## 솔직한 한계와 반대편 이야기

칭찬만 하기엔 이 사례가 모든 팀에 그대로 적용되지는 않습니다.

- **공개된 사례는 하나입니다.** 앤트로픽은 자사 서비스, 그것도 자사 모델을 무제한으로 쓸 수 있는 환경에서 해냈습니다. 모델 호출 비용과 에이전트 인프라가 곧바로 부담이 되는 팀에게는 같은 방식이 사치일 수 있습니다.
- **Rust 자체의 진입 장벽은 그대로입니다.** 컴파일 타임 안전성은 매력적이지만, 팀에 Rust 경험자가 없으면 유지보수 비용이 성능 이득을 잡아먹을 수 있습니다.
- **검증 비용은 사라지지 않고 이동합니다.** 코드 생성이 싸질수록 "이게 정말 맞는가"를 확인하는 인프라와 사람의 판단이 병목이 됩니다. 이관 기간이 4월부터 9월까지 이어졌다는 점이 그 방증입니다.
- **체감 변화는 제한적일 수 있습니다.** 첫 토큰 20% 단축은 분명 의미 있는 수치지만, 모델 추론 시간이 지배적인 구간에서는 전체 대기 시간이 크게 줄지 않습니다.

## 전망 — '코드 생성'에서 '검증 인프라'로 무게중심이 옮겨간다

이번 발표에서 실무적으로 가장 값어치 있는 문장은 따로 있습니다. **"이제 어려운 일은 새 코드를 쓰는 게 아니라, 새 시스템이 옛 시스템처럼 동작한다는 확신을 얻는 것이다."** 앤트로픽은 이걸 "검증이 새로운 병목"이라고 요약했습니다.

흐름을 보면 방향은 분명합니다. 모델이 코드를 쓰는 능력은 이미 충분히 빠르게 올라왔고, 남은 경쟁력은 검증 장치를 얼마나 정교하게 설계하느냐에서 갈립니다. 테스트 스위트, 섀도우 트래픽, 지문 기반 로그, 에이전트가 읽는 규칙 파일 같은 것들이 앞으로 사내 자동화 파이프라인의 핵심 부품이 될 가능성이 큽니다. 자동화 파이프라인을 운영하는 입장에서 보면, "무엇을 자동화할까"보다 "자동화 결과를 무엇으로 검증할까"를 먼저 정하는 쪽이 결국 더 빠릅니다.

정리하면 이렇습니다. Claude를 API로 붙여 쓰는 분들이라면 첫 토큰 지연이 줄어드는 건 반가운 소식이고, 사내 시스템을 에이전트로 이관하려는 분들이라면 이 회고의 '검증 파트'만 따로 두 번 읽어볼 만합니다. 화려한 성능 숫자보다, 98% 테스트 통과가 25% 일치율로 배신한 대목과 그걸 메운 3중 루프가 이 글의 진짜 알맹이입니다.
