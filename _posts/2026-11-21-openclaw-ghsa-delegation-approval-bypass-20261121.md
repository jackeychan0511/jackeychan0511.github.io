## 에이전트 권한을 '읽기 전용'으로 묶어두고 쓰는 구성이라면

AI 에이전트를 실사용하고 있습니다. 크론잡을 돌리고 있습니다. 이렇게 자동화 파이프라인을 운영하다 보면 권한을 나눠두는 게 자연스러워집니다. 요약·수집·모니터링 같은 반복 업무는 넓게 허용하고, 파일 쓰기나 셸 실행은 막아두는 식입니다. "이 에이전트는 조회만 하면 된다"는 전제로 정책을 조여두는 경우가 많습니다.

문제는 **그 전제가 지켜지는지를 정책 파일만 보고 판단하기 어렵다**는 점입니다. 에이전트가 직접 셸을 못 돌려도, **설정을 바꿀 수 있는 도구**가 열려 있으면 결과적으로 실행 경로를 스스로 열 수 있습니다. 이번 공지가 정확히 그 지점을 다룹니다.

솔직히 말하면 이런 유형의 취약점은 릴리스 노트만 훑어서는 눈에 잘 안 들어옵니다. 기능 추가가 아니라 **"막아둔 게 실제로 막혔는가"** 의 문제라서, 보안 공지를 따로 봐야 그림이 잡힙니다. 오늘은 **GitHub 보안 공지(GHSA-pw3x-g8v8-fvj2), 2026.11.4·2026.11.6 체인지로그, 공식 문서(Exec approvals), npm dist-tags** 를 기준으로 — 무엇이 뚫렸고, 어디까지 영향이 있고, 지금 무엇을 확인해야 하는지 순서로 정리하겠습니다.

|:---|:---|
| 공지 ID | **GHSA-pw3x-g8v8-fvj2** |
| CVE | 미부여 (2026-11-21 확인 시점 기준 CVE ID 없음) |
| 공개 시각 | 2026-11-19 02:01 UTC → **2026-11-19 11:01 (한국시간)** |

CVSS 벡터를 풀어보면 의미가 분명해집니다. **네트워크로 도달 가능(N)**, **공격 복잡도 낮음(L)**, **권한은 필요하지만 낮은 수준(PR:L)**, **사용자 상호작용 불필요(UI:N)**. 즉 "이미 게이트웨이에 붙을 수 있는 낮은 권한의 주체"가 사용자 클릭 없이 Confidentiality·Integrity·Availability 모두 High로 영향을 줄 수 있다는 평가입니다.

다만 공지 본문은 **"OpenClaw의 신뢰 운영자(trusted-operator) 모델 자체가 바뀐 것은 아니다"** 라고 선을 긋습니다. 인증된 게이트웨이 운영자, 설치된 플러그인, 의도된 로컬 실행 표면은 별도의 정책·승인·샌드박스·인증 경계를 넘지 않는 한 여전히 신뢰 대상이라는 설명입니다. **"외부 침입자가 원격에서 뚫는 취약점"이 아니라 "권한을 좁혀둔 구성에서 그 좁힘이 새는 문제"** 로 읽어야 정확합니다.

## 2. 영향 범위 — 두 구간으로 갈립니다

공지에 명시된 버전 범위는 아래와 같습니다.

| 구간 | 영향 | 비고 |
|:---|:---|:---|
| `>= 2026.9.2, < 2026.10.33` | **영향** | 2026.9.37, 2026.10.10 등 10월 라인 포함 |
| `>= 2026.11.1, < 2026.11.4` | **영향** | 2026.11.1 · 11.2 · 11.3 |
| `2026.10.33` | 패치됨 | 확장 안정판(extended-stable) 사용자용 |
| `2026.11.4` 이상 | 패치됨 | 2026.11.5 · 11.6 포함 |
| `2026.9.2` 미만 | 공지 대상 아님 | 어느 범위에도 해당하지 않음 |

여기서 헷갈리기 쉬운 지점이 두 가지 있습니다.

첫째, **확장 안정판 사용자는 2026.10.33으로 올려야 patched** 입니다. 2026.9.37이나 2026.10.10에 머물러 있었다면 위 표의 첫 줄에 그대로 걸립니다. 2026.10.33은 공지 공개 **하루 전**(11월 18일 13시 15분)에 이미 배포돼 있었기 때문에, 그때 올려둔 인스턴스는 공지 시점에 이미 안전한 상태였습니다.

둘째, **2026.11.4 이상은 영향 없음** 입니다. 11.4가 11월 16일 안정판으로 나왔고, 공지는 11월 19일에 공개됐습니다. 순서상 **패치가 먼저 나가고 공지가 뒤에 붙은** 형태입니다. 그래서 "공지를 보고 나서야 고쳐졌다"가 아니라, **"이미 나와 있던 11.4에 수정이 들어 있었고 사흘 뒤에 그 사실이 공개됐다"** 로 이해하는 게 맞습니다.

현재 npm `dist-tags`는 이렇게 걸려 있습니다.

| 태그 | 버전 |
|:---|:---|
| `latest` | **2026.11.6** |
| `beta` | 2026.11.10-beta.1 |
| `extended-stable` | **2026.10.33** |

정리하면 — **정규 채널은 11.4 이상이면 patched, 확장 안정판은 10.33이면 patched** 입니다. 반대로 11.1~11.3이나 10.10 이하에 머물러 있다면 지금이 조치 시점입니다.

## 3. 무엇이 뚫렸나 — 정책이 막은 것과 설정이 연 것

공지의 핵심 문장은 이렇습니다.

> "In affected versions, the `openclaw` tool could apply persistent configuration changes without approval when tool policy denied execution and file writes."

번역하면 **"영향받는 버전에서 `openclaw` 도구는, 도구 정책이 실행과 파일 쓰기를 거부한 상태에서도 승인 없이 지속 설정 변경을 적용할 수 있었다"** 입니다. 그리고 영향 항목은 이렇게 이어집니다.

> "This could let a restricted agent enable host command execution through configuration changes."

**제한된 에이전트가 설정 변경을 통해 호스트 명령 실행을 켤 수 있었다**는 뜻입니다. 즉 직접 셸을 두드리는 경로는 막혀 있어도, **설정을 고쳐서 그 문을 열어젖히는 우회로**가 남아 있었습니다.

이 설명은 2026.11.4 체인지로그의 해당 항목과 정확히 맞물립니다.

> "Requires approval for delegated persistent changes when authority is restricted or unverified and no other grant applies. Adds a standing approval setting for permitted delegated changes. **Full Access or standing approval can authorize changes that enable host code execution even when direct execution or editing tools are denied.**"

해석하면 — 권한이 제한됐거나 검증되지 않은 상태에서는 **위임된 지속 변경(delegated persistent changes)** 에 승인을 요구하고, 허용된 위임 변경에 대해서는 **상시 승인(standing approval)** 설정을 새로 둡니다. 그런데 문제가 된 건 그 뒤 문장입니다. **Full Access나 상시 승인이 있으면, 직접 실행·편집 도구가 거부된 상태에서도 호스트 코드 실행을 가능하게 하는 변경을 승인할 수 있었다**는 것이죠.

| 계층 | 기존 동작 | 11.4 이후 |
|:---|:---|:---|
| 직접 실행 도구 | 정책이 거부 | 정책이 거부 (동일) |
| 직접 파일 쓰기 | 정책이 거부 | 정책이 거부 (동일) |
| 위임된 설정 변경 | 자동 승인 설정에 기대는 경로가 있었음 | **권한이 제한·미검증이면 승인 요구** |
| 반복되는 위임 변경 | 매번 승인 | 상시 승인으로 한 번에 허용 가능 |
| 결과 | 설정으로 실행 경로를 열 수 있었음 | 승인 없이는 열리지 않음 |

정리하면 **"도구를 막는 것"과 "설정을 바꾸는 것을 막는 것"이 별개였다**는 게 이번 사건의 본질입니다. 권한 설계를 도구 단위로만 하고, 설정 변경 권한은 따로 보지 않았다면 그 틈이 그대로 노출됩니다.

## 4. 왜 실무에서 더 신경 쓰이는가 — 기본값이 '묻지 않음'입니다

여기서 공식 문서를 같이 봐야 합니다. `Exec approvals` 문서는 게이트웨이 호스트의 기본값을 이렇게 설명합니다.

- `tools.exec.mode` 값: `deny` / `allowlist` / `ask` / `auto` / `full`
- `exec.security` 기본값: **게이트웨이·노드 호스트는 `full`**, 샌드박스 호스트는 `deny`
- `exec.ask` 기본값: **`off`**
- `askFallback` 기본값: **`deny`** (승인 UI에 닿을 수 없거나 시간 초과 시)

즉 **게이트웨이를 상시 서비스로 올려놓은 구성에서는 기본적으로 승인 프롬프트가 뜨지 않습니다.** 문서 표현대로라면 "호스트 실행을 일반 정책 프롬프트 없이 실행"하는 상태입니다. 이건 게이트웨이 운영자를 신뢰 대상으로 보는 설계 때문인데, **에이전트에 낮은 권한을 주려는 목적이라면 기본값을 그대로 두면 안 된다**는 뜻이기도 합니다.

문서는 한 가지를 더 분명히 합니다.

> "effective policy is the stricter of `tools.exec.*` and approvals defaults: approvals can only tighten config-derived security/ask, never loosen them."

**승인 설정은 설정값보다 느슨해질 수 없고, 조일 수만 있다**는 원칙입니다. 그래서 "승인 파일에 뭔가 적혀 있으니 안전하겠지"가 아니라, **설정값 자체를 조여야 하는 경우가 많습니다.**

자동화를 돌리는 구성이라면 여기에 한 겹이 더 있습니다. 문서의 `Standing grants for automations` 항목을 보면, **게이트웨이 호스트의 크론(자동화) 실행에서 발생한 승인 요청은 연결된 승인 클라이언트(Control UI, macOS/iOS/Android 앱, 승인 기능을 선언한 API 클라이언트)에만 전달**됩니다. TUI는 승인 카드를 그리지 않고, **채팅 채널은 자동화 승인을 절대 받지 않습니다.** 승인 화면이 연결돼 있지 않으면 **요청은 즉시 거부되고 실행 오류에 정책 수정 안내가 붙습니다.**

| 상황 | 승인 카드 도착 | 결과 |
|:---|:---|:---|
| Control UI·앱·API 클라이언트 연결됨 | 도착 | 결정할 때까지 대기 |
| 승인 화면 없음 | 없음 | **즉시 거부** + 오류에 정책 안내 |
| 텔레그램·슬랙 등 채널만 연결 | 없음 | 채널로는 오지 않음 |
| TUI만 열어둠 | 없음 | 카드 렌더링 안 됨 |

업무 자동화를 무인으로 굴리는 경우, **"승인 프롬프트가 뜨면 눌러주면 되지"라는 전제가 성립하지 않는 구간이 있다**는 얘기입니다. 승인 없는 자동 실행을 원한다면 그건 **상시 승인(standing grant)을 명시적으로 발급**해서 관리해야 하고, 반대로 안전을 원한다면 승인 화면이 붙어 있는 클라이언트를 상시 띄워둬야 합니다.

## 5. 패치 버전에서 실제로 달라진 것

11.4의 변경을 실무 관점으로 다시 정리하면 세 줄입니다.

1. **위임된 지속 변경에 승인 요구** — 권한이 제한·미검증이면 자동 승인 설정에 기대지 못합니다.
2. **상시 승인 설정 추가** — 반복되는 허용된 변경은 한 번 승인으로 처리할 수 있습니다(대신 그 승인의 범위를 관리해야 합니다).
3. **낡은 자동 승인 설정 무시** — 실행 중 설정이 바뀌거나 도구가 준비되는 사이에 이전 `autoApproveChanges` 값에 기대던 경로를 다시 검사합니다. 회수된 승인은 실행이 이전 모델 설정을 들고 있어도 재확인됩니다.

세 번째가 특히 중요합니다. **승인을 회수했는데 실행 중인 턴이 예전 설정을 그대로 들고 가는** 유형은 자동화에서 놓치기 쉽습니다. 크론잡이 길게 도는 구성일수록 "회수했는데 왜 아직 도나" 하는 상황이 생기기 때문입니다.

## 6. 하루 뒤 후속 패치 — 2026.11.6의 승인 검사

공지가 나온 다음 날(2026-11-19 17:26 UTC → **2026-11-20 02:26 한국시간**), 안정판 **2026.11.6**이 나왔습니다. 규모는 **PR 386건, 기여자 157명**. 릴리스 노트 첫 문장은 "버그 수정과 편의 개선을 담은 패치 릴리스"라고 밝히고 있지만, **보안·프라이버시 섹션에는 승인 집행과 직결되는 수정이 여러 건** 들어 있습니다.

| 항목 | 내용 |
|:---|:---|
| 승인 필요 명령의 일관성 | macOS·Linux에서 승인이 필요한 게이트웨이 셸 명령 검사를 더 일관되게 적용. **이전에 자동 실행되던 명령이 이제 승인 요구 또는 거부될 수 있음** |
| 정책 우회 구멍 | 정책상 필요한 승인 없이 일부 셸 명령이 실행되던 문제 수정 |
| Windows 인라인 셸 | 인라인 POSIX 셸 명령 승인은 **1회성** 유지 (`allow always`를 골랐어도 재실행 시 재승인) |
| 환경 변경 명령 | 명령이 환경을 바꾸는 경우의 승인 검사 수정. 이전에 자동 실행되던 일부가 이제 프롬프트 대상 |
| 자동 검토 비활성화 | 변경 없는 exec 정책을 다시 적용할 때 자동 명령 검토가 조용히 꺼지던 문제 수정 (cautious 프리셋 포함) |
| 자격증명 노출 | 플러그인 소유 자격증명이 일반 모델 자격증명 탐색에 섞이지 않도록 수정 |
| 브라우저 스냅샷 | 입력된 비밀번호, 일회용 코드·카드번호·보안코드 필드가 모델에 노출되던 문제 수정 |
| 샌드박스 검색 | 샌드박스 웹 검색이 신뢰 정책 밖 제공자를 쓰던 문제 수정 |
| 환경변수 차단 | `PERLLIB`·`PERL5SHELL`을 워크스페이스 환경 파일과 호스트 명령 환경에서 차단 |

여기서 읽어야 할 신호는 **"승인 검사가 더 자주, 더 엄격하게 걸린다"** 입니다. 11.6으로 올리면 이전까지 조용히 통과하던 명령이 승인 대기로 바뀌거나 거부될 수 있습니다. 자동화가 갑자기 멈춘 것처럼 보인다면, 버그가 아니라 **의도된 조임**일 가능성을 먼저 확인해야 합니다.

## 7. 지금 확인할 것 — 다섯 줄 체크리스트

버전과 정책을 눈으로 확인하는 순서입니다. 명령은 공식 문서에 나온 형태를 그대로 씁니다.

**① 설치 버전 확인**

```bash
npm view openclaw version      # 레지스트리 최신값
openclaw approvals get         # 이 호스트의 실효 exec 정책
```

**② 정책 모드 확인** — `openclaw approvals get` 결과에서 `tools.exec.mode`(또는 레거시 `exec.security`/`exec.ask` 조합), 승인 파일 기본값, 병합된 실효값을 함께 봅니다. `full` + `off` 조합이면 **승인 프롬프트가 사실상 없다**고 이해해야 합니다.

**③ 대기 중인 승인 확인**

```bash
openclaw approvals pending
```

무인 자동화를 돌리는 구성이라면 여기에 카드가 쌓여 있지 않은지 주기적으로 보는 게 좋습니다. 승인 화면이 연결돼 있지 않으면 카드가 쌓이는 대신 **즉시 거부**되므로, 실행 로그의 거부 사유도 같이 봐야 합니다.

**④ 위임 변경 자동 승인 정리** — 상시 승인(standing grant)을 발급해 둔 항목이 있다면, 그 범위가 지금도 필요한지 확인합니다. 문서 기준으로 상시 승인은 **에이전트·자동화·작업 구성·명령 텍스트·작업 디렉터리·환경**에 묶입니다. 작업 정의가 실질적으로 바뀌면 승인이 무효가 되고 다시 프롬프트가 뜹니다(일시정지 후 재개는 유지).

**⑤ 게이트웨이 공유 금지** — 공지의 완화 문구에 명시된 항목입니다. **서로 신뢰하지 않는 사용자끼리 하나의 게이트웨이를 공유하지 말 것**, 채널·도구 허용목록을 좁게 유지할 것, 쓰지 않는 기능은 끌 것.

공지가 제시한 완화책 원문은 이렇습니다.

> "Upgrade to a patched version. Before upgrading, set `tools.exec.mode` to `ask` and deny untrusted delegated changes. As general hardening, keep channel and tool allowlists narrow, avoid sharing one Gateway between mutually untrusted users, and disable the affected feature when it is not needed."

업그레이드가 어려운 상황이라면 **최소한 `tools.exec.mode`를 `ask`로 두고, 신뢰하지 않는 위임 변경을 거부**하는 것이 공지가 권하는 임시 조치입니다.

## 8. 솔직한 단점과 주의점

이번 공지를 읽을 때 과하게 읽지도, 가볍게 넘기지도 않아야 합니다.

- **"원격에서 바로 뚫린다"는 식의 표현은 과장입니다.** 공지 스스로 신뢰 운영자 모델은 그대로라고 밝히고 있고, 전제 조건은 **이미 게이트웨이에 접근 가능한 낮은 권한의 주체**입니다.
- **반대로 "패치됐으니 끝"도 아닙니다.** 기본값이 `full`/`off`인 구성에서는 승인 프롬프트가 애초에 뜨지 않습니다. 패치로 우회로는 막혔지만, **권한 설계 자체를 다시 볼 시점**이라는 신호로 읽는 게 맞습니다.
- **CVE 번호가 아직 없습니다.** GHSA ID로만 추적되므로, CVE 목록만 모니터링하는 방식으로는 이 건을 놓칠 수 있습니다. GitHub Security Advisories를 직접 구독하는 편이 안전합니다.
- **11.6은 패치 릴리스입니다.** 새 기능이 아니라 승인·자격증명·스냅샷 쪽을 조인 릴리스이므로, 업데이트 직후 자동화가 승인 대기로 멈추는 현상을 정상 동작 범위에 넣어두고 봐야 합니다.
- **자동화 승인은 채팅 채널로 오지 않습니다.** 텔레그램으로 알림을 받는 구성이라면 "승인 요청이 안 왔는데 왜 멈췄지"가 되기 쉽습니다. 승인은 승인 클라이언트에서, 결과 알림은 채널에서 — 경로가 다르다는 점을 분리해서 설계해야 합니다.

## 마무리 — 권한은 '도구'가 아니라 '변경 경로'까지 묶어야 합니다

정리하면 이렇습니다.

| 질문 | 답 |
|:---|:---|
| 무슨 일이 있었나 | 제한된 에이전트가 승인 없이 지속 설정을 바꿔 호스트 실행을 켤 수 있었음 (GHSA-pw3x-g8v8-fvj2) |
| 심각도 | High, CVSS 3.1 **8.8** (CWE-863) |
| 영향 버전 | 2026.9.2~10.33 미만, 2026.11.1~11.4 미만 |
| 패치 버전 | **2026.11.4** / 확장 안정판 **2026.10.33** / 후속 **2026.11.6** |
| 임시 완화 | `tools.exec.mode: ask`, 신뢰하지 않는 위임 변경 거부, 허용목록 축소 |
| 확인 명령 | `openclaw approvals get`, `openclaw approvals pending` |

에이전트 권한을 설계할 때 흔히 도구 목록만 봅니다. "이 에이전트는 exec를 못 쓰고, 파일 쓰기도 못 쓴다"로 끝내는 경우가 많습니다. 그런데 이번 사건은 **그 두 개를 막아도 설정을 바꿀 수 있는 경로가 열려 있으면 결과적으로 같은 일이 가능하다**는 걸 보여줍니다.

가성비 좋은 구성, 다시 말해 **적은 운영 부담으로 안전하게 오래 굴리는 구성**을 찾는 분들이라면 순서를 이렇게 잡는 게 좋습니다. ① 버전을 패치선 위로 올린다(11.4 이상 또는 10.33), ② `tools.exec.mode`를 `ask` 또는 `allowlist`로 조인다, ③ 상시 승인은 자동화 단위로만, 범위를 좁게 발급한다, ④ 승인 화면이 붙은 클라이언트를 상시 띄워둔다. 네 줄이면 이번 유형의 사고는 대부분 막힙니다.

업무 자동화를 오래 돌릴수록 무서운 건 기능 부족이 아니라 **"막아뒀다고 믿은 것"이 실제로는 안 막혀 있던 상태**입니다. 이번 공지는 그 믿음을 한 번 점검해보라는 신호로 받아들이면 되겠습니다.
