야간 배치를 돌려놓고 아침에 결과를 확인하는 방식으로 자동화 파이프라인을 운영하다 보면, 요금제 구조가 바뀌는 뉴스가 유난히 예민하게 느껴집니다. 모델 단가표가 조금 오르는 것보다 무서운 건 **"하루에 얼마까지 쓸 수 있는지"라는 상한선 자체가 새로 생기는 변화**입니다. 상한이 생기면 배치 하나가 중간에 잘려도 그 사실을 모른 채 다음 날 결과만 보고 있게 되니까요.

2026년 10월 27일, 노우스 리서치(Nous Research)가 헤르메스 에이전트(Hermes Agent) 구독 구조를 개편했습니다. 핵심은 세 가지입니다. **월 단위 크레딧 한 덩어리를 일·주·월 사용 한도 조합으로 바꾸고**, **모든 신규 플랜에 클라우드 에이전트를 포함하고**, **일부 고가 모델에는 별도의 월 한도를 둡니다.** 여기에 "레거시 유료 플랜에서 새 플랜으로 넘어가면 되돌릴 수 없다"는 조건이 붙습니다.

![헤르메스 에이전트 공식 홈페이지 대표 이미지](/assets/images/posts/hermes-subscription-plans-20261030/hermes-hero.jpg)
*헤르메스 에이전트 공식 사이트의 대표 아트워크 (출처: Nous Research 공식 홈페이지)*

> **📌 한줄 요약:** 10월 27일부로 헤르메스 에이전트 구독은 "월 크레딧 한 덩어리"에서 **일·주·월 다층 한도 구조**로 바뀌었습니다. 고가 모델에는 별도 월 한도가 붙고, 사용량 페이지에 리셋 시각이 표시되며, 모든 신규 플랜에 클라우드 에이전트가 포함됩니다. 기존 구독자는 Nous Portal 결제 페이지에서 전환할 수 있지만 **레거시 유료 플랜으로 되돌아가는 것은 불가능**합니다. 코드 쪽에서는 v0.22.5에 이미 플랜 게이지와 리밋 카드가 들어와 있었기 때문에, UI가 먼저 준비되고 정책이 뒤따라온 순서입니다.

## 1. 무엇이 바뀌었나 — 발표된 내용 그대로

노우스 리서치가 공개한 개편 내용은 다음 항목으로 정리됩니다.

| 항목 | 개편 후 |
|:---|:---|
| 과금 구조 | 월 단위 크레딧 한 덩어리 → **일·주·월 사용 한도 조합** |
| 고가 모델 | 일부 모델에 **별도 월 한도** 추가 |
| 사용량 확인 | Usage 페이지에서 **각 한도의 리셋 시각** 표시 |
| 구매 크레딧 | 한도를 다 쓴 뒤 **이어서 쓰는 것은 선택 사항** |
| 클라우드 에이전트 | **모든 신규 플랜에 포함** |
| 기존 구독자 | Nous Portal 결제 페이지에서 전환 가능 |
| 전환 되돌리기 | **불가** (레거시 유료 플랜으로 복귀 불가) |

숫자로 된 정확한 플랜별 가격표나 한도량은 이 글을 쓰는 시점에 공식 문서에 아직 반영되지 않았습니다. 확인 가능한 건 **구조가 바뀌었다는 사실과 되돌릴 수 없다는 조건**입니다. 그래서 이 글에서는 "얼마인가"보다 **"무엇이 달라지고, 무엇을 먼저 확인해야 하는가"** 에 초점을 맞춥니다.

## 2. 순서가 흥미롭다 — 코드가 먼저, 정책이 나중

이 개편에서 눈에 띄는 점은 **v0.22.5 릴리스 노트에 이미 "usage-window plan support"가 들어 있었다**는 것입니다. 10월 22일 릴리스 노트에는 이렇게 적혀 있습니다.

> usage-window plan support (plan gauges, limit cards and model-switch recovery for window-based plans)

풀어보면 세 가지입니다.

1. **플랜 게이지** — 남은 한도를 게이지 형태로 보여주는 UI
2. **리밋 카드** — 한도에 도달했을 때 상태를 알려주는 카드
3. **모델 전환 복구** — 윈도우 기반 플랜에서 모델을 바꿀 때 세션이 깨지지 않도록 하는 처리

즉 **5일 먼저 클라이언트가 다층 한도를 표현할 준비를 마쳤고, 그 위에 10월 27일 실제 요금 정책이 올라온 것**입니다. 릴리스 노트에 "undocumented here on purpose"라고 적혀 있던 항목이 며칠 뒤 정책 발표로 이어진 셈이라, 릴리스 노트를 꼼꼼히 읽는 쪽이라면 이미 예고를 본 셈입니다.

자동화를 돌리는 입장에서 이 디테일이 중요한 이유는, **"한도에 닿았을 때 에이전트가 어떻게 행동하는가"가 코드로 정의되어 있다**는 뜻이기 때문입니다. 리밋 카드가 뜨고 모델 전환이 복구된다는 건, 한도 도달이 **조용한 실패가 아니라 화면에 드러나는 이벤트**로 취급된다는 이야기입니다.

## 3. 크론잡을 돌리는 쪽에서 실제로 달라지는 것

여기가 이 글의 본론입니다. 크론잡으로 정기 배치를 돌리는 자동화 파이프라인을 운영하고 있다면, 이번 개편은 **비용 문제가 아니라 스케줄 설계 문제**로 다가옵니다.

### ① 야간 장기 배치가 일 한도에 걸릴 수 있다

기존에는 월 크레딧이 한 덩어리였기 때문에 "이번 달 예산 안에서 언제 몰아 쓰든" 자유로웠습니다. 일 한도가 생기면 이야기가 달라집니다. 밤사이 여섯 시간짜리 배치를 돌리는 구성이라면, **그 배치 하나가 그날의 일 한도를 통째로 태우고 중간에 멈출 수 있습니다.**

대응은 두 가지입니다. 배치를 **일 한도 안에서 끝나는 크기로 쪼개는 것**, 또는 **한도 소진 시 다음 윈도우까지 대기 후 재개하는 로직**을 잡 스크립트에 넣는 것. 후자는 "실패하면 재시도"와는 다른 개념이라, 잡 스크립트에 **한도 도달을 정상 종료가 아닌 별도 상태로 기록**해두는 편이 안전합니다.

### ② 고가 모델의 별도 월 한도는 모델 라우팅 설계를 바꾼다

"일부 비싼 모델에는 별도 월 한도"라는 조건은, 위임(delegation) 구성에 직접 영향을 줍니다. 최상위 모델을 기본값으로 박아두고 모든 하위 작업을 거기로 보내는 구성은, 이제 **월 한도라는 두 번째 벽**에 부딪힙니다.

최근 헤르메스 에이전트에는 서브에이전트마다 모델을 고르는 라우팅 백엔드가 들어와 있으므로, **판단이 필요한 작업만 고가 모델로 보내고 조회·요약·로그 긁기는 저가 모델로 내리는 구성**이 사실상 필수가 됩니다. 비용 최적화라기보다 **한도 회피 설계**에 가깝습니다.

### ③ 리셋 시각을 모르면 재시도 타이밍을 못 잡는다

Usage 페이지에 리셋 시각이 표시된다는 건, 반대로 말하면 **그 시각을 확인하지 않으면 언제 다시 돌릴 수 있는지 모른다**는 뜻입니다. 자동 재시도 로직을 "일정 시간 후 재시도"로만 짜두면, 한도가 풀리기 전에 여러 번 헛방을 치게 됩니다. 파이프라인 상태 확인 절차에 **사용량 게이지 확인 단계**를 하나 넣어두는 편이 좋습니다.

### ④ 클라우드 에이전트 포함은 운영 위치를 바꾼다

모든 신규 플랜에 클라우드 에이전트가 포함된다는 점도 무시할 수 없습니다. 지금까지는 로컬이나 개인 VPS에 에이전트를 띄우고 크론을 돌리는 구성이 일반적이었는데, **구독에 클라우드 실행 환경이 딸려 오면 "어디서 돌릴 것인가"라는 선택지가 하나 늘어납니다.** 상시 실행이 필요한 정기 배치라면 로컬 전원 상태에 묶이지 않는 쪽이 유리합니다. 다만 클라우드 에이전트의 사양·세션 유지 방식·파일 시스템 접근 범위는 아직 공개된 정보가 제한적이라, 실제 이전은 문서가 채워진 뒤에 판단하는 편이 안전합니다.

### ⑤ 전환은 편도 통행권이다

가장 조심해야 할 항목입니다. **레거시 유료 플랜에서 새 플랜으로 넘어가면 되돌릴 수 없습니다.** 새 구조가 현재 사용 패턴에 맞는지 확신이 서지 않는다면, 전환 전에 최근 청구서와 사용량 기록을 남겨두는 것이 최소한의 보험입니다. "일 한도에 자주 걸리는 편인지", "고가 모델 비중이 얼마인지"를 숫자로 확인한 뒤 결정하는 편이 낫습니다.

## 4. 직접 확인하는 절차

전환 전후로 확인할 명령은 그리 많지 않습니다. 헤르메스 에이전트는 구독 상태를 CLI에서 그대로 보여줍니다.

```bash
hermes portal info     # 로그인 상태, 구독 정보, 모델·게이트웨이 라우팅
hermes portal open     # 구독 관리 페이지를 브라우저로 열기
```

`hermes portal info`는 로그인 여부, 현재 추론 제공자, 툴 게이트웨이 연결 상태(웹 검색·이미지 생성·TTS·브라우저·클라우드 터미널)를 한 화면에 보여줍니다. 여기서 **내 구독이 어떤 과금 구조로 잡혀 있는지**가 첫 번째 확인 지점입니다.

브라우저 쪽에서는 Nous Portal의 구독 관리 페이지에서 플랜과 사용량을 볼 수 있습니다. 이번 개편으로 **Usage 페이지에 각 한도의 리셋 시각**이 표시되므로, 새 구조로 넘어간 뒤에는 이 화면을 정기적으로 보는 습관이 필요합니다.

정리하면 확인 순서는 이렇습니다.

1. `hermes portal info` 로 현재 구독·제공자 상태 확인
2. Nous Portal 결제 페이지에서 새 플랜의 한도 구성 확인
3. 최근 사용 패턴(일 최대 사용량, 고가 모델 비중)과 대조
4. 크론잡 스케줄이 일 한도 안에 들어오는지 계산
5. 이상 없을 때만 전환 — **전환은 되돌릴 수 없음**

## 5. 솔직히 아쉬운 점

**첫째, 플랜별 수치가 아직 문서에 없다.** 공식 문서의 Nous Portal 페이지는 여전히 "월 구독 하나로 300+ 모델과 툴 게이트웨이를 쓴다"는 설명 수준에 머물러 있고, 일·주·월 한도 구성이나 고가 모델의 별도 한도 기준은 반영되지 않았습니다. 정책이 먼저 나가고 문서가 따라오는 전형적인 순서라, 당분간은 결제 페이지와 공지가 유일한 정보원입니다.

**둘째, 클라우드 에이전트의 실체가 아직 얇다.** "모든 신규 플랜에 포함"이라는 문장만으로는 상시 실행이 가능한 수준인지, 세션이 얼마나 유지되는지, 로컬 파일에 접근하는지 알 수 없습니다. 자동화 파이프라인을 클라우드로 옮길지 판단하려면 이 부분이 채워져야 합니다.

**셋째, 되돌릴 수 없는 전환이라는 조건 자체가 부담이다.** 요금제 개편에서 흔한 방식이긴 하지만, 사용 패턴이 계절에 따라 크게 흔들리는 쪽이라면 새 구조가 맞는지 판단할 관찰 기간이 짧게 느껴질 수 있습니다.

## 6. 이런 분들이라면 지금 확인해볼 만하다

- 크론잡으로 **정기 배치를 자동 실행**하고 있는 경우 — 일 한도가 스케줄 설계를 바꿉니다
- 서브에이전트를 여러 개 띄우는 **배치 위임**을 쓰는 경우 — 고가 모델 별도 한도가 직결됩니다
- 월 크레딧을 몰아 쓰는 패턴(월말 집중 작업)으로 운영해온 경우 — 다층 한도에서는 불리할 수 있습니다
- 상시 실행이 필요해 **클라우드 실행 환경**을 검토 중인 경우 — 신규 플랜에 포함됩니다
- 레거시 유료 플랜을 유지 중인 경우 — **전환 전 사용량 기록 필수**

반대로 월 몇 번 대화형으로 쓰는 정도라면, 솔직히 이번 개편의 체감 차이는 크지 않습니다. 한도가 여러 겹으로 나뉘어도 그 안에서 끝나기 때문입니다.
