> **📌 한줄 요약:** 2026년 11월 23일 10시 33분(한국시간), OpenClaw **안정 채널이 2026.11.7로 올라갔습니다.** 이번 릴리스의 중심은 화려한 신기능이 아니라 **"끊겨도 이어지는 실행"** 입니다. 게이트웨이가 재시작되면 사라지던 답변·하위 에이전트 결과를 되살리고, 자동화 실패를 **복구된 실행 / 의도적으로 건너뛴 실행 / 진짜 실패**로 구분해 줍니다. 동시에 **플러그인 SDK에 브레이킹 체인지 3건**(세션 컨트롤 등록 방식, 게이트웨이 메서드 디스패치, 실행 시작 관찰 시점 API)이 들어갔기 때문에, 커스텀 플러그인이나 스킬을 직접 만들어 쓰는 구성이라면 **업데이트 전에 마이그레이션 확인이 필요한 릴리스**입니다.

## 에이전트 자동화에서 제일 무서운 건 '실패'가 아니라 '모르는 상태'

에이전트에게 정기 작업을 맡겨 두는 구성이라면, 진짜 골치 아픈 순간은 실행이 터졌을 때가 아닙니다. **"이 작업이 돌긴 한 건가?"** 를 알 수 없을 때입니다.

새벽에 돌던 요약 작업이 게이트웨이 재시작과 겹쳤다고 해 봅시다. 로그에는 실패가 없습니다. 그런데 결과물도 없습니다. 이럴 때 사람이 할 수 있는 일은 두 가지뿐입니다. **전부 다시 돌리거나**, 아니면 **그냥 넘기거나**. 앞의 선택은 중복 발송·중복 결제 같은 사고를 만들고, 뒤의 선택은 조용한 누락을 만듭니다.

2026.11.7 릴리스 노트를 읽으면서 가장 눈에 들어온 대목이 바로 여기였습니다. OpenClaw 쪽도 같은 문제를 **"복구된 실행과 진짜 실패를 구분하지 못하는 상태"** 로 정의하고, 이번 버전에서 그 구분을 제품 동작으로 끌어올렸습니다. 업무 자동화에 실질적인 영향이 있는 변화라, 새 기능 목록보다 이 지점부터 정리하는 게 맞겠습니다.

## 핵심 1 — 게이트웨이를 넘어가는 대화 복구

첫 번째 축은 **Conversation recovery** 입니다. 릴리스 노트 표현 그대로 옮기면, 게이트웨이 재시작 전후로 **끊긴 답변(interrupted replies)** 과 **하위 에이전트 결과(child results)** 를 **대기 중인 작업을 잃지 않고** 되살립니다. 관련 PR은 #198905, #201544, #200924, #200967이고 저자는 @steipete입니다.

여기서 중요한 건 "재시도"가 아니라 **"복구"** 라는 점입니다. 재시도는 같은 작업을 처음부터 다시 돌리는 것이고, 복구는 **이미 만들어 둔 중간 산출물을 이어붙이는 것**입니다. 파일 생성·메시지 발송·외부 API 호출처럼 **부작용(side effect)이 있는 단계**가 섞인 작업에서는 이 차이가 결정적입니다. 재시도는 중복 실행을 만들고, 복구는 만들지 않습니다.

실제로 체감되는 시나리오는 이렇습니다.

- 하위 에이전트 여러 개를 병렬로 던져 두고 부모 턴이 길게 돌아가는 구조
- 게이트웨이 프로세스가 크래시하거나 호스트가 재부팅되는 상황
- 긴 리서치 작업 도중 세션이 끊겼다가 다시 붙는 상황

이 세 경우 모두 **"부모는 살아 있는데 자식 결과가 증발"** 하는 형태로 문제가 나타납니다. 11.7은 이 증발 지점을 메우고, 자식 하나의 전달 실패가 **형제 결과까지 같이 날리지 않도록** 고쳤다고 명시합니다(#200873, #201563, #195275).

## 핵심 2 — 자동화 실패를 세 갈래로 나눈다

두 번째 축이 이번 릴리스에서 가장 실무적인 부분입니다. **Reliable automations** 항목은 두 가지를 말합니다.

1. **자동화의 소유자 대화(owner conversation)가 실패를 스스로 수리할 수 있게** 했다.
2. **복구된 실행(recovered run)** 과 **의도적으로 건너뛴 실행(intentionally skipped run)** 을 **진짜 실패(genuine failure)** 와 구분**해서 보여준다.

관련 PR은 #161007, #201638, #152165, #194276, 연관 #194261입니다.

왜 이게 큰 변화인지 짚어 보겠습니다. 자동화를 오래 돌리면 **알림 피로**가 먼저 옵니다. 실패 알림이 하루에 열 번 오는데, 그중 여덟 번이 "실제로는 정상 처리된 것"이라면 사람은 곧 알림을 무시하게 됩니다. 그러다 진짜 실패 한 번을 놓칩니다. 이건 도구의 문제가 아니라 **신호 분류의 문제**입니다.

11.7은 그 분류를 에이전트 쪽에서 해 줍니다. 조건 휴일로 스킵된 실행, 재시작 후 복구된 실행, 실제로 터진 실행이 **같은 빨간색으로 뭉개지지 않는다**는 뜻입니다. 자동화를 여러 개 굴리는 구성일수록 이 차이는 "알림을 켜 둘 수 있느냐"로 직결됩니다.

여기에 **Scheduled work** 수정도 같이 붙습니다. 계정·공유·그룹 변경을 넘어가도 **자동화 소유권을 유지**하고, 예약된 전역 작업이 **원래 대화에 그대로 머무르게** 했습니다(#201008, #201434, #188173). 자동화를 만든 사람이 조직을 옮기거나 공유 설정을 바꿨다고 예약이 엉뚱한 대화로 튀는 일이 줄어든다는 의미입니다.

## 핵심 3 — 업데이트가 중간에 멈춰도 끝까지 간다

세 번째는 **Smoother updates** 입니다. Git 업데이트와 패키지 업데이트가 **스키마 변경, 잠긴 데이터베이스, 남아 있는 복구 상태**를 만나도 **새 릴리스가 시작되기 전이나 후에 멈추지 않고 끝까지 마무리**됩니다(#201600, #201463, #201545, #201330).

OpenClaw는 2026년 내내 업데이트 자체가 골칫거리였습니다. 9월 공식 블로그에도 "깨지지 않는 업데이트"를 주제로 한 인터뷰가 올라와 있을 정도입니다. 11.7의 이 항목은 그 연장선이고, 특히 **PostgreSQL 포트를 쓰는 구성**에서 "네트워크 DB 포트 설정이 끝나지 않아 몇 시간을 기다리는" 문제(#201374)와 **예약 백업이 10분을 넘기면 실패하던 제한**(#191346)을 함께 건드렸습니다. 백업을 10분 넘게 돌리는 구성이라면 이번에 조건이 풀립니다.

업데이트 계열에서 하나 더. **부분적으로 쓰인 템플릿 생성**을 재시도할 수 있게 했고(#199447), **심볼릭 링크로 연결한 상태 루트**에서도 설정 보호 쓰기가 유지되며(#155538), **잘린 설정 파일을 복원**하도록 Doctor가 동작합니다(#201501, #190194). 설정을 Git으로 관리하거나 상태 디렉터리를 외부 볼륨에 두는 구성에서 체감이 큽니다.

## 핵심 4 — 느린 파일 시스템에서도 게이트웨이가 살아 있게

네 번째는 **Responsive Gateway** 입니다. 느린 파일 시스템 작업, 큰 복구 팩, 페이지 추출 같은 무거운 작업이 도는 동안에도 **채팅·준비 상태 확인(readiness)·무관한 세션이 응답성을 유지**합니다(#191236, #201248, #200623, #200925).

이건 "느리다"가 아니라 **"멈춘다"** 는 불만에서 나온 수정으로 보입니다. 에이전트가 큰 저장소를 훑거나 브라우저 페이지를 뽑아내는 동안 채팅 응답이 통째로 멈추면, 사용자 입장에서는 죽은 것과 구분이 안 됩니다. 무거운 작업을 **다른 세션과 분리**하는 방향으로 정리된 것으로 읽힙니다.

## 핵심 5 — 브라우저 단축코드 페어링, 그리고 릴리스 없이 붙는 모델 카탈로그

다섯 번째는 **Browser pairing** 입니다. 게이트웨이 호스트에서 **짧은 코드를 승인**하는 방식으로 다른 브라우저를 페어링하고, 승인 대기 중에도 안내 문구를 명확히 보여줍니다(#191513, #200905). 브라우저 패널에서 **에이전트를 멈추지 않고 직접 조작을 넘겨받는** 흐름은 2026.11.10 베타 계열에서 이미 예고됐는데, 안정 채널에는 이번에 짧은 코드 방식이 들어왔습니다.

여섯 번째는 **Current ChatGPT catalogs** 입니다. **새로 풀린 구독 모델을 OpenClaw 릴리스 없이 발견**하고, **로그인 기반 모델 탐색을 npm과 분리**했습니다(#201130, #201493, 연관 #201480). 11월 6일 공식 블로그에서 예고한 "호스팅 카탈로그 + 설치된 Codex에서 모델 목록을 읽는" 구조가 안정판 기본 동작으로 자리 잡는 중이라는 뜻입니다. 새 모델이 나올 때마다 에이전트를 업데이트해야 했던 번거로움이 줄어듭니다.

## 브레이킹 체인지 3건 — 플러그인을 직접 만든다면 여기부터

이번 릴리스에서 놓치면 안 되는 부분입니다. 세 항목 모두 PR #175837 한 묶음으로 들어왔고, **기존 플러그인 코드가 컴파일은 되는데 동작이 달라지는 종류**입니다.

| 구분 | 바뀐 내용 | 대응 |
|:--|:--|:--|
| 세션 컨트롤 | 세션 키 기반 `setActiveEmbeddedRun(...)` 등록을 **호스트가 주는 `runAttempt` 콜백 안으로 이동**. 정리(cleanup) 함수를 그대로 유지해야 함. 승인되지 않은 등록은 `SESSION_CONTROLLER_ADMISSION_REQUIRED`로 거부 | 플러그인 초기화 시점에 하던 등록을 실행 단위 콜백으로 옮기기 |
| 게이트웨이 메서드 | 변경 가능한 `chatAbortControllers`·`chatQueuedTurns` 직접 접근을 **`openclaw/plugin-sdk/gateway-method-runtime`의 `dispatchGatewayMethod`** 로 교체. 플러그인 매니페스트에 `contracts.gatewayMethodDispatch: ["authenticated-request"]` 선언 필요 | 매니페스트에 계약 선언 추가, 기존 호출자 권한은 그대로 적용됨 |
| 실행 시작 관찰 | `AgentTurnStartOwner.observe()` 소비자가 `expiresAtMs` → **`startDeadlineAtMs`** 로 변경. 이는 **실행 시작 데드라인**이며 실행 타임아웃이 아니고, **호환 별칭이 없음** | `docs/plugins/sdk-migration.md` 기준으로 필드명 교체 |

세 번째 항목이 특히 위험합니다. **호환 별칭이 없다**고 명시했기 때문에, `expiresAtMs`를 읽던 코드는 업데이트하는 순간 **조용히 `undefined`를 받습니다.** 타임아웃 계산에 이 값을 쓰고 있었다면 만료 판정이 항상 실패하거나 항상 통과하는 식으로 뒤집힐 수 있습니다. 플러그인을 직접 관리한다면 이번 주에 코드 검색부터 하는 게 좋습니다.

```bash
# 플러그인 저장소에서 영향 범위 확인
grep -rn "setActiveEmbeddedRun\|chatAbortControllers\|chatQueuedTurns\|expiresAtMs" .
```

이런 브레이킹 체인지가 **안정판 패치 번호(11.6 → 11.7)** 에 실려 나온 점은 솔직히 부담스럽습니다. 시맨틱 버저닝 기준으로 보면 마이너에 가까운 변화인데, 버전 표기는 날짜 기반이라 그 경계가 드러나지 않습니다. **자동 업데이트를 켜 둔 구성**이라면 플러그인 코드와 업데이트 주기를 분리해서 관리하는 편이 안전합니다.

## 실제로 체감이 갈리는 수정들

## 장점과 단점, 솔직히

**장점**

1. **재시작 내성이 실제로 올라갔습니다.** 대화 복구와 자동화 소유권 유지가 같이 들어와서, "게이트웨이 한 번 재시작 = 작업 한 번 날아감" 공식이 깨졌습니다.
2. **실패 신호가 정직해졌습니다.** 복구된 실행과 진짜 실패를 구분하는 것만으로 알림을 다시 켤 수 있게 됩니다.
3. **업데이트가 끝까지 갑니다.** 스키마 변경·잠긴 DB·심볼릭 링크 상태 루트까지 고려한 건 "업데이트가 곧 장애"였던 흐름을 끊는 변화입니다.
4. **모델 대응이 릴리스에서 분리됐습니다.** 새 모델이 나와도 에이전트 업데이트를 기다리지 않아도 됩니다.

**단점**

1. **브레이킹 체인지가 패치 번호에 실렸습니다.** 플러그인을 직접 쓰는 구성에서는 이번 업데이트가 "조용한 패치"가 아닙니다.
2. **변경 범위가 넓습니다.** 390개 PR, 30줄 넘는 수정 목록은 그 자체로 회귀 리스크입니다. 2026.10월에도 워크스페이스 관련 데이터 손실 이슈가 있었던 전례가 있어, **운영 환경은 스테이징에서 하루 정도 관찰**한 뒤 올리는 편이 낫습니다.
3. **베타와 안정판이 뒤섞여 보입니다.** 같은 날 `2026.11.10-beta.2`도 나왔고, 브라우저 핸드오프처럼 베타에 먼저 들어간 기능이 안정판에는 부분만 들어옵니다. 릴리스 노트를 버전별로 대조하지 않으면 "이게 되는데?" 싶은 기능이 실제로는 안 될 수 있습니다.
4. **LTS 라인은 여전히 2026.10.33입니다.** 확장 안정판을 쓰는 구성은 이번 변화를 바로 받지 않습니다. 보안 수정만 챙기고 기능은 미루는 선택지가 남아 있다는 뜻이고, 동시에 **두 라인의 동작 차이**를 계속 의식해야 한다는 뜻이기도 합니다.

## 업데이트 전에 확인할 순서

1. **버전 확인** — `openclaw --version`으로 현재 라인 확인. 확장 안정판(2026.10.x)인지 정식 라인(2026.11.x)인지에 따라 판단이 달라집니다.
2. **플러그인 코드 스캔** — 위 grep으로 `setActiveEmbeddedRun`, `chatAbortControllers`, `chatQueuedTurns`, `expiresAtMs` 사용 여부 확인.
3. **매니페스트 계약 추가** — `contracts.gatewayMethodDispatch: ["authenticated-request"]` 선언.
4. **마이그레이션 문서 대조** — `docs/plugins/sdk-migration.md`를 버전 태그 기준으로 확인.
5. **백업 조건 재확인** — 10분 넘는 예약 백업을 쓰고 있었다면 이제 조건이 풀렸는지 확인.
6. **스테이징 하루 관찰** — 자동화 로그에서 "복구됨 / 스킵됨 / 실패"가 실제로 구분돼 찍히는지 보는 것이 이번 버전의 핵심 검증 포인트입니다.

업데이트 자체는 npm 기준 `openclaw@2026.11.7`로 배포됐고, 릴리스 검증 기록과 SHA(`e31bbf0`)가 공개돼 있습니다. 릴리스 노트 전문은 `docs.openclaw.ai/releases/2026.11.7`에서 확인할 수 있습니다.

## 정리 — 이런 구성이라면 이번 버전은 그냥 지나치면 안 됩니다

자동화를 여러 개 굴리면서 **실패 알림을 사실상 꺼 둔 상태**라면, 2026.11.7은 그 알림을 다시 켤 수 있게 해 주는 릴리스입니다. 반대로 **플러그인을 직접 만들어 쓰는 구성**이라면, 이번 버전은 신기능보다 **마이그레이션 작업**으로 기억하게 될 가능성이 큽니다. 둘 다 해당된다면 업데이트보다 코드 정리를 먼저 하는 편이 순서상 맞습니다.

새 기능이 화려하지 않다고 넘기기엔, 이번 릴리스가 건드린 지점이 **"에이전트를 믿고 맡길 수 있느냐"** 의 기반이라는 게 솔직한 감상입니다. 화려한 데모보다 재시작 한 번을 견디는 실행이 업무 자동화에서는 훨씬 값어치가 큽니다. 안정적인 자동화 파이프라인을 찾는 분께는, 지금 라인에서 가장 균형 잡힌 선택지로 보입니다.
