*Anthropic 공식 Claude Code 제품 페이지 대표 이미지. 2026년 11월, 이 도구의 '다시 묻지 않기' 승인이 개발자 비밀번호를 공개 저장소로 흘려보내는 통로였다는 연구 결과가 나왔습니다 (이미지 출처: Anthropic 공식 사이트 anthropic.com/claude-code)*

> **📌 한줄 요약:** Claude Code가 셸 명령을 승인할 때 뜨는 **"Yes, and don't ask again"** 버튼을 누르면, 승인한 명령줄이 **글자 그대로** `.claude/settings.local.json`에 저장됩니다. 문제는 그 명령줄 안에 `PGPASSWORD=...`나 `Authorization: Bearer ...`가 섞여 있을 수 있다는 것. 보안업체 **Apiiro**가 2026년 11월 1~3일 GitHub 공개 저장소를 훑어보니, 이 파일 **104,185개** 가운데 **1,122개**에 진짜 비밀번호·토큰이 평문으로 들어 있었습니다. Anthropic은 11월 7일 "무엇을 할 수 있을지 살펴보는 중"이라고 답했고, **수정 일정은 아직 없습니다.**

솔직히 이 사안은 "AI가 실수했다"기보다 **승인 UX 설계의 부작용**에 가깝습니다. 편하려고 만든 버튼 하나가, 편의를 위해 명령줄을 복사해 두는 방식과 만나면서 조용히 자격증명 저장소가 되어버린 구조니까요. AI 에이전트에게 셸 실행을 맡기는 분들이라면 한 번은 짚고 넘어가야 할 이야기입니다.

이 글은 **① 무슨 일이 있었나 → ② 왜 비밀번호가 설정 파일에 들어가나 → ③ 숫자로 보는 규모 → ④ 방어막이 뚫린 네 가지 경로 → ⑤ Anthropic의 반응 → ⑥ 사용자·개발자 영향 → ⑦ 5분 점검 체크리스트 → ⑧ 전망** 순서로 정리합니다.

## 1. 무슨 일이 있었나 — 11월 1~3일 전수조사, 11월 7일 공개

2026년 11월 7일, 코드 보안 업체 **Apiiro**가 GitHub 공개 저장소를 조사한 결과를 공개했습니다. 조사 기간은 **11월 1일부터 3일까지** 사흘. 대상은 Claude Code가 프로젝트 폴더에 만드는 로컬 설정 파일, **`.claude/settings.local.json`** 입니다.

결과는 이렇게 나왔습니다.

- GitHub에서 발견된 공개 사본: **104,185개** (리포지토리 103,617곳)
- 그중 실제로 쓸 수 있는 비밀번호·토큰·키가 든 파일: **1,122개 (1.1%)**
- 이 파일들에 담긴 서로 다른 비밀값: **1,379개**
- Claude Code 말고 다른 에이전트 설정 파일까지 합치면: **2,539개 비밀값 / 1,994개 리포지토리**
- 영향을 받은 조직: **63곳** (이 중 한 곳은 키가 아직 살아 있음을 확인)

공개 직후 Hacker News 프런트 페이지에 올라 **600점, 댓글 400개 이상**이 붙었습니다. 개발자 커뮤니티 반응이 뜨거웠던 이유는 숫자보다 **메커니즘**입니다. "내가 아무 생각 없이 누르던 그 버튼"이 원인이었다는 점이었으니까요.

## 2. 왜 비밀번호가 '설정 파일'에 들어가나

Claude Code는 셸 명령을 실행하기 전에 사용자에게 허락을 묻습니다. 이때 세 가지 선택지가 뜹니다. 거절, 한 번만 허용, 그리고 **"네, 그리고 다시 묻지 마세요(Yes, and don't ask again)"**.

세 번째를 고르면 Claude Code는 그 명령을 **allow 규칙**으로 저장합니다. 그런데 저장되는 단위가 "허용한 동작"이 아니라 **명령줄 문자열 전체**입니다. Apiiro가 든 예시는 이렇습니다.

```bash
PGPASSWORD=s3cr3t psql -h db.example.com -U app -c "select count(*) from users"
```

이 명령을 "다시 묻지 않기"로 승인하는 순간, `s3cr3t`라는 비밀번호가 JSON 파일 안에 **평문**으로 남습니다. 같은 방식으로 `curl`의 `Authorization: Bearer ...` 헤더, `mysql -p...`, `sshpass -p ...` 안의 패스워드도 그대로 따라 들어갑니다.

Apiiro는 이 동작을 **Claude Opus 5.5와 Fable 5.1**에서 재현했다고 밝혔습니다. 그리고 강조한 부분이 중요합니다. **이건 모델의 문제가 아니라 CLI 프로그램의 동작**이라는 점입니다. 모델이 아무리 조심해도, 승인 규칙을 저장하는 코드가 명령줄을 통째로 복사하면 같은 일이 벌어집니다.

파일 크기와 유출 확률도 의미심장합니다. **8KB가 넘는 설정 파일 열 개 중 하나**에는 비밀이 있었고, **500바이트 미만 파일에서는 500개 중 1개꼴**이었습니다. 다시 말해 **오래 쓰고 명령을 많이 승인한 프로젝트일수록 위험**합니다. 조사 대상 파일의 중앙값은 **217일 전**에 처음 커밋됐고, **118개 리포지토리**는 1년이 넘은 파일을 그대로 갖고 있었습니다.

## 3. 어떤 비밀이 새어 나갔나

Apiiro가 분류한 1,379개를 보면 "설마 했는데 진짜 위험한 것"이 섞여 있습니다.

| 유형 | 규모 | 의미 |
|---|---|---|
| 알려진 서비스 API 키 | 636개 | OpenAI·클라우드·결제 등 키 포맷이 뚜렷한 것들 |
| 비밀번호·토큰 | 743개 | 명령줄에 박힌 DB 비밀번호, Bearer 토큰 등 |
| 데이터베이스 비밀번호 | 379개 | 운영 DB 직접 접근 가능 |
| Supabase 서비스 키 | 122개 | 권한 관리 키. 노출 시 데이터 접근 범위가 큼 |
| SSH 접속 정보 | 43건 | 일부는 `sshpass` 명령 안에 **root 비밀번호** |

개별 사례도 구체적입니다. **관리 권한이 있고 만료 기한도 없는 클라우드 DB 업체 키**, **Azure에서 돌던 운영 Postgres 비밀번호**, **운영 환경 Square 토큰**, **의료 기록 DB 소유자 비밀번호** 등이 포함됐습니다. 스타 1,000개가 넘는 공개 프로젝트에 OpenAI 형식 키가 들어 있던 사례도 있습니다. 포크도 문제입니다. **74개 리포지토리의 포크 211개**가 같은 비밀값을 그대로 복제하고 있었습니다.

## 4. 방어막은 있었는데, 왜 뚫렸나

Anthropic 문서에는 이런 문장이 있습니다. *"Claude Code는 `.claude/settings.local.json`을 만들 때 git이 이 파일을 무시하도록 설정한다."* 실제로 보호 장치는 있습니다. 다만 **적용 범위가 "이 컴퓨터"** 입니다.

Claude Code는 이 파일을 처음 만들 때 **전역 git 제외 목록**(`core.excludesFile` 또는 `~/.config/git/ignore`)에 패턴을 추가합니다. **리포지토리의 `.gitignore`에는 넣지 않습니다.** 그래서 다음 네 가지 경우에 그물이 벌어집니다.

1. **다른 컴퓨터에서 클론했을 때** — 전역 제외 설정은 따라오지 않으니 `git add .` 한 번에 딸려 올라갑니다.
2. **폴더가 나중에 저장소가 됐을 때** — 파일이 먼저 있었으면 `git init` 시점에 제외 규칙이 등록되지 않습니다.
3. **파일을 직접 만들거나 직접 커밋했을 때** — 문서도 이 경우엔 `.gitignore`에 손으로 넣으라고 안내합니다.
4. **에이전트가 커밋했을 때** — Apiiro는 비밀이 든 추적 리포지토리 1,105개 중 **539개(48.8%)** 에서 이 파일을 **Claude가 공동 작성자로 들어간 커밋**이 건드렸다고 지적했습니다.

4번은 해석이 갈립니다. Apiiro는 "에이전트가 파일을 커밋했다"고 보고, Claude Code를 이끄는 **보리스 체르니(Boris Cherny)** 는 Hacker News에서 "프로그램이 생성 시 자동으로 제외하므로, 발견된 사본은 사람이 만들고 커밋한 것"이라고 반박했습니다. 두 주장은 동시에 성립할 수 있습니다. **제외 설정은 파일이 태어난 그 컴퓨터에만 존재하고, 커밋은 다른 곳에서 이뤄질 수 있으니까요.**

## 5. Anthropic은 뭐라고 했나

11월 7일 기준 Anthropic의 공식 답변은 **"살펴보는 중"** 입니다. 패치도, CVE도, 권고문도 아직 없습니다. 체르니가 Hacker News에 남긴 내용을 정리하면 세 가지입니다.

- Claude Code는 **지금까지 명령줄에서 비밀값을 걸러내지 않았다.** 팀은 "무엇을 할 수 있을지 검토 중"이며, **기본 시크릿 스캔**이 프로토타이핑 후보 중 하나다.
- 수동 allow/deny 목록은 **구식 접근**이라고 봤습니다. 대신 분류기가 승인을 대신 판단하는 **auto mode**를 대안으로 제시했습니다.
- 어떤 에이전트를 쓰든 **시크릿 스캐닝은 켜 두는 게 좋다.**

아쉬운 부분은 따로 있습니다. Apiiro에 따르면 이 메커니즘은 **2025년 8월부터** Claude Code 이슈 트래커에 여러 번 보고됐고, 그중 **세 건은 자동으로 닫혔습니다.** 사용자 입장에서는 "알려졌는데 반영되지 않은" 유형의 문제였던 셈입니다.

## 6. 사용자·개발자에게 실제로 무엇이 달라지나

**개인 개발자에게** 가장 큰 위험은 API 키 과금입니다. 클라우드 키나 모델 API 키가 공개 저장소에 있으면 스캐너 봇이 몇 분 안에 긁어갑니다. 이번 조사에서도 스타 1,000개 프로젝트의 키 같은 사례가 나왔습니다. 반면 **기본 시크릿 스캐너로는 절반 정도만 잡힙니다.**

| 도구 | 1,122개 중 탐지 | 비율 |
|---|---|---|
| gitleaks | 564개 | 50.3% |
| TruffleHog | 643개 | 57.3% |
| 둘 다 놓침 | 215개 | 19.2% |

이유는 단순합니다. 스캐너는 **키의 '생김새'** 를 봅니다. 그런데 `PGPASSWORD=` 뒤에 붙은 문자열은 그냥 평범한 단어처럼 보입니다. 정규식으로는 키가 아니라 **명령줄의 일부**일 뿐이죠. "시크릿 스캐닝을 켜 두면 안전하다"는 말이 이번 사안에서는 **절반의 진실**인 이유입니다.

**팀 단위로 에이전트를 운영하는 조직**은 위험이 더 큽니다. 63개 조직이 영향을 받았고, 그중 하나는 키가 여전히 유효했습니다. 저장소가 포크되면 삭제해도 사본은 남습니다. 키를 지우는 것으로 끝나지 않고 **회전(rotation)** 이 필요한 이유입니다.

**자동화 파이프라인을 운영하는 입장**에서도 이번 건은 남는 교훈이 있습니다. 에이전트에게 셸을 맡기면 편의 승인을 누르게 되고, 그 승인이 곧 **권한의 기록**으로 남습니다. 파이프라인 설계 단계에서 "승인 로그에 비밀이 남지 않는가"를 먼저 따져야 한다는 뜻입니다.

## 7. 지금 5분 안에 확인하는 방법

복잡하지 않습니다. 터미널에서 세 줄이면 끝납니다.

```bash
# 1) 내 저장소에 이 파일이 추적되고 있나?
git ls-files | grep "claude/settings.local.json"

# 2) 과거 커밋에 남은 적 있나?
git log --all --oneline -- .claude/settings.local.json

# 3) .gitignore에 규칙이 있나?
grep -n "settings.local.json" .gitignore
```

**1번에서 뭔가 나오면** 추적을 해제하고 규칙을 추가합니다.

```bash
git rm --cached .claude/settings.local.json
printf "\n.claude/settings.local.json\n" >> .gitignore
git commit -m "chore: stop tracking claude local settings"
```

**2번에서 기록이 나오면** 그 키는 이미 공개된 것으로 봐야 합니다. 파일만 지우는 걸로는 부족하고 **해당 비밀번호·토큰을 전부 교체**해야 합니다. 포크가 있다면 포크에도 같은 값이 남아 있습니다.

추가로 챙길 것들:

- GitHub **Secret scanning / push protection**을 켜 둡니다. (무료 공개 저장소에서도 동작합니다)
- 에이전트에게 `PGPASSWORD=...`, `mysql -p...`, `sshpass` 같은 **명령줄 직접 입력을 시키지 않습니다.** `.pgpass`, `~/.my.cnf`, SSH 키, 환경변수 파일처럼 **파일 권한으로 관리되는 경로**를 쓰게 하는 편이 안전합니다.
- 승인 다이얼로그에서 "다시 묻지 않기"를 누르기 전에 **명령줄에 비밀이 보이는지** 한 번만 확인합니다.
- 저장소를 넘길 때는 `.gitignore`를 **저장소 안에** 두는 습관이 여전히 유효합니다. 전역 설정은 내 컴퓨터만 지켜줍니다.

## 8. 전망 — '편의 승인'의 회계학

이번 사안의 핵심은 취약점 하나가 아닙니다. **에이전트 시대의 승인 UX가 아직 미완성**이라는 신호입니다. 사람이 모든 명령을 읽고 승인하는 방식은 오래 못 갑니다. 그래서 자동화 모드로 이동하는데, 자동화 모드는 **비밀이 어디로 흘러가는지에 대한 별도의 설계**를 요구합니다.

Anthropic이 기본 시크릿 스캔을 실제로 넣으면 재발은 상당 부분 줄어들 겁니다. 다만 이미 공개된 1,122개 파일과 그 포크들은 패치로 되돌아오지 않습니다. 결국 남는 건 **키 회전**과 **저장소 위생**입니다.

정리하면 이렇습니다. 도구가 알아서 걸러줄 거라고 가정하지 말고, **에이전트가 남기는 파일이 곧 로그이자 권한 기록**이라는 전제로 저장소를 관리하는 편이 안전합니다. Claude Code를 업무에 붙여 쓰는 분들이라면, 이번 주에 저장소 한 번 훑어보시길 권합니다. 5분이면 끝나는 일이고, 그 5분이 다음 달 청구서를 지켜줄 수도 있습니다.
