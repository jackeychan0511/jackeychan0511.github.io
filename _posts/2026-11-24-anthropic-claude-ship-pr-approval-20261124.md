코드를 쓰는 속도는 이미 사람 손을 떠났습니다. 문제는 그다음 단계입니다. PR을 열고 나면 리뷰가 돌아올 때까지 기다리고, 지적을 반영하고, 다시 리뷰를 돌리고, 마지막으로 누군가에게 "승인해 주세요"를 부탁해야 합니다. 에이전트가 코드를 뽑아내는 속도가 빨라질수록 이 마지막 줄이 병목이 됩니다.

2026년 11월 23일, 앤트로픽이 그 마지막 줄을 건드렸습니다. **Claude Ship** 베타를 공개했습니다. 풀 리퀘스트를 리뷰하고, 고치고, **팀이 정한 정책에 따라 승인까지 하는** 에이전트 묶음입니다. 로이터와 테크크런치가 같은 날 보도했고, 앤트로픽은 "코드를 쓰는 속도만큼 빠르게 배포하자"는 문장으로 발표문을 열었습니다.

한 줄로 줄이면 이렇습니다. "AI가 코드를 쓰는 건 이제 익숙하다. 그럼 **AI가 코드를 승인하게** 하자." 개발 워크플로에서 사람이 마지막으로 붙잡고 있던 지점을 정면으로 겨냥한 제품입니다.

## 세 개의 에이전트 — 리뷰, 수정, 그리고 승인

Claude Ship은 하나의 도구가 아니라 역할이 나뉜 에이전트 묶음입니다. 이 분리가 이번 발표의 핵심 설계입니다.

**① Code Review — 이미 정식 출시된 리뷰 담당**

PR을 코드베이스 맥락과 함께 여러 관점에서 훑습니다. 발견한 사항을 모으고, **스스로 반박 검증(adversarial verification)** 을 거친 뒤, 분류해서 PR에 코멘트로 남깁니다. 저장소마다 리뷰 깊이를 **Quick / Standard / Deep** 세 단계 중에 고를 수 있습니다. "지적을 쏟아내는 봇"이 아니라, 걸러낸 뒤 올리는 구조를 강조한 셈입니다.

**② PR Steward — 고치는 담당, 승인은 하지 않음**

실패한 CI 체크, 머지 충돌, Code Review나 동료가 남긴 피드백을 받아 실제로 코드를 고칩니다. 여기서 중요한 제약이 있습니다. **PR Steward는 승인도, 머지도 하지 않습니다.** 푸시할 때마다 "무엇을 바꿨고, 어떻게 되돌리는지"를 코멘트로 남깁니다. 개발자는 `@claude` 멘션으로 방향을 지시하거나, `@claude stop`으로 작업을 멈추게 할 수 있습니다.

![PR Steward가 PR에서 실패한 체크와 리뷰 피드백을 반영하는 화면 예시 — 이미지: Anthropic 공식 블로그](https://pub-a8e00ddf355f47339bd2e01ff3221de7.r2.dev/assets/images/posts/claude-ship-20261124/02-pr-steward.jpg)

**③ Claude Approvals — 승인 판단 담당**

여기가 논쟁의 중심입니다. 팀이 **저장소에 파일 하나로 승인 정책을 써 두면**, Claude가 그 정책에 따라 PR을 승인합니다. 앤트로픽의 표현을 빌리면 "**더 똑똑한 CODEOWNERS 파일**"입니다. 정책에는 경로별로 몇 명의 승인이 필요한지, 어떤 조건에서 Claude가 승인해도 되는지를 적습니다. Code Review 결과나 팀이 직접 만든 **자연어 분류기(classifier)** 를 판단 신호로 쓸 수도 있습니다.

![저장소에 두는 승인 정책 파일 예시. 경로별 승인 인원과 Claude가 승인 가능한 범위를 적습니다 — 이미지: Anthropic 공식 블로그](https://pub-a8e00ddf355f47339bd2e01ff3221de7.r2.dev/assets/images/posts/claude-ship-20261124/03-approval-policy.png)

앤트로픽이 권하는 도입 순서도 눈에 띕니다. **처음에는 관찰 모드(observe-only)** 로 켜서 판단이 어떻게 나오는지 지켜본 다음, 신뢰가 쌓이면 브랜치 보호 규칙에 Claude Approvals의 통과를 필수 조건으로 걸라는 것입니다. 기존 브랜치 보호와 필수 체크 설정을 그대로 쓰기 때문에, "AI가 규칙을 우회한다"기보다 "AI가 그 규칙 안에서 판단 한 표를 행사한다"에 가까운 구조입니다.

## 왜 지금인가 — 리뷰가 새로운 병목이 됐다

앤트로픽이 공개한 내부 수치가 이 제품의 존재 이유를 설명합니다.

| 지표 | 변화 (2026년 6월 → 9월) |
|:----|:----|
| Claude Code 팀의 병합된 PR | **2배 이상** |
| 되돌린(revert) 변경 비율 | **40% 이상 감소** |

이 숫자는 Claude Ship 전체를 쓴 결과가 아니라, **Code Review를 전체 프로세스의 한 층으로 둔 상태**에서 나온 것입니다. 앤트로픽은 Claude Code 팀에서 "Claude가 우리 코드의 대부분을 쓴다"고 밝혔습니다. 사람이 모든 줄을 쓰던 시절의 리뷰 관행으로는 감당이 안 되는 볼륨이라는 뜻입니다.

재밌는 건 발표문에 소개된 실제 사례입니다. 고객이 "Analytics API 문서가 Admin 키로 Pro·Team 사용량을 조회할 수 있는 것처럼 읽힌다"고 피드백을 남겼고, 제품 매니저가 Claude에게 물어 PR을 열게 했습니다. Code Review가 막는 사항이 없다고 판단했고, 문서 리뷰어가 승인했고, Claude Approvals가 정책상 통과시키면서 **그날 저녁에 머지**됐습니다. 사람이 코드를 쓴 게 아니라, 사람이 **판단만** 한 케이스입니다.

## 비용 구조 — '무료 기능'이 아닙니다

도입을 검토한다면 여기부터 봐야 합니다. Claude Ship은 **토큰 과금**입니다. 좌석 요금에 포함된 사용량과 별도로 조직의 사용량 크레딧에서 차감됩니다.

- **Code Review·PR Steward**: 관리자가 저장소별 **월 지출 한도**를 설정할 수 있습니다.
- **Claude Approvals**: 기본 요금은 없습니다. 다만 정책에 넣은 분류기가 쓰는 토큰은 과금되고, **정책이 Claude의 리뷰를 트리거하면 관찰 모드에서도 Code Review 요금이 발생**합니다.
- **`/ship` 명령**: 일반 Claude Code 사용량으로 계산됩니다.
- **Enterprise 크레딧**: 대상 조직은 **최소 1만 달러**의 Claude Ship 크레딧을 청구할 수 있습니다. 2027년 1월 15일까지 신청, 청구 후 30일 내 사용 조건입니다.

또 하나, **Zero Data Retention(ZDR), HIPAA 구성, 고객 관리 암호화 키(CMEK)** 를 쓰는 조직에는 제공되지 않습니다. 규제 산업에서 "데이터를 남기지 않는" 구성을 선택한 팀은 이번 베타 대상이 아니라는 뜻입니다.

## 영향 — 누가 무엇을 얻고, 무엇을 잃나

**개발자 개인**: Claude Code에서 `/ship`을 치면 푸시부터 PR 생성, 리뷰, 피드백 반영까지 이어집니다. 다만 Claude Ship 자체는 Team·Enterprise 조직 대상이라, Pro·Max 개인 구독자는 이 승인 자동화의 직접 수혜자가 아닙니다. 개인 사용자에게는 "리뷰 대기 시간"보다 "내 PR이 어디서 막히는지"를 빨리 아는 쪽이 실익입니다.

**팀·조직**: 병목이 '작성'에서 '승인'으로 옮겨간 팀에 실질적 효과가 있습니다. 특히 문서·설정·의존성 범프처럼 위험도가 낮고 빈도가 높은 변경이 많은 저장소라면, 정책 파일로 그 구간만 자동 통과시키고 사람은 결제 로직·인증·마이그레이션에 집중하는 그림이 가능합니다. 앤트로픽 고객사 엔지니어링 디렉터의 코멘트도 같은 맥락입니다. "Claude Code Review가 사람 리뷰어보다 먼저 실제 이슈를 잡아낸 사례가 여러 번 있었고, PR Steward가 기여자를 도와 고쳤다. **사람은 루프 안에 두되, 사람의 시간은 필요한 변경에 쓰게 됐다.**"

**보안·컴플라이언스 담당**: 가장 예민한 지점입니다. 지금까지 "AI가 쓴 코드"의 책임은 리뷰한 사람에게 있었습니다. Claude가 승인 표를 행사하면, 감사(audit) 관점에서 **누가 승인했는가**의 기록이 달라집니다. 앤트로픽은 관찰 모드 → 정책 신뢰 → 브랜치 보호 연동 순서를 권하지만, 조직 입장에서는 정책 파일 자체가 새로운 **공격 표면**이 됩니다. 정책 파일을 바꾸는 PR이 자동 승인되면 승인 체계 전체가 무력화될 수 있으니, 정책 파일 경로는 반드시 사람 승인 필수로 걸어두는 것이 기본입니다.

## 한계와 반론 — 앤트로픽도 '놓칠 수 있다'고 적었습니다

공식 제품 이미지에 들어간 고지 문구가 솔직합니다. "Claude Ship은 AI를 사용하며, **버그·보안 취약점·기타 문제를 놓칠 수 있습니다.**" 리뷰 자동화 도구가 자기 한계를 제품 첫 화면에 적어 둔 셈입니다.

정리하면 리스크는 세 갈래입니다.

1. **거짓 통과(false approve)**: 리뷰가 놓친 문제를 승인까지 통과시키면, 기존에는 사람 리뷰어가 걸렀을 문제가 그대로 머지됩니다. 리뷰와 승인이 같은 모델 계열이면 **같은 사각지대를 공유**합니다.
2. **리뷰 역량의 외주화**: 사람이 리뷰에서 손을 떼는 시간이 길어질수록, 코드베이스에 대한 팀의 이해도는 낮아집니다. 장애가 났을 때 읽을 줄 아는 사람이 줄어드는 비용은 지표에 안 잡힙니다.
3. **비용의 비선형 증가**: PR 수가 늘고 리뷰 깊이를 Deep으로 올리면 토큰 비용이 같이 뜁니다. 지출 한도를 걸어두지 않으면 "리뷰도 결제 대상"이라는 사실을 청구서로 배웁니다.

## 전망 — 확인할 네 가지

1. **GitHub 밖으로 나가는가**: 현재는 GitHub 저장소만 지원합니다. GitLab·Bitbucket 지원 여부가 엔터프라이즈 확산의 1차 관문입니다.
2. **과금이 정액제로 바뀌는가**: 지금은 순수 토큰 과금입니다. "리뷰 1건당 얼마" 같은 정액 옵션이 나오면 예산 계획이 훨씬 쉬워지고, 리뷰 전문 SaaS와의 가격 경쟁도 본격화됩니다.
3. **AI 승인이 감사 증적으로 인정되는가**: SOC 2·ISO 심사에서 "AI 에이전트의 승인 기록"을 어떻게 다룰지가 정해지면, 자동 승인 범위가 산업별로 갈립니다.
4. **경쟁 구도의 이동**: 지금까지 코드 리뷰 AI들은 '지적'까지만 했습니다. 승인 결정까지 넘보는 순간, 경쟁 상대는 리뷰 봇이 아니라 **코드 소유권·거버넌스 제품**이 됩니다.

## 정리 — 도입 전에 점검할 것

솔직히, 이번 발표의 핵심은 기능 목록이 아니라 **책임의 위치**입니다. "리뷰는 AI가 하고 승인은 사람이 한다"는 경계가, "일상적 변경은 AI가 승인하고 사람은 예외만 본다"로 한 칸 이동했습니다. 이 이동이 맞는지는 팀마다 다릅니다.

도입을 검토하는 팀이라면 순서를 이렇게 잡는 편이 안전합니다.

- **한 저장소, 관찰 모드로 시작**: 판단 로그를 2~4주 모은 뒤 정책을 다듬습니다. 처음부터 브랜치 보호에 걸지 않습니다.
- **정책 파일은 사람 승인 필수 경로로**: 승인 규칙을 바꾸는 변경이 자동 승인되면 나머지 규칙은 의미가 없습니다.
- **자동 승인 대상은 화이트리스트로**: 문서, 테스트, 의존성 범프처럼 되돌리기 쉬운 변경부터. 결제·인증·데이터 마이그레이션은 명시적으로 제외합니다.
- **지출 한도와 리뷰 깊이를 먼저 정하고 켜기**: 켠 다음 조정하면 첫 달 청구서가 교재가 됩니다.
- **지표는 '머지 수'가 아니라 '롤백률'과 '리드타임'**: 앤트로픽이 내세운 숫자도 결국 되돌린 비율의 감소입니다. 속도만 보면 리뷰 자동화의 실패를 놓칩니다.

AI 에이전트를 실사용하는 팀이 늘수록, 자동화의 마지막 칸은 언젠가 '배포 버튼'까지 내려옵니다. Claude Ship은 그 방향의 첫 상용 제품입니다. 지금 필요한 건 성능표가 아니라 **어디까지 기계에 맡길지 정하는 규칙**입니다.
