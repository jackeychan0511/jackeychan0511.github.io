> **📌 한줄 요약:** 요즘 오픈소스 AI 에이전트를 업무 파이프라인에 붙여 쓰는 분들이라면, 이번 소식은 그냥 넘기기 어렵습니다. **2026년 10월 11일**, OpenClaw가 **10월 첫 정식판인 `2026.10.1`을 배포**했습니다. 10월 5일 베타(.1-beta.1)와 10월 8일 핫픽스 베타(.1-beta.2)를 거쳐 올라온 판으로, **커밋 기록 기준 396개 PR**이 묶였습니다. 핵심은 **Claude Haiku 5.5 모델 지원**, **Code Mode의 `store`/`load` 상태 영속화**, **Workboard 사이드바·보드 고정**, **MCP Apps 개선**, 그리고 업데이트 방식을 바꾸는 **"sealed immutable installation generations(봉인된 불변 설치 세대)"** 입니다. 즉 이번 판은 **"모델 + 상태 + 설치 안정성" 세 축이 한 번에 움직인 정식 릴리스**입니다.

## 이 글을 읽으면 알 수 있는 것

- **2026.10.1 정식판**이 이전 2026.9.x 라인과 무엇이 다른지
- **Claude Haiku 5.5 지원**과 **Code Mode 상태 영속화**가 자동화에 갖는 의미
- **"불변 설치 세대"**가 업데이트·롤백을 어떻게 바꾸는지
- Workboard·MCP Apps 등 **Control UI 쪽 변화**
- **보안·복구 관련 수정**과 곧 도래하는 **SDK deprecation** 목록
- 지금 **올려야 할지 판단하는 기준**과 순서

## 도입: "신기능 뉴스보다 무서운 건, 업데이트가 반쯤 멈추는 일"

업무 자동화 파이프라인에 AI 에이전트를 붙여 굴리는 분들이라면 아마 공감할 텐데, 실사용에서 제일 골치 아픈 건 기능이 부족한 게 아니라 **"업데이트가 중간에 멈춰서 게이트웨이가 내려가는 일"** 입니다. 어제까지 잘 돌던 스케줄 작업이 업데이트 한 번에 멈추거나, 플러그인이 큰 환경에서 게이트웨이 시작이 몇 분씩 늘어지는 문제는 원인 찾기도 어렵습니다.

그래서 이번 **OpenClaw 2026.10.1**은 성격상 눈여겨볼 만합니다. 겉으로는 "모델 하나 추가 + UI 개선"처럼 보이지만, 실제로 무게가 실린 곳은 **상태 영속성(state persistence)** 과 **설치·업데이트 안정성**입니다. 오늘은 **GitHub 공식 릴리스 노트**와 **OpenClaw 공식 문서**를 기준으로, 꼭 알아야 할 것만 정리해 드립니다.

## 2. 핵심 변경 — "모델·상태·설치" 세 축

### ① Claude Haiku 5.5 지원
이번 판에서 명시적으로 추가된 신모델은 **Claude Haiku 5.5**입니다(#166706). 앞선 2026.9.9에서 **GPT-6.1 Sol(Codex 경유)** 과 함께 들어왔던 모델 지원이 정식판에도 그대로 실렸습니다. 자동화 관점에서 의미가 있는 건, **경량·저비용 모델 선택지가 하나 더 늘었다**는 점입니다. 대량 반복 작업은 Haiku급으로 돌리고, 판단이 필요한 구간만 상위 모델로 올리는 식의 비용 설계가 훨씬 자연스러워집니다.

### ② Code Mode의 `store`/`load` — 상태가 재시작을 넘어간다
개인적으로 이번 판에서 **가장 실무적인 변화**로 보는 항목입니다. **Code Mode가 `store`와 `load`로 작은 세션 스코프 값을 셀·답장·게이트웨이 재시작을 넘어 유지**할 수 있게 됐습니다(#164086). 쉽게 말해, 멀티스텝 자동화에서 중간 계산 결과나 진행 커서 같은 걸 **에이전트가 재시작돼도 잃지 않게** 됐습니다. 예약 작업·장기 실행 워크플로를 굴리는 입장에서는 "중간에 끊기면 처음부터"라는 고질적 문제를 줄여 주는 변화입니다.

### ③ 봉인된 불변 설치 세대(sealed immutable installation generations)
업데이트 방식 자체를 건드린 변화입니다. **설치 세대를 봉인·불변으로 관리하고, 활성화(activation)와 복구(recovery)를 지원**하도록 바뀌었습니다(#163799, #164306). 릴리스 노트 전반에 걸쳐 **"중단된 업데이트 복구", "게이트웨이를 멈춘 채로 두지 않는 롤백", "레거시 자식 리스(lease)가 이후 업데이트를 막지 않도록"** 같은 수정이 대거 포함된 것도 이 흐름의 연장선입니다. 요약하면 **"업데이트가 실패해도 이전 세대로 되돌아가기 쉬운 구조"** 를 지향한 것입니다.

### ④ Control UI — Workboard·MCP Apps·인라인 재생
- **Workboard 사이드바 내비게이션 + 개인 보드 고정**(#164604)
- **MCP Apps가 뷰를 열어둔 채로 도구를 호출**하고, 인라인 확인 메시지·폼·파일·컨텍스트를 동기화(#164496, #164493, #164277)
- **Control UI 채팅에 인라인 YouTube 재생** 추가(#164576)
- macOS 사이드바 신원 정보·플러그인 세션 카탈로그, Linux 컴패니언에 번들 Bun 사용(#164591, #164436, #164401)

자동화 콘솔을 자주 들여다보는 입장에서는 **MCP Apps의 "열어둔 채 호출"** 이 특히 반갑습니다. 승인 흐름과 도구 실행을 오가며 화면이 초기화되던 불편이 줄어듭니다.

### ⑤ 플러그인 격리와 엔터프라이즈
- **로드된 각 플러그인이 자체 격리된 상태·인그레스 큐를 사용**(#165063) — 특권 기능의 신뢰 요건은 그대로 유지
- **엔터프라이즈 저장소에 대한 클라우드 워커 지원** 추가(#160108)
- **기존 에이전트를 로컬 Claws로 마이그레이션**(#162329)
- RPC 응답 크기·메인 스레드 힙 진단 추가(#164335, #164418)

플러그인이 서로 상태를 오염시키지 않게 격리하는 건, 스킬을 여러 개 얹어 쓰는 환경에서 **장애 전파를 줄이는 방향**이라 실무적으로 의미가 있습니다.

## 3. 보안·복구 — 눈에 안 띄지만 중요한 수정들

릴리스 노트의 "Fixes" 섹션에는 자동화 운영에 직결되는 항목이 많습니다. 눈에 띄는 것만 추리면 이렇습니다.

- **보안·프라이버시:** 시작 전 **NUL 실행 인자 거부**, 미해결 피어 자격증명에 대해 **fail-closed** 처리, **만료된 Codex 세션·외부 라이브 오너가 후속 워크스페이스를 변경하지 못하도록** 차단, **사설 런타임 컨텍스트가 답장·저장 대화로 새지 않도록** 수정(#164770, #165021, #164197, #164203 등)
- **업데이트·Doctor:** 읽기 전용 관리형 설정에서도 복구 동작, 중복된 config·backup·metadata·pnpm-root 프로브 제거, **아직 시작 중인 게이트웨이는 경고로 처리**(#164193, #161924 등)
- **게이트웨이 시작(설치형 플러그인):** 큰 플러그인이 있는 환경에서 **설정 읽기마다 플러그인 Doctor 모듈을 캡처·폐기하지 않도록** 수정, Windows 플러그인 캡처가 다시 빠른 고정 디스크립터 복사를 사용해 **수 분 지연 없이 시작**(#168017, #167544, #161267)
- **Codex·ChatGPT·로컬 모델:** 스트림이 마지막 델타를 떨어뜨려도 **Codex 답장의 마지막 토큰 유실 방지**, Ollama 도구 호출이 Tool Search와 함께 동작, 작은 호스트에서 llama.cpp 메모리 인덱싱 OOM 해소
- **저장소·메모리:** 대용량 스토어의 SQL 변수 실패·롤백 저널 락 실패 제거, 유휴 런타임 상태·폐기된 버퍼 해제로 **메모리 사용량 감소**

솔직히 말하면 이런 항목들은 사용자 기능이 아니라서 체감이 잘 안 됩니다. 그런데 **"업데이트가 반쯤 멈추는 문제"와 "메모리 누수"는 프로덕션에서 가장 조용히 쌓이다 크게 터지는 유형**입니다. 이번 판은 그쪽에 무게가 실려 있습니다.

## 4. 곧 사라지는 것 — SDK deprecation 체크

정식판 릴리스 노트에는 **"Upcoming deprecations"** 목록도 함께 실립니다. 이번 판 기준으로, 이미 제거 목표일이 지났거나 경고가 시작된 항목이 여러 개 있습니다.

- **2026-09-08 제거 목표:** `sdk-untrusted-context-identifier-aliases` → 채널명 기반 프롬프트 컨텍스트 필드와 `buildChannelMetadata`로 이전
- **2026-09-26 경고 시작:** `channel-webhook-listener-config-inputs` → `legacyWebhook`로 이전
- **2026-10-01 경고 시작:** `session-manager-sync-persistence`, `extension-session-sync-persistence`, `provider-replay-sync-persistence`, `memory-session-sync-inventory` 등 → **Async 접미사가 붙은 비동기 API로 이전**
- **2026-10-02~03 경고 시작:** `workspace-mutation-guard-callback`, `gateway-placement-sync-results`, `watched-sessions-sync-harness-context`

**커스텀 플러그인·스킬을 직접 만들어 쓰는 분들이라면** 이 목록을 한 번 훑어보는 게 좋습니다. 대부분 "동기(sync) API → Async API"로 옮기는 성격이라, 지금 손보면 나중에 급하게 쫓기지 않습니다.

## 5. 지금 올려야 할까 — 업데이트 판단 가이드

**① 정규 라인(최신)을 쓰는 경우**
- 2026.9.9 → **2026.10.1로 올리는 게 자연스럽습니다.** 신모델(Haiku 5.5)과 상태 영속화, 업데이트 복구 개선이 함께 들어옵니다.
- 다만 **"불변 설치 세대"로 업데이트 구조 자체가 바뀌는 판**이라, 전형적인 순서를 권합니다: 현재 버전·설정 백업 → 별도 인스턴스에 2026.10.1 설치 → 대표 워크플로 3~5개 리허설 → 문제 없으면 전환.

**② LTS(extended-stable)로 고정 운용하는 경우**
- 최신 정규판으로 갈 필요는 없습니다. LTS 트랙은 별도로 관리되며, 검증된 변경만 내려옵니다. (직전 LTS 대응 판은 2026.8.35)

**③ 여러 대를 굴리는 경우**
- **핵심 업무 파이프라인은 LTS, 실험·신기능은 정규 라인**으로 분리하는 방식이 여전히 실질적으로 유리합니다.
- 업데이트는 **한 대씩 순차적으로.** 한 번에 다 올리면 문제 원인을 못 찾습니다.

**④ 플러그인을 직접 만든 경우**
- 위 SDK deprecation 목록을 먼저 확인하고, **Async API 이전**을 미리 해두면 좋습니다.

## 6. 솔직한 장단점 정리

**좋았던 점**
- **Code Mode 상태 영속화**가 실무적으로 큽니다. 재시작을 넘어 상태가 유지되면 장기 실행 자동화의 안정감이 달라집니다.
- **봉인된 불변 설치 세대**로 업데이트·롤백 안정성을 손봤습니다. 눈에 안 띄지만 운영에 직결됩니다.
- **Claude Haiku 5.5 지원**으로 비용 설계 선택지가 늘었습니다.
- **큰 플러그인 환경의 게이트웨이 시작 지연**을 줄인 수정이 포함됐습니다.
- 보안 쪽 `fail-closed` 처리와 컨텍스트 누출 방지가 명시적으로 표기됩니다.

**아쉬운 점**
- **396개 PR 규모**답게 변경 폭이 커서, 릴리스 노트를 다 읽기 부담스럽습니다.
- **업데이트 구조(불변 설치 세대)가 바뀌는 판**이라, 안정화 전까지는 다중 인스턴스에서 먼저 검증하는 게 안전합니다.
- **Workboard·MCP Apps·인라인 YouTube** 같은 UI 항목은 자동화 파이프라인 자체에는 직접 영향이 적습니다.
- deprecation 목록이 길어, **커스텀 플러그인 유지보수 부담**이 조금씩 늘고 있습니다.

## 마무리 — "안 터지는 판"을 원하는 분께 추천

정리하면, **OpenClaw 2026.10.1**은 화려한 단일 기능보다 **"모델 + 상태 + 설치 안정성"을 한 번에 다시 조인 정식판**입니다. Claude Haiku 5.5 지원과 Code Mode 상태 영속화는 자동화 설계를 조금 더 여유 있게 만들어 주고, 봉인된 불변 설치 세대는 업데이트가 반쯤 멈추는 사고를 줄이는 방향입니다. 최신 기능을 쫓기보다, **검증된 변경을 주기적으로 얹어 파이프라인을 조용히 굴리고 싶은 분** — 그런 분께 추천합니다.

**도입 팁 하나.** 지금처럼 업데이트 구조가 바뀌는 시점에는 **"한 번에 최신으로"보다 "한 대씩, 백업 후"** 가 훨씬 가성비가 좋습니다. 업무 자동화에 에이전트를 붙여 쓰는 분들이라면, **테스트 인스턴스에서 2026.10.1을 먼저 굴려 보고** 문제가 없을 때 핵심 파이프라인을 옮기는 순서를 권합니다.

> 다음 관전 포인트는 **2026.10.x 라인의 후속 정식판**과, **SDK deprecation 항목들이 실제로 어떤 판에서 제거로 확정되는지**입니다. 상태 영속화와 불변 설치 세대가 실제 운영에서 얼마나 안정적으로 자리 잡는지도 지켜볼 만합니다.
