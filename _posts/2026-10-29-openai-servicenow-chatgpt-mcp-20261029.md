> **📌 한줄 요약:** 2026년 **10월 28일(현지시간)**, ServiceNow와 OpenAI가 **파트너십 확장**을 발표했습니다. 핵심은 **ServiceNow MCP 플러그인이 OpenAI 마켓플레이스에 공개**된 것으로, ChatGPT 대화 안에서 **장애 티켓 조회 → 변경 위험 평가 → 레코드 갱신**까지 이어지는 **승인된 실행(governed action)** 이 가능해집니다. 권한과 업무 규칙은 ServiceNow의 **Action Fabric**이 그대로 적용하고, 실제 실행과 통제는 ServiceNow가 맡습니다. 여기에 **Codex의 AI Workflow Factory 통합**, **OpenAI 사이버 모델 기반 취약점 우선순위 판별**, **음성 리스크 평가**, **양사 내부 전면 도입**까지 묶였습니다. 다만 **지금 바로 쓸 수 있는 건 플러그인 하나**이고, 나머지는 2027년 일정입니다.

사내 IT 장애가 들어오면 흐름이 이렇게 갈립니다. ChatGPT에 증상을 붙여넣어 원인 후보를 정리하고, 다시 ITSM 화면으로 돌아가 유사 티켓을 검색하고, 변경 이력을 열어 위험도를 확인하고, 마지막으로 레코드에 코멘트를 남깁니다. 답을 얻는 시간보다 **화면 사이를 오가는 시간**이 더 긴 경우가 많습니다.

10월 28일 ServiceNow와 OpenAI가 내놓은 발표는 정확히 그 왕복 구간을 겨냥합니다. 질문에 답하는 챗봇이 아니라, **권한과 승인 규칙을 통과한 뒤 실제 시스템을 바꾸는** 쪽으로 넘어가는 시도입니다. 이 글은 **무엇이 열렸는지 → 권한은 어떻게 지켜지는지 → 개발자·운영팀에 뭐가 걸리는지 → 아직 아닌 것** 순서로 정리했습니다.

숫자 하나만 짚으면 이렇습니다. 올해 1월 계약 발표 때 ServiceNow가 언급한 규모는 **연간 800억 건**이었고, 이번 보도자료의 회사 소개 문구는 **1,000억 건**입니다. 9개월 사이 플랫폼을 지나는 업무량이 그만큼 늘었다는 뜻이고, 그 위에 AI가 붙는 것과 안 붙는 것의 차이도 같이 커집니다.

## 상세 분석

### 1) ChatGPT 안에서 '묻는 것'에서 '하는 것'으로

새 플러그인의 핵심은 **양방향 연결**입니다. 지금까지 ChatGPT와 사내 시스템을 잇는 방식은 대개 한쪽 방향이었습니다. 데이터를 꺼내와 요약하는 것까지는 되지만, 결과를 다시 시스템에 넣는 일은 사람이 했습니다. 이번 통합은 그 반대 방향까지 엽니다.

- ChatGPT가 **ServiceNow 인스턴스에 연결**되고, 고객이 **노출할 기능을 직접 선택**
- IT 담당자는 **유사 장애 검색 → 변경 위험 평가 → 해당 레코드 갱신**을 한 대화에서 처리
- ServiceNow는 **"실행과 통제의 시스템"** 지위를 유지한다고 명시

예고된 확장 시나리오도 구체적입니다. 온콜 엔지니어가 **연결된 알림, 최근 변경, 영향받은 서비스**를 한 화면에서 확인하고, 대응 팀을 지정한 뒤 인시던트 레코드를 갱신해 워크플로를 닫는 흐름입니다. 지금은 화면 세 개를 오가며 하던 일입니다.

### 2) 권한은 어디서 지켜지나 — Action Fabric

기업 입장에서 가장 중요한 질문은 "AI가 사내 시스템을 건드려도 되는가"입니다. 이번 발표에서 그 답으로 내세운 장치가 **Action Fabric**입니다.

- ServiceNow 안에서 적용되던 **권한·업무 규칙(business rules)·승인 절차**를 ChatGPT 상호작용에도 그대로 적용
- 사용자가 ServiceNow에서 가진 권한이 **ChatGPT로 넘어가도 유지**
- 실제 쓰기 작업은 **ServiceNow 쪽에서 실행·기록**

구조를 보면 OpenAI는 **판단과 대화**를, ServiceNow는 **권한과 실행**을 맡는 분업입니다. IT 부서가 별도 커스텀 연동을 직접 만들지 않아도 된다는 점이 이 구조의 영업 포인트입니다.

다만 이 설계는 **프롬프트 인젝션**류 공격과 맞닿아 있습니다. 티켓 본문이나 첨부 문서에 심어진 문장이 모델을 통해 "레코드 갱신" 같은 실행으로 이어질 수 있기 때문입니다. 권한 범위를 좁게 잡고, **쓰기 작업에 사람 승인 단계**를 두는 구성이 사실상 필수입니다.

### 3) 보안: 취약점 1만~10만 건 중 무엇부터

두 번째 축은 보안입니다. 보도자료가 든 예시가 상징적입니다. 코드베이스 스캔 한 번에 **1만~10만 건 이상**의 취약점이 잡히는데, 문제는 개수가 아니라 **"지금 당장 고쳐야 하는 것"을 가려내는 일**입니다.

- OpenAI의 **사이버 역량**과 ServiceNow의 **자산·접근 권한·기업 맥락**을 결합
- 목표는 **코드·앱·워크로드·네트워크·아이덴티티 전반의 공격 경로**를 식별·분류·검증·완화
- ServiceNow의 **'Shift Zero'** 전략(사고 전 예방) 가속이 목적
- ServiceNow는 OpenAI의 **Trusted Access for Cyber** 프로그램에도 합류

일정은 **2027년 1월 얼리액세스, 2분기 정식 출시**입니다. 올해 안에 쓸 수 있는 기능이 아니라는 점은 분명히 해둘 필요가 있습니다.

### 4) Codex는 앱 개발 쪽으로 들어옵니다

개발자에게 직접 와닿는 항목은 **Codex의 AI Workflow Factory 통합**입니다.

- ServiceNow의 **비즈니스 맥락과 플랫폼 기능**을 활용해 앱을 만드는 방향
- **Build Agent**, **Autonomous Engineer**에도 OpenAI 모델이 들어감
- 목표는 **레거시 앱을 ServiceNow 기반 워크플로로 현대화**하는 비용 절감

일정은 **2027년**입니다. 지금 Codex를 쓰는 팀 입장에서는 "ServiceNow 프로젝트를 할 때 별도 연동 없이 컨텍스트가 붙는" 그림이지만, 아직 발표 단계입니다.

### 5) 음성으로 리스크 평가서를 채우는 시나리오

세 번째 축은 음성입니다. **Super Intelligence Control Tower**에 OpenAI 음성 모델이 들어갑니다.

- 리스크 담당자가 **AI 활용 사례를 말로 설명**
- 에이전트가 **평가 문항을 최대한 자동 작성**
- 정보가 빠지거나 모호하면 **되묻는 질문**을 던짐
- 설명된 목적을 기준으로 **리스크 등급을 자동 부여**

AI 에이전트를 대량으로 굴리는 조직에서 병목이 되는 건 모델 성능이 아니라 **거버넌스 문서 작업**인 경우가 많습니다. 그 지점을 음성 인터페이스로 줄이겠다는 구상이고, 일정은 **2027년 1분기**입니다.

### 6) 두 회사가 서로의 고객이 됩니다

발표에서 실무적으로 의미가 큰 부분은 **상호 도입**입니다.

- ServiceNow: **전 직원**에게 ChatGPT Work와 Codex 제공 (지금까지는 **엔지니어링 조직**으로 제한)
- ServiceNow: 내부 보안 업무에도 OpenAI 역량 활용
- OpenAI: **자사 운영에 ServiceNow** 도입, Control Tower로 지원
- OpenAI: ServiceNow의 **Control Tower Alliance** 창립 멤버로 참여

"우리도 쓴다"는 선언이 붙은 B2B 계약은 보통 도입 속도를 앞당깁니다. 반대로 말하면, 두 회사 모두 **자기 조직에서 검증되지 않은 기능은 팔기 어렵다**는 뜻이기도 합니다.

## 영향 — 누구에게 무엇이 달라지나

### 사용자(IT·운영 담당자)

가장 먼저 체감하는 변화는 **탭 전환 감소**입니다. 장애 대응 중 "챗봇에서 답을 얻고 다시 ITSM으로 옮겨 적는" 구간이 줄어듭니다. 다만 권한이 그대로 따라오기 때문에, **할 수 있는 일은 원래 자기 권한 범위 안**입니다. AI가 권한을 넓혀주지는 않습니다.

### 개발자·플랫폼 팀

MCP 플러그인이 마켓플레이스에 올라왔다는 건, **사내 시스템을 MCP 서버로 노출하는 방식**이 기업 표준 경로로 자리 잡는 중이라는 신호입니다. ServiceNow 같은 대형 벤더가 직접 나섰다는 점에서, 자체 개발한 사내 도구도 같은 방식으로 붙일 수 있는지 검토할 시점입니다. 동시에 **어떤 도구를 어떤 권한으로 노출할지**를 정하는 일이 새 숙제가 됩니다.

### 업계

구도가 더 분명해졌습니다. ServiceNow는 이미 **Google Cloud와의 파트너십을 확장**했고, **NVIDIA**와도 협력하며 스스로를 "멀티 모델" 진영으로 규정합니다. OpenAI는 마이크로소프트, 세일즈포스에 이어 **ITSM·업무 플랫폼**까지 파고드는 중입니다. 모델 성능 경쟁이 **"어느 업무 시스템에 먼저 박히느냐"** 경쟁으로 옮겨가는 모습입니다.

주가 반응은 담담했습니다. 발표 다음 날(10월 28일) 미국 장에서 ServiceNow(NOW) 주가는 **3% 안팎 하락**했습니다(야후 파이낸스 기준). 파트너십 뉴스보다 실적·가이던스가 주가를 더 크게 움직이는 국면이라는 뜻으로 읽힙니다.

## 한계와 주의점

- **지금 쓸 수 있는 건 하나**: 실제로 열린 건 **MCP 플러그인**입니다. 음성·보안·Codex 통합은 모두 **2027년 대기**
- **플러그인도 초기 버전**: 강화 기능은 **2026년 말** 예정. 초기엔 조회·기본 갱신 수준으로 보는 편이 안전
- **권한 상속 = 공격면 확대**: 편의의 근원이 권한 위임이므로, **쓰기 액션 승인 규칙**과 **로그 감사**를 먼저 정해야 함
- **벤더 종속 리스크**: Action Fabric·Control Tower에 워크플로를 얹을수록 이전 비용이 커짐. **어떤 액션을 위임하지 않을지**를 계약 단계에서 정하는 편이 낫습니다
- **"에이전트가 한다"는 표현의 범위**: 실제 실행 주체와 책임 소재는 여전히 **고객 조직**입니다. 사고 시 책임 구조를 문서로 확인할 항목

## 실무 체크리스트 — 지금 점검할 것

- **연결 대상 인스턴스 분리**: 운영과 개발 ServiceNow 인스턴스를 같은 플러그인으로 묶지 않기
- **쓰기 액션 목록화**: 레코드 갱신·상태 변경·담당자 지정 중 **자동 허용/승인 필요/금지**를 3단계로 분류
- **프롬프트 인젝션 대비**: 티켓 본문·첨부파일에 외부 출처 텍스트가 섞이는 경로 확인, 실행 전 사람 확인 단계 배치
- **감사 로그 설계**: ChatGPT에서 시작된 액션이 **누구 이름으로, 어떤 근거로** 실행됐는지 남는지 확인
- **MCP 서버 인벤토리**: 사내에서 이미 돌리는 MCP 서버가 있다면 **노출 범위·인증 방식** 재점검
