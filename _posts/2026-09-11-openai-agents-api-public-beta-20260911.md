> **📌 한줄 요약:** OpenAI가 **2026년 9월 10일(미국 현지시간)** 오픈소스 **'Codex 하네스'**를 그대로 감싼 **Agents API를 퍼블릭 베타로 공개**했습니다. 핵심은 **"에이전트 오케스트레이션을 개발자가 직접 짜지 않아도 된다"**는 것 — **세션 관리, 컨텍스트 자동 압축(compaction), 툴 서치, 프로그램적 도구 호출, 병렬 서브에이전트, 장애 복구**를 **OpenAI가 직접 운영·유지**합니다. 실행 환경은 **① OpenAI 호스팅 샌드박스 ② 자체(self) 호스팅 ③ Blaxel·Cloudflare·Daytona·DigitalOcean·E2B·Modal·Oracle·Runloop·Vercel 등 9개 파트너 샌드박스** 중 고를 수 있습니다. 과금은 **토큰·도구·컨테이너 시간 외 추가 요금 없음**이라고 밝혔지만, 현재 **데이터는 미국(US) 리전만, Zero Data Retention(ZDR)은 미지원**입니다. 아래에서 무엇이 바뀐 건지, 우리 업무·개발에는 어떤 의미인지 살펴봤습니다.

요즘 저처럼 사내 업무 자동화를 **"에이전트로 굴려보자"** 고 벼르시는 분들, 공감하실 겁니다. 저도 최근 몇 달간 사내 반복 업무를 에이전트로 돌리려고 시도해 봤는데요, 결국 제일 오래 붙잡고 있던 게 **모델 성능이 아니라 '하네스(harness)'**였습니다. 세션을 어떻게 유지할지, 대화가 길어지면 컨텍스트를 언제 잘라낼지, 중간에 툴 호출이 실패하면 어떻게 복구할지, 여러 작업을 병렬로 돌리려면 서브에이전트 상태를 어떻게 나눌지… 솔직히 이 '접착제 코드'를 짜다가 지쳐서 원래 하려던 업무 자동화는 뒷전이 된 적이 한두 번이 아닙니다.

그런데 **9월 10일(미국 현지)** OpenAI가 흥미로운 걸 내놨습니다. **Codex와 ChatGPT for Work를 돌리는 그 하네스를, API 한 번으로 가져다 쓸 수 있게 개방한 'Agents API' 퍼블릭 베타**입니다. "그동안 각자 짜던 오케스트레이션 레이어를 우리가 운영해 줄 테니, 너희는 에이전트의 두뇌(지시문·도구)에만 집중하라"는 선언에 가깝습니다. 저처럼 **여러 AI 소식을 챙겨 보시는 분들**께는 꽤 의미 있는 변화라, 공식 발표문과 MarkTechPost·AI/TLDR 등 보도를 바탕으로 정리해 봤습니다.

## 이슈 요약 — 무엇이 나왔나

먼저 결론부터 정리하면 이렇습니다.

- **발표일**: 2026년 9월 10일 (미국 현지시간), **퍼블릭 베타**로 모든 개발자에게 개방
- **정체**: 오픈소스 **Codex 하네스**를 감싼 **관리형(managed) 에이전트 서비스**. 하네스는 **OpenAI가 직접 호스팅·유지**
- **한 줄 예시**: 세션 생성 한 번으로 **장시간 실행되는 에이전트**를 띄우고, 스트리밍/웹훅으로 진행 상황을 추적
- **내장 기능**: 컨텍스트 자동 압축, 툴 서치, 프로그램적 도구 호출, **병렬 서브에이전트**
- **과금**: **토큰·도구·컨테이너 시간**만 청구, **하네스 이용 추가 요금 없음**
- **제약**: **미국(US) 리전만**, **Zero Data Retention 미지원**

한마디로 **"에이전트를 만들 때 늘 새로 짜던 오케스트레이션·상태관리·복구 로직을, OpenAI가 서비스로 대신 제공"**한다는 겁니다. Codex 하네스가 그동안 실제로 검증돼 온 물건이라, 그걸 그대로 API 뒤에 얹어 준 셈입니다.

## 상세 분석 — 안을 뜯어보면

### ① API는 4가지 개념으로 정리된다

공식 문서는 Agents API를 **네 가지 개념**으로 설명합니다.

- **Agent(에이전트)**: 어떤 모델을, 어떤 지시문으로, 어떤 도구·MCP 서버를 붙여 쓸지 정의
- **Environment(환경)**: 에이전트가 파일을 읽고, 스킬을 불러오고, 명령을 실행하는 **샌드박스**(선택)
- **Session(세션)**: 작업을 수행하고 입력에 반응하는 **내구성 있는(durable) 에이전트 인스턴스**
- **Events & items(이벤트·항목)**: 에이전트에 보내는 입력과 그 결과물

흐름도 단순합니다. **세션 생성 → 작업 지시 → 스트리밍/웹훅으로 진행 추적 → 새 작업 부여 또는 진행 중 턴에 개입(steer)**. 기존에 개발자가 손으로 엮던 세션 상태·재시도·컨텍스트 관리를 이 네 개념 안으로 흡수한 구조입니다.

### ② 실행 환경 — 어디서 돌릴지가 핵심 설계 결정

OpenAI는 "에이전트를 어디서 실행할지"가 가장 중요한 아키텍처 선택이라고 강조합니다. 선택지는 세 갈래(그리고 **샌드박스 없이 실행**도 가능).

- **OpenAI 호스팅 샌드박스**: Codex와 ChatGPT for Work를 돌리는 그 샌드박스 인프라를 그대로 사용. 파일·패키지·스킬·플러그인 구성 가능
- **자체(self) 호스팅**: 내 환경에서 `codex exec-server`를 돌리고 제한된 키로 등록, **WebSocket으로 연결(모든 연결은 아웃바운드)**
- **파트너 샌드박스**: **Blaxel, Cloudflare, Daytona, DigitalOcean, E2B, Modal, Oracle, Runloop, Vercel** 9곳이 1급(first-class) 연동

폐쇄망·규제 산업이라면 **자체 호스팅**을, 빠른 프로토타이핑이라면 **OpenAI 호스팅**을, 이미 쓰는 클라우드가 있다면 **파트너 샌드박스**를 고르는 그림입니다. "하네스는 OpenAI가 관리하되, 실행 컴퓨팅은 원하는 곳에서"라는 유연성을 준 셈이죠.

### ③ 하네스가 대신 해 주는 것들

이게 이번 발표의 알맹이입니다. 개발자가 직접 안 짜도 되는 것들입니다.

- **장시간(Long-running) 세션**: 세션이 한계에 가까워지면 **이전 컨텍스트를 자동으로 압축(compaction)** — 직접 압축 로직을 안 써도 됩니다
- **효율적 툴 사용**: **툴 서치**가 도구 정의를 필요할 때만 불러와 토큰·비용을 줄이고 모델 캐시를 보존
- **프로그램적 도구 호출**: 도구를 **병렬로 실행**하고 체이닝. 결과를 코드로 필터·결합해 **관련 데이터만 컨텍스트로 반환**
- **서브에이전트**: **멀티에이전트**로 복잡한 작업을 독립 조각으로 쪼개고, 각 서브에이전트가 **자기 컨텍스트**를 유지. 메인 에이전트가 조율·취합

지원 도구도 **MCP, 커스텀 함수, 웹 서치 같은 빌트인**까지 폭넓습니다. 공식 예시 코드를 보면, **모델을 `gpt-6-astra`로 지정**하고 MCP 관측(observability) 서버와 `max_concurrent_subagents: 3` 설정을 넣어, **장애 조사(investigation) 에이전트를 단 한 번의 호출로** 띄우는 모습을 볼 수 있습니다.

### ④ 세 가지 런타임, 어디에 쓸까

OpenAI는 **Agents API / Agents SDK / Responses API** 세 가지를 이렇게 구분합니다.

| 구분 | Agents API | Agents SDK | Responses API |
|:--|:--|:--|:--|
| 에이전트 실행 위치 | OpenAI가 관리하는 Codex 하네스 | 내 애플리케이션 내부 | 내 앱(호스팅 오케스트레이션 선택) |
| 통합 난이도 | 낮음 | 중간 | 높음 |
| 작업 간 상태 | 세션 설정·턴·항목 저장됨 | 직접 저장 + SDK 세션 | 히스토리·체이닝·Conversations 수동 |

정리하면 **"빠르게 가고 싶으면 Agents API, 통제가 필요하면 SDK/Responses"**입니다. 올해 여러 에이전트 프레임워크를 깔짝거려 보신 분들이라면, 이 비교표가 왜 나왔는지 바로 아실 겁니다.

## 실제 사용감 — 초기 고객 사례

OpenAI가 공개한 초기 고객 수치입니다. **어디까지나 벤더가 밝힌 자체 수치이지 독립 검증 벤치마크는 아니라는 점**은 감안하고 보셔야 합니다.

- **Ciridae**: 평가 점수 **0.71 → 0.85**, 서브에이전트 흐름에서 **지연(latency) 4배 감소**
- **SafetyKit**: 사례 검토 워크플로 마이그레이션 후 **케이스당 비용 60% 절감**
- **Hypha**: **하네스와 샌드박스를 분리한 뒤 실패한 에이전트 응답 86% 감소**
- **Nash.ai**: 글로벌 물류망 전반에 **수천 개의 장시간 에이전트** 운영

솔직히 "0.71 → 0.85" 같은 숫자는 우리 업무에 그대로 대입되진 않습니다. 다만 **"하네스와 샌드박스를 분리했다"**는 Hypha 사례처럼, 그동안 에이전트를 만들며 **런타임과 실행 환경이 얽혀서 생기던 문제**를 아키텍처 차원에서 정리해 준다는 신호는 눈여겨볼 만합니다.

## 장점과 아쉬운 점(단점)

**장점**
- **오케스트레이션 코드 제거**: 세션·압축·복구·서브에이전트를 직접 안 짜도 됨
- **실행 환경 자유도**: OpenAI 호스팅·자체 호스팅·9개 파트너 샌드박스
- **추가 요금 없음**: 토큰·도구·컨테이너 시간만 과금
- **하네스 오픈소스**: Codex 저장소로 로직이 공개돼 **가시성** 확보

**아쉬운 점**
- **미국(US) 리전 전용 + ZDR 미지원**: 규제가 빡센 금융·의료·공공은 당장 도입이 어려움
- **Codex 하네스 종속**: 구조가 마음에 안 들면 결국 SDK/직접 구현으로 내려가야 함
- **베타**: 요동치는 정책·가격·SLA는 아직 지켜봐야 함

저처럼 사내 데이터가 민감한 곳에서 일하시는 분들께는, **US 리전·ZDR 미지원**이 첫 번째 체크 포인트가 될 겁니다. 생각보다 이 제약이 도입 여부를 가르는 결정적 조건이 되곤 하니까요.

## 영향 — 사용자와 개발자에게

**개발자에게**
- 그동안 **에이전트 프레임워크·오케스트레이션 SaaS를 직접 골라 붙이던 팀**이라면, 선택지가 하나 크게 늘었습니다. 특히 **MCP·커스텀 툴·서브에이전트**가 1급으로 들어와 있어, 새 에이전트 프로젝트의 부트스트랩 시간이 확 줄어들 전망입니다
- 반대로 **"내 하네스를 직접 만들어 차별화하던" 팀**에게는, 그 레이어의 가치가 OpenAI 쪽으로 상당 부분 흡수되는 압박이 됩니다

**일반 사용자에게**
- 직접 체감은 늦게 옵니다. 다만 **ChatGPT for Work·Codex 계열 제품의 백엔드가 이 하네스**라는 점을 감안하면, 우리가 쓰는 자동화 기능이 **더 오래 안 끊기고, 더 긴 작업을 끝까지 해내는 방향**으로 개선될 가능성이 큽니다

**업계에**
- "모델은 누구나, 승부는 하네스"라는 흐름이 한 번 더 확인됐습니다. 경쟁 프레임워크(LangGraph·CrewAI 등)와 클라우드 진영은 **샌드박스·오케스트레이션 통합 경쟁**으로 옮겨 붙을 겁니다

## 전망

세 가지를 봅니다.

1. **리전·컴플라이언스 확장이 관건.** US-only·ZDR 미지원은 베타의 한계입니다. 여기가 풀리는 시점이 **엔터프라이즈 대규모 도입의 변곡점**이 될 겁니다
2. **파트너 생태계 확대.** 지금 9개 파트너 샌드박스가 1급인데, 여기에 **관측·평가·가드레일 도구가 붙는** 흐름이 예상됩니다. 에이전트 '런타임'이 아니라 '운영 플랫폼'으로 넓어지는 그림이죠
3. **개발자 경험 표준화.** 세션·환경·이벤트라는 개념이 자리 잡으면, **"에이전트를 어떻게 기술할지"에 대한 사실상의 표준(de facto)** 이 될 수 있습니다. 좋든 싫든, 이 추상화는 한동안 업계 문법으로 남을 가능성이 큽니다

## 마무리 — 이런 분께 추천

정리하면, **Agents API**는 "에이전트를 만들고 싶은데 오케스트레이션·상태관리에 진이 빠지는" **업무 자동화 담당자·개발자분들께 가성비 좋은 선택지**입니다. 특히 이번 주(9/10) **ChatGPT for Financial Services**와 함께 나온 걸 보면, OpenAI가 **"에이전트를 실제 업무에 꽂는" 레이어를 본격적으로 서비스화**하는 국면이라는 게 분명해 보입니다.

착수 팁을 하나 드리면, 이렇게 시작하시면 됩니다.

- 민감정보가 없는 **내부 도구·반복업무 자동화**부터 퍼블릭 베타로 붙여 보기 (US 리전 제약 회피)
- 이미 클라우드가 있다면 **파트너 샌드박스(Vercel·Cloudflare·E2B 등)** 로 시작해 이관 비용 줄이기
- **하네스와 샌드박스를 분리한 아키텍처**(Hypha 사례)를 처음부터 염두에 두고 설계하기

규제가 걸린 데이터라면, 아쉽지만 **ZDR·리전 확장 발표를 기다렸다가** 도입하는 게 낫습니다. 지금은 **"우리 업무 중 어떤 걸 에이전트로 넘길 수 있는지 목록을 뽑아두는"** 단계로 쓰기 좋은 시점이라고 봅니다. 저도 이번 주말에 그 목록부터 다시 정리해 보려고 합니다.
