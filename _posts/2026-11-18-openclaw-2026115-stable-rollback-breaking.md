## 게이트웨이를 서비스로 띄워두고 잡을 돌리는 분들이라면

에이전트를 게이트웨이 서비스로 올려두고, 크론잡으로 반복 업무를 맡기고, 결과를 텔레그램으로 받는 구성이라면 이번 버전은 **"기능이 늘었다"보다 "업데이트하다 죽는 경우를 줄였다"** 로 읽는 게 맞습니다.

생각보다 무서운 건 새 기능이 아니라 업데이트 그 자체입니다. 자동 업데이트를 켜둔 인스턴스에서 닥터(Doctor) 검사나 게이트웨이 기동이 실패하면, 예전에는 **새 버전이 활성화된 채로 서비스가 뜨지 못하는 상태**가 남을 수 있었습니다. 2026.11.5는 이 지점을 정면으로 건드렸고, 동시에 플러그인 작성자에게는 **코드를 고쳐야 하는 변경**을 함께 넣었습니다.

두 가지가 한 릴리스에 같이 들어왔다는 게 이번 글의 핵심입니다. 운영자에게는 안전장치, 개발자에게는 숙제입니다.

## 바뀐 것 ① 업데이트가 실패하면 되돌린다

이번 릴리스에서 운영자에게 가장 중요한 변화입니다. 체인지로그의 표현은 이렇습니다.

> "닥터 또는 게이트웨이 기동이 실패하면 **활성화된 업데이트를 롤백**하고, 복원된 npm 패키지는 비루트 서비스에서도 읽을 수 있게 유지한다." (#197851, #193272)

읽어보면 구조가 이렇게 바뀝니다.

| 상황 | 이전 | 2026.11.5 이후 |
|---|---|---|
| 업데이트 후 닥터 검사 실패 | 새 버전이 활성 상태로 남을 수 있음 | **직전 상태로 롤백** |
| 업데이트 후 게이트웨이 기동 실패 | 서비스가 뜨지 못한 채 대기 | **자동 롤백** |
| 롤백으로 복원된 전역 npm 패키지 | root 소유로 바뀌어 서비스가 못 읽음 | **비루트 서비스도 읽을 수 있게 유지** |
| 업데이트 진행률 조회 | 닥터 유지보수를 막아 DB 자동 복구 불가 | **조회가 복구를 막지 않음** (#192083) |
| 플러그인 사후 닥터 실패 | 요약에서 사라짐 | **실패와 복구 안내가 요약에 표시** (#192942) |

여기에 복구 경로를 막던 자잘한 것들도 함께 정리됐습니다. Windows 패키지 업데이트가 같은 경로를 다르게 표기했다는 이유로 유효한 복구본을 거부하던 문제(#189385), 성공한 업데이트가 오래된 복구본을 남기던 문제(#189628), 후보 DB 검사가 임시 복사본을 못 지워 업데이트가 멈추던 문제(#193702) 등입니다.

### 다만, 순서가 있습니다

솔직히 이 부분이 이번 릴리스에서 가장 헷갈리는 지점입니다. 체인지로그 몇 항목에는 **"실행 중인 업데이터가 이미 이 수정을 포함하고 있어야 한다"** 는 단서가 붙어 있습니다.

- #193685 — Windows 백업 캡처 중 잠깐 잠긴 파일 재시도
- #196371 — 서비스가 다른 설치본을 쓸 때 CLI가 엉뚱한 곳에 남는 문제
- #196301 — 외부 데이터 파일을 쓰는 플러그인의 업데이트 리허설

즉 **11.4 이하에서 11.5로 올리는 첫 업데이트에는 이 수정들이 적용되지 않습니다.** 두 번째 업데이트부터 효력이 생깁니다. "롤백이 생겼으니 이제 안전하다"고 받아들이기 전에, 첫 점프는 수동으로 상태 디렉터리를 복사해 두는 편이 낫습니다.

## 바뀐 것 ② 파괴적 변경 — 하네스와 플러그인 세션 제어

이번 릴리스에 **Breaking** 딱지가 붙은 항목은 하나입니다. GitHub 릴리스 노트의 설명을 그대로 옮기면 이렇습니다.

> "서드파티 하네스는 **host runAttempt 콜백 안에서 세션 키 기반 활성 런을 등록**하고, 반환된 정리(cleanup) 함수를 보관해야 한다. 플러그인 RPC 핸들러는 `chatAbortControllers`/`chatQueuedTurns`를 **권한이 부여된 게이트웨이 메서드 디스패치로 교체**해야 한다. 시작 소유자 관측은 `expiresAtMs` 대신 `startDeadlineAtMs`를 쓴다. 번들 소비자는 마이그레이션 완료." (#175837)

업무 자동화 쪽에서 체감이 갈리는 지점은 두 번째 문장입니다.

| 대상 | 해야 할 일 | 안 하면 |
|---|---|---|
| 서드파티 하네스 개발자 | runAttempt 콜백 안에서 세션 키 기반 런 등록 + cleanup 함수 보관 | 런 추적·취소가 어긋남 |
| 플러그인 RPC 핸들러 작성자 | 내부 컨트롤러 직접 접근 → **권한 검사를 거치는 게이트웨이 메서드 디스패치**로 교체 | 핸들러가 거부되거나 권한 경계를 우회 |
| 시작 소유자 관측 코드 | `expiresAtMs` → `startDeadlineAtMs` | 만료 시점 판단 오류 |
| 번들 플러그인 사용자 | 별도 작업 없음 (이미 마이그레이션됨) | — |

여기서 눈에 띄는 건 방향입니다. 내부 컨트롤러를 직접 만지던 경로를 **권한 검사를 거치는 정식 디스패치로 밀어넣는** 변경이라, 편의성은 조금 떨어지고 대신 권한 경계가 분명해집니다. 사내에서 플러그인을 직접 만들어 쓰는 조직이라면, 11.5로 올리기 전에 **RPC 핸들러에서 내부 컨트롤러를 직접 참조하는 코드가 있는지**부터 확인하는 게 순서입니다.

## 바뀐 것 ③ 재시작을 넘어 살아남는 큐와 권한

지난 글에서 "재시작 한 번에 운영이 흔들린다"고 정리했는데, 이번 릴리스는 그 연장선입니다. 특히 **권한이 재시작을 넘어 유지되는지**를 다룹니다.

| 상황 | 2026.11.5의 처리 |
|---|---|
| 정상 재시작 중 접수된 큐 메시지 | **사라지지 않음**, 원래 한도와 현재 권한을 그대로 재확인 (#196923) |
| 재시작 후 큐에 남은 전송 | **접수 당시보다 넓은 권한을 쓰지 않음**, 원래 권한 확인 불가면 실패 후 재제출 (#196540) |
| 마지막 채팅 쓰기 | 남은 시간이 있으면 완료까지 드레인, 마감 초과 시 진단 정보 포함 거부 (#196493) |
| 워크스페이스 준비 중 재시작 | **중단된 턴을 버리지 않고 재개** (#196423) |
| 재시작 요청이 멈춘 경우 | 세션을 저장해 재개할 기회를 잃지 않음 (#188047) |
| 재시작 수락이 닫힌 뒤 도착한 채널 메시지 | 클레임되지 않게 막고, 롤백되면 전달 재개 |

권한 쪽 단서가 특히 중요합니다. **"원래 권한을 검증할 수 없는 전송은 실패하고 다시 제출할 수 있다"** 는 문장은, 재시작 후 조용히 넓은 권한으로 실행되는 것보다 **실패로 떨어지는 쪽을 택했다**는 뜻입니다. 크론잡이 재시작 직후 한 번 실패로 찍힌다면, 그건 버그가 아니라 의도된 안전 동작일 가능성이 큽니다.

메모리 쪽도 손봤습니다. 큰 메모리 인덱스 재구축이 메모리 부족으로 반복 재시작해 **벡터 검색이 통째로 먹통이 되던 문제**(#196378), 임베딩 배치 한도 오류가 감싸진 형태로 와서 인덱싱이 실패하던 문제(#187797)가 수정됐습니다.

## 크론잡·자동화에서 달라진 것

자동화 관련 수정은 10건 안팎입니다. 잡을 돌리는 쪽에서 체감이 큰 순서로 정리했습니다.

| # | 수정 내용 | 왜 중요한가 |
|---|---|---|
| 1 | **설정 핫 리로드가 진행 중 잡을 중단시키지 않음**, 시작 마감·취소는 그대로 유효 (#197606, #188982) | 설정 손보는 순간 잡이 잘리던 문제 |
| 2 | 스케줄러가 **늦게 깨어나도 잡을 조용히 버리지 않음** (#197484) | 다운타임·시계 점프 이후 유실 방지 |
| 3 | 재시작 재시도 마감·완료 런 식별자·예약 계정 선택 유지 (#180677, #197449) | 재시작 후 잡 신원이 어긋나던 문제 |
| 4 | 자동 스케줄을 끄면 **유휴 워커를 해제** (#196387) | 꺼둔 잡이 자원을 붙잡던 문제 |
| 5 | **수동 시작 자동화가 스킵·실패하면 소유 대화에 안내** (commit 6604030) | "안 돌았다"를 나중에 알게 되는 상황 완화 |
| 6 | 조용한(quiet) 자동화의 **거짓 실패 메시지 제거**, 조건 미충족 시 대화를 위로 올리지 않음 (#188594, #188700) | 알림 피로 감소 |
| 7 | 기본 DM 스코프에서 **메인 세션 자동화가 DM에서 정상 실행** (#180603) | 모델 호출 전에 실패하던 케이스 |
| 8 | 대화 리셋 후 **예약된 플러그인 명령이 거부되던 문제** (commit 94e1bfb) | 예약 명령 신뢰성 |
| 9 | 자동화 시간 제한이 **런 시작 전 대기까지 포함** (commit c12366a) | 무한 대기 방지 |
| 10 | `cron list`/`cron show` 중단 시 타임아웃까지 기다리던 문제 (#187726) | CLI 응답성 |

1번과 2번은 지난 글에서 "게이트웨이 재시작은 여전히 실행 중 잡을 중단시킨다"고 적었던 부분의 후속입니다. 설정 리로드 쪽은 이제 확실히 견디고, **재시작 자체는 여전히 잡을 끊습니다.** 배포 타이밍을 신경 써야 하는 건 변하지 않았습니다.

| 압축 요약 자격증명 (commit 21bb4e7) | 압축 요약의 인용 문맥에서 **인식된 자격증명을 마스킹** | 원본 트랜스크립트는 그대로, **모든 비밀을 가리지는 않음** |
| Tlon 인용 범위 (#186092) | 채널 자동 탐색이 꺼져 있어도 **미등록 채널에서 인용이 확장**되던 문제 | 공유 DM 세션에서는 소유자가 인용한 내용이 다른 발신자에게 보일 수 있음 |
| PR 귀속 안내 (#187805) | 귀속이 꺼져 있거나 시크릿 모드면 **대화에서 PR 귀속 지시 제거** | 기존 세션은 새 세션을 열어야 정리됨 |
| Control UI 응답 경로 (commit 2b08b6f) | 플러그인 리로드 후 응답이 **내부가 아니라 마지막 외부 채팅으로** 가던 문제 | 답변이 엉뚱한 채널로 새는 사고 방지 |

마스킹 항목에는 단서가 붙습니다. **"마스킹은 모든 비밀을 포함하지 않는다"** 는 문장은, 압축 요약을 외부로 내보내는 구성이라면 여전히 자체 필터가 필요하다는 뜻입니다.

## 솔직한 단점 — 이번 버전에서 걸리는 지점

1. **첫 업데이트에는 롤백이 반쯤 무용지물입니다.** 앞서 정리한 대로 업데이터 자체를 고치는 항목은 11.4 이하에서 올릴 때 적용되지 않습니다.
2. **베타와 안정판 간격이 30시간입니다.** 11.5-beta.4가 11월 16일 03:12 UTC, 안정판이 17일 10:47 UTC입니다. 검증 기간이 짧다는 뜻이라, 크리티컬한 자동화를 굴리는 인스턴스라면 하루 이틀 관망하는 편이 낫습니다.
3. **수정 138건은 "전부 확인했다"는 뜻이 아닙니다.** 이 글에서 다룬 건 하이라이트와 자동화·보안 섹션 위주입니다. 플러그인·모델 라우팅 쪽은 별도로 읽어야 합니다.
4. **파괴적 변경의 영향 범위가 좁다는 건 양날의 검입니다.** 번들 플러그인만 쓰는 사용자는 아무 일도 없지만, 직접 만든 하네스나 RPC 핸들러가 있으면 **업데이트 직후 조용히 거부**될 수 있습니다.

## 어떤 버전을 골라야 하나

| 선택지 | 버전 | 성격 | 권장 상황 |
|---|---|---|---|
| 안정 | **2026.11.5** | 롤백·재시작 복구·자동화 수정 대량 | 운영 인스턴스. 단, 커스텀 플러그인·하네스가 있으면 코드 점검 후 |
| 이전 안정 | 2026.11.4 | 승인 모델 강화, 유실·재시작 수정 | 커스텀 RPC 핸들러 마이그레이션 시간이 필요할 때 임시 유지 |
| 이전 안정 | 2026.11.3 | 보안 릴리스, 회귀 보고 있음 | 잡이 멈추는 증상이 이미 나타난 경우에만 |

판단 기준은 두 줄로 정리됩니다.

- **"자동 업데이트를 켜두고 손을 못 대는 환경이다"** → 11.5로 올린다. 단, 첫 점프 전에 상태 디렉터리를 복사한다.
- **"사내 플러그인·하네스를 직접 관리한다"** → 11.4에 머무르며 RPC 핸들러부터 마이그레이션한다.

## 마무리 — 업데이트 팁 세 줄

오픈소스라 구매 비용은 0원이지만, **업데이트 판단 자체가 비용**이라는 점은 이번에도 같습니다. 이번 버전 기준으로는 이렇게 정리됩니다.

> **① 상태 디렉터리를 먼저 복사하고, ② 내부 컨트롤러를 직접 참조하는 플러그인 코드가 있는지 확인한 뒤, ③ 업데이트 후 첫 크론 결과 전달까지 눈으로 확인한다.**

1번이 이번에 특히 중요한 이유는, 롤백 기능이 **첫 점프에서는 온전히 작동하지 않기** 때문입니다. 2번은 Breaking 항목이 알려주는 유일한 사전 점검 지점입니다. 3번은 변함없는 마무리 확인입니다. 재시작 직후 큐 전송이 한 번 실패로 찍히더라도, 권한 재확인 때문에 의도적으로 실패시킨 결과일 수 있으니 곧바로 롤백하지 마세요.

업무 자동화 파이프라인을 운영하면서 "요즘 업데이트만 하면 서비스가 한 번씩 안 뜬다" 싶은 분들이라면, 이번 릴리스의 롤백 항목부터 읽어보시길 권합니다. 플러그인을 직접 굴리는 분들이라면 #175837 하나만 먼저 확인해도 절반은 끝납니다.
