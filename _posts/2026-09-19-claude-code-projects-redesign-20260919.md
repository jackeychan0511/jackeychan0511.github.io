> **📌 한줄 요약:** **2026년 9월 17일(현지시간)**, Anthropic이 **Claude Code의 핵심 기능 'Projects(프로젝트)'를 전면 재설계**해 베타로 공개했습니다. 공식 제목은 **"Projects redesigned: from folder to conversation"** — **폴더에서 대화로**입니다. 기존 프로젝트가 **파일과 지침을 담아두는 정적인 폴더**였다면, 새 프로젝트는 **목표 하나만 던지면 Claude가 요청을 해석하고(scopes), 작업을 쪼개 병렬 스레드로 위임하고, 결과를 검토해 최종 산출물로 조립하는 '하나의 지속되는 대화'** 입니다. **각 스레드는 자체 브랜치와 레포 사본을 가진 Claude Code 클라우드 세션**이고, **프로젝트 공유 메모리와 라이브러리**를 함께 씁니다. 작업이 **클라우드에서 돌기 때문에 노트북을 닫아도 계속 진행**됩니다. 베타는 **Claude Code 클라우드 세션을 쓰는 일부 Pro·Max 구독자부터** 시작해 이번 주에 확대됩니다.

요즘 저처럼 **AI 에이전트를 실사용하면서 개발·업무 자동화 파이프라인을 굴리시는 분들** 많으시죠? 솔직히 저는 요즘 가장 자주 하는 고민이 **"에이전트를 하나 더 붙일까"가 아니라 "이 일을 어떻게 쪼개서 맡길까"** 였습니다. 병렬로 돌리려고 창을 여러 개 띄우고, 브랜치를 손으로 나누고, 끝난 결과를 다시 손으로 합치는 과정이 은근히 발목을 잡았습니다. **생각보다 병목은 모델이 아니라 '작업 분배와 취합'에 있었습니다.**

그런데 **2026년 9월 17일(현지시간), Anthropic이 그 병목을 정면으로 건드리는 기능을 내놨습니다.** Claude Code의 **Projects를 '폴더'에서 '대화'로** 다시 정의한 겁니다. 이번 글도 다른 소식들과 마찬가지로 **이슈 요약 → 상세 분석 → 영향(사용자·개발자) → 전망** 순서로 정리해 드리겠습니다.

*Anthropic 공식 블로그(claude.com/blog/projects-redesigned)에 게시된 'Projects redesigned: from folder to conversation' 대표 이미지 — 이번 업데이트의 핵심은 '폴더였던 프로젝트가 대화가 됐다'는 한 줄로 요약됩니다 (출처: claude.com 공식 블로그, 2026.9.17)*

## 🗞️ 이슈 요약 — 한눈에 보기

- **무엇:** **2026년 9월 17일(현지시간)**, Anthropic이 **Claude Code의 Projects 경험을 전면 재설계**해 **베타로 공개**. 공식 블로그 제목은 **"Projects redesigned: from folder to conversation"**, 부제는 "A new experience for Claude projects, now available in beta in Claude Code"
- **무엇이 바뀌나:** 기존 프로젝트 = **파일·지침·참고자료를 담는 폴더 + 하나의 채팅**. 새 프로젝트 = **목표와 레포(또는 컨텍스트)를 지정하면 Claude가 바로 착수할 일을 제안**하고, **요청 범위를 정해(scopes) 작업을 위임하고, 병렬 스레드를 조율하고, 결과를 검토해 최종 결과물을 조립**하는 **하나의 지속되는 대화**
- **핵심 구조:** **① 스레드(threads)가 일을 하고, ② 코디네이터(coordinator)가 스레드를 지휘**합니다. **각 스레드는 자체 브랜치와 레포 사본을 가진 완전한 Claude Code 클라우드 세션**입니다
- **공유 자산:** **프로젝트 공유 메모리**(모든 스레드가 읽고 씀 — "릴리스가 금요일로 옮겨졌다", "export가 왜 빠졌다" 같은 맥락 축적)와 **라이브러리**(내가 올린 파일 + Claude가 만든 산출물 모음)가 프로젝트 단위로 붙습니다
- **사용 방식:** 사용자는 **메인 프로젝트 채팅에서 진행 상황을 모니터·가이드**하거나 **개별 스레드에 들어가 세부 조정**할 수 있습니다. **휴대폰에서도 지시 가능**하고, **컴퓨터를 떠나도 작업이 계속**됩니다
- **주의할 점:** 여러 스레드가 동시에 돌면 **각각이 풀 Claude Code 세션**이므로 **사용 한도(usage limits)에 더 빨리 도달**할 수 있습니다. 공식 문서도 이 점을 명시했습니다
- **제약:** **스레드는 현재 클라우드에서만 실행**됩니다. **로컬 머신에서 내 도구·코드·사내 네트워크와 함께 실행하는 기능은 "곧(very soon)"** 이라고 예고했습니다
- **누가 쓸 수 있나:** **베타는 Claude Code에서 클라우드 세션을 사용하고, 웹·데스크톱에 기존 프로젝트가 없는 일부 Pro·Max 구독자**부터. **이번 주에 같은 플랜 사용자로 확대**, 그 이후 **모든 Claude와 Team·Enterprise 플랜**으로 넓힙니다. 대기자 명단(웨이트리스트)도 열려 있습니다
- **한 줄 요약:** **"에이전트를 잘 쓰는 법"이 '프롬프트 잘 쓰기'에서 '일을 잘 쪼개 맡기기'로 옮겨가는 순간**입니다. 그리고 Anthropic은 그 분배·조율·취합을 **제품 기능으로 흡수**했습니다

## 🔍 상세 분석

### 1️⃣ "폴더에서 대화로" — 무엇이 근본적으로 달라졌나

기존 Claude Code 프로젝트는 **정적인 작업 공간**에 가까웠습니다. 파일을 넣어두고, 지침을 적어두고, 그 안에서 **하나의 채팅**을 이어가는 구조였습니다. 여러 세션을 굴리려면 **사람이 직접 일을 나누고, 인계(handoff)를 넘기고, 결과를 다시 꿰매 붙여야** 했습니다. 공식 블로그가 인정한 문장이 정확히 이 지점입니다.

> **"Managing multiple sessions across a build used to require you to divide the work, juggle handoffs, and stitch the results back together."** (여러 세션을 굴리려면 일을 나누고, 인계를 저글링하고, 결과를 다시 꿰매야 했다)

새 프로젝트에서는 이 세 가지를 **Claude가 맡습니다.** 목표를 주면 **① 범위를 정하고(scopes) → ② 작업을 위임하고(delegates) → ③ 병렬 스레드를 조율하고(coordinates) → ④ 결과를 검토하고(reviews) → ⑤ 완성된 결과로 조립(assembles)** 합니다. 사용자는 **진행 중에도 계속 개입(steer)** 할 수 있습니다.

공식 문서가 든 예시 두 개가 이 기능의 성격을 잘 보여줍니다.

- **예시 A — 결제 지연 잡기:** 프로젝트를 설정하고 **"checkout의 p75 지연을 줄여라"**는 목표를 세우면, Claude가 **엔드포인트별로 프로파일링 → 최적화 테스트 → PR 생성**을 **여러 스레드에서 병렬로** 진행합니다
- **예시 B — 멀티 레포 마이그레이션:** **API·웹·모바일 레포를 연결**하고 **"폐기 예정 v1 엔드포인트를 정리하라"**는 목표를 주면, **레포별로 스레드를 하나씩 만들어** 호출자 마이그레이션 → 테스트 → PR 생성까지 하고, **어떤 PR을 먼저 머지해야 하는지 순서까지 알려줍니다**

저처럼 자동화 파이프라인을 운영하며 **"이 작업을 몇 개로 쪼개서 어디에 맡길까"를 매번 사람이 설계하던 입장**에서는, 이 분배 로직이 **도구 안으로 들어왔다는 점**이 가장 큰 변화입니다.

### 2️⃣ 구조를 뜯어보면 — '스레드'와 '코디네이터'

공식 문서의 표현은 이렇습니다. **"Projects have threads that do the work and a coordinator that directs them."** (프로젝트에는 일을 하는 스레드와, 그 스레드들을 지휘하는 코디네이터가 있다)

내부 구조를 정리하면 다음과 같습니다.

- **스레드 = Claude Code 클라우드 세션 1개.** 각 스레드는 **자체 브랜치**와 **레포 사본**을 받아서 작업합니다. 즉 **클라우드에 가상 개발 머신이 하나씩 뜨는** 구조입니다
- **충돌 처리는 PR과 동일하게.** 코디네이터가 작업을 정리해주지만, **두 스레드가 같은 코드를 건드리면 일반 PR처럼 머지 충돌(merge conflict)로 해소**됩니다. 마법이 아니라 **기존 형상관리 규칙 위에서** 돌아간다는 뜻입니다
- **스레드는 더 쪼갤 수 있습니다.** 각 스레드는 필요하면 **서브에이전트·루프·워크플로**로 자기 작업을 다시 나눠, 큰 작업을 더 빨리 끝냅니다
- **레포가 연결되면** 스레드가 **PR을 열고 테스트를 돌립니다.** 문서가 연결되면 **문서를 읽고 초안을 씁니다**
- **사용자가 개입하는 두 개의 창:** **메인 프로젝트 채팅**(전체 진행 모니터링·지시)과 **개별 스레드**(세부 확인·조정). 공식 표현대로 **"참모장(chief of staff)에게 브리핑하듯"** 프로젝트에 지시하면, Claude가 **새 스레드 또는 기존 스레드로 작업을 라우팅**합니다

![Claude Code 새 프로젝트의 '새 스레드 시작' 화면 (Anthropic 공식 자료)](/assets/images/posts/2026-09-19-claude-code-projects-redesign-20260919/claude-code-projects-threads-ui-official.png)
*새 프로젝트에서는 왼쪽 대화에서 목표를 주면 오른쪽에 스레드가 열리고, 그 아래에 메모리·의사결정·결과가 쌓입니다 (출처: claude.com 공식 블로그 'Projects redesigned', 2026.9.17)*

### 3️⃣ 공유 메모리와 라이브러리 — "프롬프트 엔지니어링을 줄인다"

이번 업데이트에서 실무적으로 가장 반가운 부분은 **기억**입니다. 공식 문서는 **"모든 스레드가 공유 메모리에 더하고, 공유 메모리에서 읽는다(Every thread now adds to and draws from a shared memory)"** 고 설명합니다. 그 결과 **복잡한 프롬프트 엔지니어링의 필요가 줄어든다**고 밝혔습니다.

프로젝트가 기억하는 것의 예시는 아주 현실적입니다.

- **"릴리스가 금요일로 옮겨졌다"**
- **"이 export 기능은 왜 빠졌는지"**
- **"billing 서비스를 건드리기 전에 누구에게 확인해야 하는지"**

여기에 더해 **라이브러리**가 생겼습니다. **내가 추가한 파일과 Claude가 만들어낸 산출물(artifacts)을 한곳에 모아**, 관련 자료를 찾기 쉽게 하고 **새 작업이 과거 결과 위에 쌓이게** 합니다. 그리고 Claude는 **작업 스타일·소통 방식까지 기억**해서, **얼마나 자주 체크인할지, 새 스레드를 얼마나 자주 열지, 업데이트를 얼마나 자세히 쓸지**를 조정할 수 있습니다.

솔직히 이건 **"에이전트가 똑똑해졌다"보다 "에이전트가 우리 팀 맥락을 기억한다"** 에 가까운 변화입니다. 저는 개인적으로 **에이전트 자동화에서 가장 자주 깨지는 지점이 '맥락 단절'** 이라고 봅니다. 매번 같은 배경을 다시 설명해야 하는 구조는 아무리 모델이 좋아도 실무에서 못 씁니다.

### 4️⃣ 정직하게 짚어야 할 대가 — 사용 한도와 '클라우드 전용'

공식 문서는 **단점도 숨기지 않았습니다.** 가장 중요한 문장은 이겁니다.

> **"Projects can run several threads at once, and each one is a full Claude Code session. Because of this, projects can reach usage limits faster."** (프로젝트는 여러 스레드를 동시에 돌릴 수 있고, 각각이 완전한 Claude Code 세션이다. 그래서 **프로젝트는 사용 한도에 더 빨리 도달할 수 있다**)

Anthropic이 제시한 대응책은 **① 프로젝트 단위 사용량 확인**, **② 코디네이터 채팅과 워커 스레드에 쓸 모델·추론 강도(effort) 레벨 선택**입니다. 즉 **"병렬성은 공짜가 아니라 한도를 먹는다"** 는 것을 제품이 먼저 인정한 셈입니다. 외신도 이 지점을 짚었습니다 — The New Stack은 이 기능이 **사용량을 갉아먹을 수 있다(usage trade-offs)** 고 분석했습니다.

두 번째 제약은 **실행 위치**입니다. **현재 스레드는 클라우드에서만 돕니다.** 공식 문서는 **"로컬 머신에서 내 도구·코드와 함께, 그리고 사내 네트워크 뒤에서 실행하는 것은 곧 온다(coming very soon)"** 고 예고했습니다. 장점은 분명합니다 — **노트북을 닫아도, 자리를 비워도 작업이 이어집니다.** 반대로 단점도 분명합니다 — **로컬 파일과 사내망 접근이 필요한 팀은 아직 못 씁니다.**

### 5️⃣ 누가, 언제부터 쓸 수 있나

공식 롤아웃 순서는 이렇습니다.

1. **오늘부터 베타:** **Claude Code에서 클라우드 세션을 쓰고, 웹·데스크톱에 기존 프로젝트가 없는 Pro·Max 구독자 일부**
2. **이번 주 중:** 같은 플랜의 더 많은 Claude Code 사용자로 확대
3. **그 이후:** **모든 Claude**, 그리고 **Team·Enterprise 플랜**
4. **기존 프로젝트:** Pro·Max의 기존 프로젝트는 **지금처럼 계속 작동**하며, 롤아웃이 **chat·Cowork로 확대될 때 업그레이드**됩니다
5. **접근이 안 되면:** Pro·Max 사용자는 **대기자 명단(웨이트리스트)** 에 이름을 올릴 수 있습니다

프로젝트를 만들 때는 **목표와 레포(또는 컨텍스트)를 고르고**, **클라우드 환경·커넥터·플러그인·지침·모델**을 설정할 수 있습니다. 그리고 시작하자마자 **Claude가 "지금 바로 집어들 수 있는 일"을 먼저 제안**합니다.

## 🌊 영향 — 사용자와 개발자에게

### 🧑‍💻 일반 사용자 입장

- **아직은 개발자 도구입니다.** 이번 베타는 Claude Code(클라우드 세션) 기반이라, **채팅·Cowork 쪽으로 확대되는 건 그다음**입니다. 일반 사용자가 체감할 시점은 **Team·Enterprise 롤아웃 이후**로 보는 게 정확합니다
- **Pro·Max 구독자라면 조건을 확인해 보세요.** 베타 진입 조건이 **"웹·데스크톱에 기존 프로젝트가 없을 것"** 이라서, 이미 프로젝트를 만들어 둔 계정은 **기존 프로젝트가 그대로 유지되는 대신 이번 베타 대상에서는 빠질 수 있습니다**
- **"악마는 한도에 있다"는 점은 미리 알아두시면 좋습니다.** 병렬 스레드는 **한도를 빨리 소진**합니다. 베타에 들어가면 **프로젝트 단위 사용량 화면을 먼저 확인**하는 습관이 필요합니다

### 🛠️ 개발자·기업 입장 (업무 자동화 시사점)

- **'작업 분해'가 사람의 설계에서 제품 기능으로 넘어왔습니다.** 지금까지 병렬 에이전트 운영은 **사람이 일을 쪼개고 브랜치를 나누고 결과를 합치는** 수작업이었습니다. 새 프로젝트는 이걸 **코디네이터 + 스레드 + 공유 메모리**로 흡수합니다. 우리 자동화 파이프라인 관점에서 보면 **오케스트레이션 계층을 직접 만들지 않아도 되는 범위가 넓어진 것**입니다
- **그래도 검증 책임은 우리에게 남습니다.** 각 스레드가 **PR을 열고 테스트를 돌린다**는 건 좋은 신호지만, **테스트가 없으면 검증도 없습니다.** 병렬 스레드가 만든 산출물을 **누가 어떤 기준으로 승인할지**를 먼저 정해두세요. 코디네이터가 결과를 **검토한다**고 해서 **우리 도메인의 정합성까지 보증하는 건 아닙니다**
- **머지 순서와 브랜치 전략을 미리 설계하세요.** 공식 문서가 강조한 대로 **충돌은 결국 PR 머지 충돌로 해소**됩니다. 병렬성이 높아질수록 **브랜치 수명을 짧게, PR을 작게** 가져가는 규율이 더 중요해집니다
- **사내망·로컬 파일이 필요한 팀은 '로컬 실행'을 기다리세요.** 클라우드 전용이라는 제약은 **규제 산업·폐쇄망 조직에선 사실상 도입 불가**를 뜻합니다. 다만 Anthropic이 **"곧"** 이라고 공식 예고한 만큼, **파일럿 일정은 그 시점에 맞춰 잡는 게 현실적**입니다
- **한도 관리를 프로젝트 예산처럼 다루세요.** 프로젝트별 사용량이 보이고 **모델·effort를 프로젝트 단위로 고를 수 있다**는 건, 곧 **"이 프로젝트는 비싼 모델로, 저 프로젝트는 저렴하게"** 라는 운영이 가능하다는 뜻입니다. 실무에서 가장 먼저 터지는 사고는 **느린 게 아니라 예산 초과**입니다

## 🔭 전망 — 앞으로 볼 지점 4가지

1. **'로컬 실행' 지원 시점이 기업 채택의 1차 관문입니다.** 지금은 클라우드 전용이라 **로컬 파일·사내 네트워크·내 도구 체인**이 필요한 조직은 못 들어옵니다. 공식 문서가 **"very soon"** 이라고만 밝힌 이 기능이 실제로 나오는 순간, **Team·Enterprise 확산 속도가 결정**됩니다
2. **'병렬 스레드 vs 사용 한도' 정책이 다음 논쟁거리입니다.** Anthropic은 이미 **9월 중순 Claude Code 주간 한도 조정**을 단행한 바 있어, **병렬 기능 확대와 한도 정책이 충돌할 가능성**이 있습니다. **스레드 수 제한, 프로젝트 단위 과금, 우선순위 모델** 같은 장치가 나올지가 관전 포인트입니다
3. **멀티에이전트 오케스트레이션의 '품질'이 검증대로 올라옵니다.** 코디네이터가 일을 잘게 쪼개는 건 쉬운 부분이고, 어려운 건 **잘못 쪼갠 작업을 알아채고 되돌리는 능력**입니다. 병렬 스레드가 늘어날수록 **충돌률·재작업률·검토 지연**이 새로운 품질 지표가 됩니다
4. **경쟁 도구들이 같은 방향으로 수렴합니다.** Claude Code가 '프로젝트 = 대화형 오케스트레이터'로 간 이상, **다른 코딩 에이전트들도 병렬 세션·공유 메모리·PR 자동화를 따라올 가능성**이 큽니다. 결국 **표준은 '에이전트 한 개의 성능'이 아니라 '여러 에이전트를 어떻게 감독하나'** 로 이동합니다

저는 개인적으로 이번 발표를 **"모델 성능 뉴스"가 아니라 "운영 방식 뉴스"** 로 봅니다. 새 모델이 나오면 다음 모델이 더 좋아지겠지만, **일을 쪼개 맡기고 기억을 공유하는 구조**는 **한번 자리 잡으면 팀의 기본값**이 됩니다. 그리고 그 기본값이 **사람의 손에서 제품의 기능으로 넘어가는 중**이라는 게, 이 뉴스에서 가장 조용하지만 가장 큰 변화입니다.

## ✅ 마무리 — 이런 분들께

정리하면, **2026년 9월 17일은 Claude Code의 '프로젝트'가 폴더에서 대화가 된 날**입니다. **목표를 던지면 Claude가 쪼개고, 병렬 스레드가 각자 브랜치에서 일하고, 공유 메모리에 맥락이 쌓이고, PR로 결과가 모입니다.** 대신 **한도는 더 빨리 소진되고, 실행은 아직 클라우드 전용**입니다.

베타에 들어가 보실 분들을 위한 실전 팁 네 가지만 정리해 드리겠습니다. **새 도구를 사는 것보다, 지금 쓰는 플랜에서 조건을 맞추는 게 먼저**입니다.

1. **베타 자격부터 확인하세요.** Pro·Max + **Claude Code 클라우드 세션** + **웹·데스크톱에 기존 프로젝트 없음**이 1차 조건입니다. 안 맞으면 **웨이트리스트**에 올려두세요
2. **첫 프로젝트는 '작고 검증 가능한 목표'로 시작하세요.** 공식 예시처럼 **"p75 지연 줄이기"** 처럼 **성공/실패가 숫자로 판정되는 목표**가 코디네이터 성능을 판단하기 가장 좋습니다
3. **테스트가 없으면 병렬을 켜지 마세요.** 스레드가 **PR과 테스트를 자동으로 돌리는** 구조이므로, **테스트가 빈약하면 자동화가 그대로 사고가 됩니다.** 최소한 **핵심 경로 테스트부터** 갖추고 들어가세요
4. **사용량 화면을 먼저 열어두세요.** 병렬 스레드는 **풀 세션을 여러 개** 돌립니다. **프로젝트별 사용량**을 보고 **코디네이터/워커의 모델·effort를 낮춰 조절**하면, 같은 구독료로 훨씬 오래 쓸 수 있습니다 — **가성비 좋게 오래 쓰는 비결은 결국 여기**에 있습니다

저처럼 **AI 에이전트를 실사용하면서 "어디까지 맡겨도 되나" 고민하시는 분들**, 그리고 **병렬 자동화 파이프라인을 직접 설계하시는 분들**께 이 글이 도움이 되었으면 합니다. 다음 이슈가 나오면 또 정리해서 올리겠습니다.
