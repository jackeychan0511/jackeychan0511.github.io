## 1. 요즘 저처럼 "주말에도 Hermes 커밋이 안 멈추네?" 하시는 분들

요즘 저처럼 **Hermes Agent 업데이트를 매일 쫓아가시는 분들**, 특히 이 블로그처럼 **크론잡 자동 포스팅을 Hermes에 맡기고 계신 분들** 많으시죠. 지난주 금요일(8/21) 밤에 v0.20.5(v2026.8.19)가 태깅되면서 한바탕 정리됐는데, 솔직히 "이제 좀 쉬겠지" 했습니다.

그런데 말이죠. 주말이 지나고 오늘(8/24) 아침에 GitHub를 열어보니 **이틀 새 또 커밋이 잔뜩 쌓여 있더라고요.** v0.20.5 태그 이후 main 브랜치에 약 **366커밋**이 새로 들어왔습니다. 주말에 사람들이 쉬는 프로젝트가 아닌가 봅니다. 게다가 다음 릴리스는 아직 태그가 안 찍힌 **v0.21.0**인데, 이 녀석은 단순 패치가 아니라 **v0.20.0 이후 전체를 큐레이티드 릴리스 노트로 정리해 배송**된다고 예고된 상태라, 지금 쌓이는 커밋들이 곧 '정식 노트의 재료'가 됩니다.

## 3. 핵심 ① — 데스크톱 Send Diagnostics: 에러 카드에서 원클릭 진단 보내기

### 어떤 기능인가

이번 주말 feat 커밋 중 제가 제일 먼저 눈여겨본 건 이겁니다.

> **"feat(desktop): Send Diagnostics — one-click redacted debug-bundle upload from the error card"**

번역하면 **"에러 카드에서 원클릭으로 민감정보가 가려진(redacted) 디버그 번들을 업로드하는 진단 보내기"**입니다. 데스크톱 앱에서 에러가 나면 그 에러 카드에 **"진단 보내기" 버튼**이 생기고, 누르면 로그·설정 일부를 묶어서 **민감정보(API 키, 토큰 등)를 가린 채** 개발팀에 전송해주는 기능이에요.

관련 커밋들을 보면 이 기능이 꽤 신중하게 만들어졌습니다.

- `fix(desktop): Send Diagnostics review fixes — consent accuracy, log-grade redaction, dismissal guard, linkless` — 동의 문구 정확성, 로그 등급별 가림, 닫기 가드까지 리뷰 반영
- 이후 `fmt(js)`·`style: post-rebase lint fixes` — 코드 정리까지 포함

### 실제 사용감/장점

- **버그 제보가 '설명'에서 '번들'로 바뀝니다.** 예전엔 "이거 왜 이래요?" 스크린샷 하나로 끝나던 게, 이제는 재현에 필요한 로그가 통째로 갑니다. 개발자 입장에서도, 신고하는 입장에서도 **디버깅 왕복 횟수가 확 줄어드는** 구조예요.
- **민감정보 가림(redaction)이 기본 탑재**라서, "로그에 키가 섞여 나갈까 봐" 안심하고 보낼 수 있습니다. 게다가 **동의(consent) 절차를 먼저** 거치도록 설계돼 있어서 원치 않으면 안 보내면 됩니다.
- 크론잡으로 자동 포스팅을 돌리는 입장에서, 데스크톱에서 무언가 꼬였을 때 **"진단 보내기" 한 번이면 원인 파악이 빨라진다**는 건 꽤 매력적입니다.

### 단점/주의

- 아직 **태그된 릴리스가 아니라 main 브랜치 커밋**입니다. 정식으로 쓰려면 v0.21.0 태그를 기다려야 해요.
- "민감정보를 가린다"는 게 **완벽 보장은 아닙니다.** 정말 민감한 내용이 로그에 평문으로 박혀 있으면 가림 규칙을 피해갈 수 있으니, 보내기 전에 번들 내용을 한번 훑어보는 습관은 여전히 필요합니다.

## 4. 핵심 ② — Bot Mode 봇 릴레이 안정화 4종: "봇끼리 메시지"가 이제 안전망을 갖췄다

### 어떤 기능인가

지난주 v0.20.5에서 **"모든 데스크톱 연결의 봇들이 서로 메시지를 주고받을 수 있다"**(bots on every Desktop connection can message each other)는 커밋이 들어왔었죠. 그런데 봇끼리 메시지를 주고받는 **릴레이(relay)**가 많아지면 자연히 생기는 문제가 있습니다. "메시지가 유실되면?", "동시에 두 봇이 보내면?", "받는 쪽이 오프라인이면?" — 이번 주말 커밋은 정확히 그 질문들에 답하고 있습니다.

> - **envelope TTL + offline fast-fail for bot relay** — 봇 릴레이 메시지에 유효기간(TTL)을 두고, 받는 쪽이 오프라인이면 빨리 실패 처리
> - **push-notified relay drain with poll backstop** — 푸시 알림으로 릴레이를 비우되, 폴링을 백스톱으로 유지
> - **per-profile turn lock — concurrent deliveries queue instead of racing** — 프로필별 턴 락: 동시 전달이 레이스 대신 큐잉
> - **typed failure-reason codes for bot turns and relay replies** — 봇 턴·릴레이 응답의 실패 사유를 코드로 구분
> - **needs-attention badge for background bot failures** — 백그라운드 봇 실패 시 '관심 필요' 배지

### 실제 사용감/장점

- **"메시지가 조용히 증발하는" 시나리오가 줄어듭니다.** TTL과 fast-fail이 생기면서, 받는 봇이 없으면 **빠르게 실패했다는 사실 자체를** 알 수 있어요. 무한정 쌓였다가 나중에 터지는 일이 없어집니다.
- **레이스가 큐잉으로 바뀝니다.** 여러 봇이 동시에 같은 프로필로 메시지를 보내도 순서가 꼬이지 않고 차례로 처리됩니다. 봇 그룹룸을 실제로 돌려보신 분들은 이게 얼마나 중요한지 아실 거예요.
- **실패 사유가 코드로 온다**는 건 자동화에 매우 큽니다. 크론잡 스크립트에서 "오프라인인지, 타임아웃인지, 권한 문제인지"를 문자열 파싱 없이 코드로 분기할 수 있거든요.

### 단점/주의

- TTL이 짧게 잡히면 **지연이 좀 있는 봇의 메시지가 먼저 죽을 수** 있습니다. 설정값을 확인해보는 게 좋아요.
- 이 안정화들도 전부 **main 브랜치 기준**입니다. v0.21.0 태그 전에는 '베타 느낌'으로 보시는 게 맞습니다.

## 5. 핵심 ③ — 업데이터·플릿: restart worklist와 설정 마이그레이션

### 어떤 기능인가

이번 주말의 숨은 주인공은 사실 **업데이터(updater)** 쪽입니다. 커밋 수로만 fix(update)가 13건이나 됐어요. 핵심 두 가지를 보면:

> - **"feat(update): the plan is now the restart worklist — every planned runtime must be accounted for"** — 업데이트 계획이 이제 '재시작 작업 목록'으로 동작. 계획된 모든 런타임이 빠짐없이 재시작 대상에 포함돼야 함
> - **"feat(update): sibling profiles' configs migrate with the fleet — no more silent version drift"** — 형제(sibling) 프로필의 설정이 플릿과 함께 마이그레이션. 조용한 버전 드리프트 제거
> - **"fix(update): ZIP swap preserves the built desktop app"** — ZIP 방식 업데이트 시 데스크톱 앱 빌드본 보존
> - **"fix(windows): restore dedicated CLI launchers on update"** — Windows 업데이트 시 전용 CLI 런처 복원

### 실제 사용감/장점

- **업데이트 후 '뭔가 하나 빠진' 느낌이 사라집니다.** 예전엔 업데이트하면 데스크톱 앱이 날아가 있거나, 프로필 중 하나만 옛 설정을 들고 있는 경우가 있었는데, 이제 **계획된 모든 런타임을 재시작 목록에 넣고, 프로필 설정까지 플릿 단위로 마이그레이션**합니다.
- 여러 프로필(예: 블로그용/업무용)을 나눠 쓰는 저 같은 사용자에겐 **'조용한 버전 드리프트' 제거**가 가장 반가운 문구입니다. 한쪽만 옛날 설정으로 남아서 "왜 결과가 다르지?" 하던 일이 줄어들 거예요.
- `fix(state)` 커밋들(**"stop unbounded state.db repair loop from filling the disk"**)도 주목할 만합니다. 상태 DB 복구 루프가 무한히 돌아 디스크를 채우는 문제를 차단했는데, 장기 실행하는 에이전트한텐 꽤 중요한 수정입니다.

### 단점/주의

- 업데이터가 **더 꼼꼼해진 만큼 업데이트 시간이 조금 더 걸릴 수** 있습니다. '재시작 목록'에 모든 런타임을 넣고 확인하다 보니, 런타임이 많은 환경에선 대기 시간이 체감될 수 있어요.
- 마이그레이션 로직이 복잡해질수록 **새로운 엣지 케이스**도 생길 수 있습니다. v0.21.0 출시 후 첫 업데이트는 여유를 두고 진행하는 걸 추천합니다.

## 6. 핵심 ④ — 그 외: gateway control socket·Codex 272K 복귀·CLI 종료 노이즈 수정

### ① gateway 소유 control socket

> **"feat(gateway): gateway-owned control socket — identify/status verbs, fleet consumers prefer it over scans (#92091 step 1)"**

게이트웨이가 자기 소유의 컨트롤 소켓을 갖고, `identify`·`status` 같은 동사를 제공하며, 플릿 소비자들이 스캔 대신 이 소켓을 우선 사용하게 됩니다. 여러 프로세스가 "지금 게이트웨이 상태가 뭐지?"를 묻는 방식이 **추측(스캔)에서 공식 경로(소켓)**로 바뀌는 거예요. 장기 운영 안정성에 좋은 기반 작업입니다.

### ② Codex GPT 슬러그 기본 272K 복귀

> **"feat(model): Codex GPT slugs default back to 272K; explicit -900k picker variants opt into the verified large window"**

Codex GPT 모델 슬러그의 기본값이 **272K 컨텍스트로 복귀**하고, 900K 대형 윈도우는 **명시적으로 선택하는 변형**으로 빠집니다. "기본은 검증된 272K, 큰 게 필요하면 명시적으로 골라라"는 정책인데, 자동화 입장에선 **기본값이 예측 가능**해져서 좋습니다.

### ③ CLI 종료 노이즈 수정

> **"fix: quitting the CLI no longer spams shutdown-race API errors onto the shell"**

CLI를 종료할 때 셸에 shutdown-race API 에러가 우수수 쏟아지던 문제를 수정했습니다. 사소해 보이지만 **매일 터미널에서 Hermes를 껐다 켜는 사람**에겐 체감이 꽤 큽니다. 함께 **인터프리터 종료 시 대화 루프 즉시 중단**(`fix(agent): break immediately on interpreter shutdown`)도 들어왔어요.

### ④ Bot Chat 이름 기준 정리

> **"fix(bot-mode): the canonical Bot Chat is found by NAME — session-id pins removed"**

봇의 대표 채팅(canonical Bot Chat)을 찾는 기준이 **session-id 핀이 아니라 이름(name)**으로 통일됐습니다. 세션 ID가 바뀌어도 "그 봇의 채팅"이 유지되는 구조라, 봇을 재시작해도 대화가 끊기지 않습니다.

## 7. 그럼 v0.21.0은 언제, 뭐가 들어오나

### v0.21.0의 정체

v0.20.5 릴리스 노트에 이런 문장이 명시돼 있습니다.

> **"Full curated release notes for this window will ship with v0.21.0, which will document everything from v0.20.0 onward — highlights, feature areas, and complete contributor credits. Nothing in this window is skipped."**

즉 **v0.21.0은 v0.20.0 이후의 모든 패치(v0.20.1~v0.20.5) 내용까지 전부 큐레이티드 릴리스 노트로 묶어 배송**하는 마일스톤 릴리스입니다. v0.20.0(8/3)부터 지금까지가 다 포함되니, **v0.21.0 노트 하나면 3주간의 변화가 통째로 정리**된다는 뜻이에요.

### 예상 타임라인

프로젝트 페이스를 보면 (8/3 → 8/13 → 8/16 → 8/18 → 8/21) **3~4일에 한 번꼴로 태그**가 찍혀 왔습니다. 그 속도라면 v0.21.0도 **이번 주 안**에 나올 가능성이 높아 보입니다. 물론 "큐레이티드 노트"가 붙는 릴리스라 조금 더 신중하게 갈 수도 있어요. 커밋 실측 기준으로는 **이미 366커밋이 쌓여서 재료는 충분**합니다.

## 8. 업데이트 방법과 실사용 팁, 그리고 솔직한 총평

### 업데이트 방법

- 기존 설치: **`hermes update`** 한 방이면 됩니다. (v0.20.5부터 업데이트 영수증·검증도 생겼어요)
- 신규 설치: `curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash`
- 미리보기를 직접 보고 싶다면: main 브랜치 기준으로 설치하거나, GitHub의 `compare/v2026.8.19...main`에서 커밋 로그를 직접 확인하세요.

### 실사용 팁 (크론잡 운영자 기준)

1. **봇 릴레이를 쓴다면 TTL 설정부터 확인**하세요. 기본값에 기대지 말고, 자기 봇의 지연 특성에 맞게 잡아야 메시지가 안 죽습니다.
2. **여러 프로필을 쓴다면 v0.21.0 첫 업데이트 후 설정을 한번 대조**해보세요. 플릿 마이그레이션이 잘 됐는지 확인하는 습관이 좋습니다.
3. 데스크톱에서 에러가 나면 **이제 '진단 보내기' 버튼부터** 찾아보세요. 스크린샷 찍어서 설명하는 것보다 훨씬 빠릅니다.

### 솔직한 총평

- **좋은 점:** 패치 직후 주말에 신기능보다 **안정성·운영 품질에 집중한 건 매우 건강한 신호**입니다. 특히 봇 릴레이 안정화와 업데이터 플릿 마이그레이션은 "여러 봇 + 여러 프로필 + 자동화"로 쓰는 사용자에게 **생각보다 체감이 큰** 변경들이에요.
- **아쉬운 점:** 아직 main 브랜치 커밋들이라 **정식 체험은 v0.21.0 태그를 기다려야** 합니다. 그리고 Send Diagnostics의 redaction이 완벽하진 않으니, 정말 민감한 로그는 보내기 전에 확인하는 게 좋습니다.

요즘 같이 Hermes Agent 업데이트를 매일 쫓아가시는 분들, 특히 **크론잡 자동 포스팅이나 봇 그룹룸을 실제로 돌리시는 분들**께는 v0.21.0이 '재료가 다 모인 완성판'이 될 거라 기대가 큽니다. 가성비 좋은 오픈소스 AI 에이전트 찾으시는 분께도, 이번 주말 커밋 흐름만 봐도 **개발이 멈추지 않는 프로젝트**라는 점은 충분히 추천 포인트가 됩니다. 다음 정식 릴리스(v0.21.0)가 태그되면 바로 실측 정리로 돌아오겠습니다.

*참고: 커밋 데이터는 2026-08-24 08:00 KST 기준 GitHub API(`compare/v2026.8.19...main`) 실측 결과입니다. 릴리스 일정은 프로젝트 사정에 따라 달라질 수 있습니다.*
