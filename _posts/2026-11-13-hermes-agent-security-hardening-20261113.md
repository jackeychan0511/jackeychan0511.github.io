업무 자동화 파이프라인을 운영하다 보면 구조적으로 피할 수 없는 지점이 하나 있습니다. **에이전트에게 일을 시키려면 결국 토큰을 쥐여줘야 한다**는 것입니다. 메일을 보내려면 SMTP 비밀번호가, 메신저로 보고를 넣으려면 봇 토큰이, 외부 API를 호출하려면 프로바이더 키가 필요합니다. 문제는 그 키들이 한 번 들어가면 **에이전트가 접근할 수 있는 모든 표면이 곧 키의 공격면**이 된다는 점입니다. 대시보드, MCP 서버, 메신저 브리지, 웹훅, 플러그인 — 편의를 위해 붙인 것들이 하나같이 자격증명이 지나가는 통로가 됩니다.

## 2. 가장 무거운 항목 — "대시보드 세션 하나로 키를 건드릴 수 있었다"

이번 묶음에서 실무적으로 가장 위험도가 높다고 판단되는 건 대시보드 계열입니다.

### ① 관리 파일 API의 쓰기 경로가 열려 있었다 (#154136)

대시보드의 관리 파일 API는 목록·읽기·다운로드 단계에서는 `.env`, `config.yaml`, `auth.json`, `mcp-tokens/**`, `pairing/**` 같은 파일을 숨기고 있었습니다. 그런데 **쓰기 경로는 `..` 탈출과 잠긴 루트 포함 여부만 검사**했습니다. 즉 인증된 클라이언트라면 `/api/files/upload`, `/api/files/upload-stream`, `/api/files/mkdir`, `DELETE /api/files`, 그리고 에디터의 `/api/fs/write-text`를 통해 **가려져 있던 자격증명 파일을 덮어쓰거나 삭제할 수 있었습니다.**

읽기는 막혀 있는데 쓰기는 열려 있는 상태는 생각보다 흔한 구멍입니다. 읽기를 막아둔 이유(민감정보 노출)와 쓰기를 막아야 하는 이유(설정 변조·서비스 장악)가 다르기 때문에, 한쪽만 처리되고 다른 쪽이 남는 경우가 생깁니다.

### ② SSH 워크스페이스에서 `~/.hermes/.env`를 읽을 수 있었다 (#153682)

`/api/fs/read-text`와 `/api/fs/read-data-url`은 SSH 워크스페이스 프로필에서 `backend.read_bytes(path)`를 **민감 경로 가드를 건너뛰고** 호출했습니다. 로컬 경로 분기와 다운로드 분기에는 가드가 있었는데, SSH 분기만 빠져 있었습니다. 결과적으로 대시보드 세션이라면 원격 머신의 `~/.hermes/.env`, `auth.json`, `mcp-tokens/*`를 읽어낼 수 있었고, **이름만 평범한 심볼릭 링크를 통해서도** 가능했습니다.

### ③ 데스크톱 렌더러가 붙인 토큰이 외부 호스트로 갈 수 있었다 (#153645)

데스크톱 앱의 `fetchJsonForBackend`는 백엔드 `baseUrl`과 렌더러가 넘긴 경로를 단순 문자열로 이어 붙인 뒤, 세션 토큰이나 OAuth 베어러를 붙였습니다. 경로 자리에 `@attacker.example/` 같은 값을 넣으면 `http://127.0.0.1:PORT@attacker.example/`로 파싱되어 **호스트가 공격자 쪽으로 바뀌고, 자격증명이 그대로 전송**되는 구조였습니다.

이 PR 본문에는 같은 계열의 `fs:*` 루트 포함 검사 절반은 **여전히 미해결(hardening 대상)** 이라고 명시돼 있습니다. 즉 이 항목은 "닫혔다"기보다 "가장 급한 절반이 닫혔다"에 가깝습니다.

### ④ 다른 프로필의 자격증명 저장소가 사각지대였다 (#153702)

파일 안전 가드는 활성 프로필(`HERMES_HOME`)과 전역 루트만 검사했습니다. `<root>/profiles/<name>` 아래는 아무도 훑지 않았기 때문에, 기본 프로필에서 **`read_file`로 `profiles/다른프로필/auth.json` 내용을 읽을 수 있었고**, `write_file`/`patch`로 다른 프로필의 `mcp-tokens/`, `.env`, `pairing/`, `state.db`를 고칠 수 있었습니다.

멀티 프로필은 업무용·개인용을 분리할 때 자연스럽게 쓰는 구성입니다. 분리를 해뒀는데 파일 접근 계층에서 분리가 유지되지 않았다면, 그 분리는 이름뿐인 분리가 됩니다.

## 3. MCP·플러그인 — "볼트에 넣었더니 더 위험해진" 역설

이번 묶음에서 가장 눈에 띄는 부분은 MCP 쪽입니다. 키를 `.env`에 두면 걸러지는데, **볼트(Bitwarden·1Password·`secrets.command`)에 두면 걸러지지 않던** 역설입니다.

### ⑤ 시크릿 소스 값이 Hermes 자체 키까지 실어 날랐다 (#153845)

`_build_safe_env`는 외부 시크릿 소스가 주입한 **모든 이름**을 그대로 stdio MCP 자식 프로세스에 전달했습니다. Hermes의 프로바이더 키, 봇·게이트웨이 토큰, `GH_TOKEN`, 릴레이 키, `AUXILIARY_*` 시크릿은 `.env`에 있을 때는 제거됐지만, **볼트에 있을 때는 서드파티 MCP 서버 전부에 그대로 전달**됐습니다. 문서(`SECURITY.md §2.3`)가 선언한 경계와 실제 동작이 어긋나 있던 셈입니다.

같은 계열로 `*_env`, `*_key`, `${VAR}` 참조, 프로필 어댑터 시크릿, `model.api` 참조 등을 stdio 자식에서 제외하는 커밋이 연달아 들어갔습니다. **MCP 서버는 대개 남이 만든 코드**라는 점을 생각하면, 이 계열 수정은 "설정 하나 바꿨을 뿐인데 키가 남의 프로세스로 갔다"는 사고를 막는 작업입니다.

### ⑥ 커스텀 엔드포인트에 OpenAI 키가 베어러로 붙었다 (#153681)

`resolve_provider_client("custom", explicit_base_url=...)`는 호스트 검증 없이 `OPENAI_API_KEY`를 읽었고, 같은 호스트용으로 설정된 키보다 **먼저** 읽었습니다. Fireworks·vLLM·오타 난 호스트·악성 호스트 어디든 OpenAI 시크릿이 베어러 토큰으로 전달될 수 있었습니다. 수정 후 우선순위는 명시 키 → 같은 출처 키 → OpenAI 호스트로 제한된 환경변수 순입니다.

### ⑦ Bitwarden CLI에 `http://` 서버 주소와 앰비언트 변수가 통과했다 (#153847)

`bws` 자식 프로세스는 `BWS_ACCESS_TOKEN`을 들고 실행됩니다. 그런데 `server_url`이 검증 없이 `BWS_SERVER_URL`로 들어갔고(`http://` 허용), 설정이 비어 있으면 **부모 셸의 앰비언트 `BWS_SERVER_URL`이 그대로 통과**했으며, `project_id`는 `--` 구분자 없이 argv에 들어가 `-`로 시작하는 값이 플래그로 해석될 수 있었습니다. 피싱성 설정 답변이나 커밋된 설정 하나로 액세스 토큰이 외부로 나갈 수 있는 구조입니다.

### ⑧ Skills Hub 리다이렉트가 메타데이터 주소까지 따라갔다 (#153818)

스킬 카탈로그가 제공하는 URL을 받아올 때 `follow_redirects=True`가 그대로 전달됐습니다. 카탈로그가 제어하는 URL이 `169.254.169.254`(클라우드 메타데이터)나 정책상 차단된 호스트로 302를 던지면 그대로 따라갔고, 세션 밖에서는 **SSRF 검사 자체가 없었습니다.** PR 본문에는 browse.sh의 `skillMdUrl`이 메타데이터로 리다이렉트된 응답이 스킬 본문으로 설치된 사례까지 적혀 있습니다.

### ⑨ 번들이 자기 `.skillignore`로 스캔을 회피할 수 있었다 (#153723)

`scan_skill`은 **스캔 대상 번들이 함께 제공한** `.skillignore`/`.clawhubignore`를 그대로 존중했습니다. 번들이 `*` 한 줄만 넣으면 `SKILL.md` 외 모든 파일이 검사에서 빠지고, `payload.sh` 안의 `curl … | sh`가 "안전"으로 통과했습니다. 설치 경로(허브·격리·에이전트 생성·프로젝트 스킬)가 모두 이 함수를 지나기 때문에 영향 범위가 넓습니다.

## 6. 그래서 지금 무엇을 해야 하나

가장 중요한 사실부터: **이 수정들은 아직 정식 릴리스에 없습니다.** 최신 태그는 11월 9일 자 v0.23.1이고, 이번 PR들은 그 이후인 11월 12일에 머지됐습니다. 공개 보안 권고문(GHSA)이나 CVE도 발행되지 않아서, 릴리스 노트를 뒤져도 이 내용은 나오지 않습니다. 변경 이력은 **PR 본문과 커밋 로그로만** 확인할 수 있는 상태입니다.

조건별로 정리하면 이렇습니다.

- **대시보드를 외부에 노출해 운영하는 경우** — 이번 수정의 핵심 대상입니다. ①·②·⑧ 항목이 모두 "대시보드 인증을 통과한 클라이언트"를 전제로 하기 때문에, 대시보드 자체의 접근 경로를 먼저 좁히는 편이 안전합니다. 터널·리버스 프록시로 공개해 두고 Basic 인증만 걸어둔 구성이라면 #153855도 함께 봐야 합니다.
- **멀티 프로필로 업무/개인을 분리하는 경우** — #153702가 해결되기 전까지 파일 접근 계층의 프로필 격리는 보장되지 않았습니다. 민감도가 다른 프로필을 같은 머신에 두고 있었다면, 파일 권한 자체를 별도 계정·별도 홈으로 분리하는 편이 확실합니다.
- **서드파티 MCP 서버를 붙여 쓰는 경우** — `.env`에 키를 두는 것과 볼트에 두는 것의 안전도가 같지 않았습니다. 서버별로 어떤 환경변수가 보이는지 확인하고, 가능하면 MCP 서버별 전용 키를 발급하는 편이 낫습니다.
- **WhatsApp·Feishu·LINE 게이트웨이를 쓰는 경우** — 세션 저장소 권한(0644 → 0700), 허용목록 매칭 방식, 리액션 우회 가능성이 모두 손봤습니다. 다중 사용자 머신에서 WhatsApp 게이트웨이를 돌렸다면 세션 디렉터리 권한을 직접 확인할 가치가 있습니다.
- **웹훅으로 외부 이벤트를 받는 경우** — V1 서명은 리플레이에 구조적으로 취약합니다. 라우트별 서명 고정 옵션이 추가됐으니, GitHub·Linear처럼 자체 서명 스킴이 있는 소스는 해당 스킴으로 고정하는 편이 좋습니다.
- **정식 릴리스를 기다리는 경우** — 이번 묶음은 v0.24.0 릴리스 노트에 정리될 가능성이 높습니다(v0.23.1 노트에도 "이 구간의 큐레이션 노트는 v0.24.0과 함께 나간다"고 적혀 있습니다). 급하지 않다면 태그를 기다리고, 급하다면 main 기준으로 빌드해야 합니다.

## 7. 솔직히, 아쉬운 점

세 가지는 분명히 해두는 게 좋겠습니다.

첫째, **공식 권고문이 없습니다.** 27건이 하루에 몰려 있는데 GHSA도 CVE도 없고, 릴리스 노트도 아직입니다. 보안 수정을 조용히 묶어서 내보내는 방식은 패치 속도를 높이는 대신, 운영자가 "내가 영향받는지" 판단할 근거를 늦게 갖게 합니다. PR 본문을 읽지 않으면 알 수 없는 종류의 변경입니다.

둘째, **일부는 부분 수정입니다.** #153645는 `hermes:api` 경로 결합 절반만 닫았고 `fs:*` 루트 포함 검사는 미해결로 남겼다고 스스로 밝힙니다. "고쳤다"는 말이 항목마다 다른 무게를 갖는다는 뜻입니다.

셋째, **실제 악용 정황은 확인되지 않았습니다.** 이 글은 PR 본문에 적힌 문제 정의와 수정 내용을 정리한 것이지, 공격 사례나 피해 보고를 확인한 것이 아닙니다. 이슈 번호로 참조된 원 보고가 다수 있지만, 그것이 실제 침해로 이어졌다는 근거는 아직 없습니다.

그럼에도 이 묶음이 "사소한 패치"가 아닌 이유는 분명합니다. **막힌 것들이 대부분 '이미 인증을 통과한 사람'이 키에 닿는 경로**였다는 점입니다. 인증을 뚫는 취약점은 아니지만, 인증된 표면 하나가 뚫리거나 세션 하나가 새는 순간 곧바로 키 유출로 이어지는 구조였습니다. 셀프호스팅 에이전트를 업무에 쓰는 입장에서는, 이런 종류의 수정이 기능 추가보다 체감 영향이 큽니다.

에이전트에 권한을 주는 일은 결국 **"어디까지 줬는지 정확히 아는 일"** 입니다. 이번 27건은 그 목록을 다시 한 번 정직하게 만든 작업이었습니다.
