## 에이전트를 두 대 이상 굴리기 시작하면 반드시 벽에 부딪히는 지점

AI 에이전트를 실사용하고 있습니다. 크론잡을 돌리고 있습니다. 그러다 보면 구성이 자연스럽게 이렇게 갈라집니다. 한쪽은 맥미니나 상시 켜둔 PC에서 도는 **게이트웨이**, 다른 한쪽은 노트북이나 폰에서 그 게이트웨이에 붙는 **클라이언트**입니다.

여기서 문제가 시작됩니다. 게이트웨이가 두 대가 되는 순간 "어느 컴퓨터의 어느 인스턴스에 붙어 있는지"가 사람 머릿속에만 남습니다. 노드를 새로 추가할 때마다 포트와 토큰을 복사하고, 누가 어떤 권한으로 붙었는지 확인하려면 로그를 뒤져야 합니다. 업무 자동화를 오래 굴리는 팀일수록 이 **신원·권한 계층**이 없다는 게 제일 불편합니다.

그리고 업데이트. 2026.11.5에서 업데이터가 꼬이는 사례가 나온 뒤로 "자동 업데이트를 켜둘까" 하는 고민이 생겼습니다. 켜두면 새벽에 게이트웨이가 내려가고, 꺼두면 보안 패치를 놓칩니다. 자동화를 오래 돌리는 입장에서는 **업데이트 자체가 리스크**가 되는 순간입니다.

2026.11.10-beta.1은 정확히 이 두 지점을 겨냥합니다. 오늘은 **GitHub 릴리스 노트(v2026.11.10-beta.1, v2026.11.6), npm dist-tags, 공식 문서(OpenClaw ID, 에이전트 템플릿, 자동 업데이트)** 를 기준으로 — 무엇이 바뀌었고, 실무에서 어떤 의미인지, 어디를 조심해야 하는지 순서로 정리하겠습니다.

## 1. 먼저 사실관계 — 같은 날 두 갈래로 갈렸습니다

npm 레지스트리에서 확인한 `dist-tags`는 이렇게 걸려 있습니다.

| 태그 | 버전 | npm 배포 (한국시간) |
|:---|:---|:---|
| `latest` | **2026.11.6** | 2026-11-20 01:52 |
| `beta` | **2026.11.10-beta.1** | 2026-11-20 00:09 |
| `extended-stable` | 2026.10.33 | 2026-11-19 13:15 (전날) |

GitHub 릴리스 공개 시각은 베타가 00시 45분, 11.6 안정판이 02시 26분입니다. **베타가 먼저 나오고, 두 시간 뒤 안정판이 따라붙은** 순서입니다. 여기서 오해하기 쉬운 부분이 있는데, **2026.11.6이 11.10 베타의 내용을 담은 안정판이 아닙니다.** 11.6은 2026.11.5 라인의 후속 수정판이고, 11.10-beta.1은 다음 마이너 라인의 기능 미리보기입니다. 번호가 커 보인다고 "더 새 안정판"으로 읽으면 안 됩니다.

정리하면 이렇습니다.

- **안정적으로 쓰는 쪽** → `latest` = 2026.11.6
- **LTS처럼 천천히 따라가는 쪽** → `extended-stable` = 2026.10.33
- **새 기능을 먼저 보는 쪽** → `beta` = 2026.11.10-beta.1

세 채널이 서로 다른 코드 베이스에서 움직인다는 점은 지난달 확장 안정판 글에서도 짚었는데, 이번 주는 그 구조가 가장 선명하게 드러난 사례입니다.

## 2. OpenClaw ID — 드디어 '어느 게 내 노드인가'를 계정으로 묶습니다

이번 베타에서 가장 큰 변화입니다. 릴리스 노트 표현은 이렇습니다.

> **OpenClaw ID:** connect nodes through the ID tunnel, approve them from Access, and link owner devices to your own identity.

지금까지 노드 연결은 게이트웨이 주소와 토큰을 직접 다루는 일이었습니다. OpenClaw ID는 그 위에 **소유자 신원 계층**을 얹습니다. 노드는 ID 터널을 통해 붙고, 붙은 노드는 **Access 화면에서 승인**하며, 소유자 기기는 자기 신원에 연결됩니다.

공식 문서(`openclaw id`)를 보면 동작 방식이 꽤 구체적으로 나옵니다.

- 상태 확인은 `openclaw id status`. 원격 접근이 켜져 있는지, 이 클로(claw)의 호스트명, Discovery가 가진 바인딩 번호, 연결 키 두 개(엔드포인트 키·게이트웨이 키)의 짧은 지문, 마지막 게시 시각을 보여줍니다.
- 키 파일이 없거나 다른 키가 들어 있으면 상태가 그대로 알려줍니다. `keys_missing`이면 "이 컴퓨터에 연결 키가 없어서 기기들이 닿을 수 없다", `key_mismatch`면 "이 컴퓨터의 연결 키가 기기들이 신뢰하는 키가 아니다"라고 표시됩니다. **이때도 게이트웨이 자체는 계속 돕니다.** 원격 접근만 꺼지는 것이고, 새 키가 저절로 생기지도 않습니다.
- 키를 옮겨야 할 때는 `openclaw id rebind`. 복구 키트(`OCK1-…`)와 링크 코드를 함께 씁니다. 링크 코드는 소유자 계정에서 발급되고 **10분 만에 만료**됩니다.
- `rebind`는 **이 컴퓨터의 게이트웨이에 직접 루프백으로 붙은 클라이언트에서만** 받습니다. 터널 너머나 다른 네트워크에서는 거부됩니다. 원격에서 남의 노드를 키 교체하는 시나리오를 막는 설계입니다.

실무적으로 왜 중요할까요. 자동화 파이프라인을 운영하면서 노드를 여러 대 붙여두면, 지금까지 권한 관리는 "토큰을 아는 사람은 다 할 수 있다"에 가까웠습니다. OpenClaw ID는 여기에 **소유자·멤버·초대·기기 로그인**이라는 단위를 넣습니다. 이번 베타의 수정 항목에도 "OpenClaw ID 멤버 권한을 HTTP 기록과 연결 앱 패널에도 일관되게 적용"이라는 항목이 들어 있습니다. 즉 UI에서만 가려지고 API로는 뚫리는 구멍을 막는 방향으로 다듬고 있습니다.

다만 **실험실(Labs) 기능**입니다. 문서도 "experimental Lab"이라고 명시합니다. 업무 핵심 경로에 바로 넣을 물건은 아니고, 노드가 세 대를 넘어가는 시점에 한 번 평가해볼 만한 기능으로 보는 게 맞습니다.

## 3. ClawHub 에이전트 템플릿 — CLAW.md 한 장으로 에이전트를 통째로

두 번째 축은 템플릿입니다. 그동안 "에이전트 하나 잘 세팅해두면 그 세팅을 다른 사람에게 넘기는 일"은 사실상 문서 작업이었습니다. `AGENTS.md`, `SOUL.md`, 스킬 폴더, 플러그인, 스케줄을 하나하나 설명해야 했습니다.

이번 베타는 그걸 **패키지**로 만듭니다. 명령은 스킬과 같은 형태입니다.

```bash
openclaw templates add @publisher/slug
```

패키지 구조는 `package.json`이 매니페스트를 가리키고, 매니페스트는 `CLAW.md`입니다. `CLAW.md` 앞부분의 YAML 프런트매터에 에이전트 정의가 들어가고, 본문은 새 에이전트의 `SOUL.md`로 그대로 적용됩니다. 문서에 실린 예시는 이렇게 생겼습니다.

```yaml
---
schemaVersion: 1
agent:
  id: github-triage
  name: GitHub Triage
  description: Reviews incoming issues.
  categories: [engineering]
workspace:
  files:
    - source: workspace/reference.md
      path: reference.md
skills:
  - ref: "@acme/triage"
    version: 1.2.0
mcpServers: {}
automations: []
---
```

무엇이 들어가고 무엇이 빠지는지가 중요합니다.

| 구분 | 포함 | 제외 |
|:---|:---|:---|
| 에이전트 정의 | 지시문, 워크스페이스 파일, 스킬, 플러그인, MCP 서버, 자동화(스케줄) | 기억(memory), 대화 기록, 자격증명 |
| 비밀값 | 환경변수 **참조**로만 선언 | 실제 토큰 값 |

"내 대화 기록과 메모리는 안 넘어간다"는 게 핵심입니다. 남에게 넘길 때 민감한 맥락이 따라가지 않으니, 팀 단위로 같은 업무 에이전트를 복제하기가 훨씬 수월해집니다.

템플릿은 ClawHub에서 스캔·검증을 거치고, 설치는 OpenClaw 쪽이 로컬 검사 → 새 에이전트 계획 → 동의 → 추가 순서로 처리합니다. 카테고리는 `engineering`, `operations`, `productivity`, `research`, `sales` 같은 슬러그를 씁니다. 참고로 **2026년 11월 18일부로 `personal`, `governance`, `finance`, `people` 카테고리는 ClawHub에서 제거**됐습니다. 그 슬러그로 시작하는 매니페스트는 여전히 게시되지만 자동 분류로 넘어갑니다.

그리고 이것도 **실험 기능**입니다. 문서 기준으로 `Settings → Labs`에서 Templates를 켜야 하고, 헤드리스 설치라면 `gateway.controlUi.experimental.templates`를 `true`로 두어야 합니다. 기본값이 꺼져 있다는 뜻이니, "명령이 안 먹는다"면 십중팔구 이 스위치입니다.

## 4. 업데이트를 '예약'하고, 들어오기 전에 '예행'한다

지난주 11.5 사태를 겪은 팀이라면 이 항목이 가장 반갑습니다.

> **Updates:** configure automatic update schedules and let the incoming release run its own pre-update rehearsal.
> **State upgrades:** migrate Gateway state using copy-and-swap at startup rather than modifying the live store in place.

두 문장이 뜻하는 바는 이렇습니다.

1. **업데이트 시간을 정할 수 있습니다.** 자동 업데이트가 아무 때나 도는 게 아니라, 지정한 스케줄에 맞춰 움직입니다. 업무 시간대 피크를 피하려는 팀에겐 실질적인 변화입니다.
2. **들어오는 릴리스가 자체 예행(pre-update rehearsal)을 돌립니다.** 새 버전이 상태 저장소를 건드리기 전에 미리 리허설을 해보고, 문제가 있으면 진행하지 않는 구조입니다.
3. **상태 마이그레이션이 copy-and-swap으로 바뀝니다.** 기존에는 살아 있는 저장소를 제자리에서 고쳤습니다. 이제는 복사본을 만들어 교체합니다. 업그레이드 도중 게이트웨이가 죽어도 원본이 남습니다.

여기에 같은 날 나온 **2026.11.6 안정판**의 첫 항목이 붙습니다.

> **Smoother upgrades:** bridge the 2026.11.5 updater to the current release path and validate staged plugin dependencies correctly on Windows.

11.5에서 업데이터가 꼬여 멈춘 케이스를 현재 릴리스 경로로 이어주는 수정입니다. 윈도우에서 스테이징된 플러그인 의존성 검증도 함께 고쳤습니다. **11.5에 머물러 있는 노드가 있다면, 베타로 가지 말고 11.6으로 먼저 올리는 게 순서**입니다. 11.6에는 메모리 사용량 감소(제한된 호스트에서 시작 시 메모리 압박 완화), 서브에이전트 결과를 게이트웨이 재시작 너머로 유지, iOS Talk의 30초 컷오프 해제 같은 실용적인 수정도 함께 들어 있습니다.

## 5. 재시작을 넘어가는 실행 — 자동화에서 제일 중요한 부분

실무적으로 이번 베타에서 가장 중요한 변화라고 보는 항목입니다.

> **Durable execution:** keep background commands running across Gateway restarts on macOS.

크론잡으로 반복 업무를 맡기고 결과를 메신저로 받는 구성에서, 지금까지 가장 골치 아팠던 건 **게이트웨이가 재시작되는 순간 날아가는 작업**이었습니다. macOS에서 백그라운드 명령이 게이트웨이 재시작을 넘어 계속 돕니다. 릴리스 노트에는 서브에이전트 결과를 재시작 너머로 유지하고, 요청자가 중단됐을 때 완료 전달을 재시도한다는 수정도 함께 들어 있습니다.

같은 결의 변경이 몇 개 더 있습니다.

- **브라우저 핸드오프:** 에이전트가 쓰는 브라우저를 Browser 패널에서 직접 넘겨받을 수 있습니다. 에이전트를 멈추지 않고 개입할 수 있다는 뜻입니다. 로그인 벽에 막혔을 때 에이전트를 죽이고 다시 띄우던 절차가 사라집니다.
- **채팅 제어:** 실행을 멈추지 않고 대기 중인 조향 메시지를 보내고, 큐에 쌓인 메시지를 편집하고, 앱을 재시작해도 작성 중이던 초안이 남습니다.
- **게스트 멤버 역할:** 샌드박스된 세션 도구만 가진 게스트 역할이 추가됐습니다. 외부 협업자를 들일 때 권한을 잘라주기 쉬워집니다.
- **도구 색인(opt-in):** 사용 빈도로 정렬된 도구 인덱스를 켤 수 있습니다. MCP 도구도 포함됩니다. 도구가 수십 개로 늘어난 게이트웨이에서 프롬프트가 비대해지는 문제를 줄이는 방향입니다.

## 6. 솔직히 아쉬운 점, 조심해야 할 점

장점만 쓰면 후기가 아니죠. 생각보다 걸리는 부분도 분명합니다.

**① 베타 채널입니다.** 11.10-beta.1은 정식판이 아닙니다. 업무 핵심 자동화가 도는 게이트웨이에 바로 올릴 물건은 아닙니다. 별도 인스턴스에서 먼저 검증하는 게 안전합니다.

**② OpenClaw ID와 템플릿 모두 실험 기능입니다.** Labs 스위치를 켜야 동작하고, 문서도 experimental이라고 못 박습니다. "기능이 있다"와 "지금 켜도 된다"는 다른 얘기입니다.

**③ 키 관리 부담이 생깁니다.** OpenClaw ID는 편리한 대신 **키 파일이 사라지면 원격 접근이 꺼집니다.** 다행히 로컬 게이트웨이는 계속 돌고, 복구 키트(`OCK1-…`)로 `rebind`가 가능하지만, 복구 키트를 잃으면 그 클로는 옮길 수 없습니다. 문서 표현 그대로 "Without the kit, the claw cannot be moved"입니다. 키트 보관을 진지하게 해야 합니다.

**④ `rebind`는 원격에서 못 합니다.** 직접 루프백으로 붙은 클라이언트에서만 됩니다. 서버실에 있는 노드를 집에서 키 교체하는 시나리오는 안 됩니다. 물리적 접근이 필요한 상황을 미리 가정해야 합니다.

**⑤ 버전 번호 혼동.** 앞서 짚었듯 `latest`는 11.6, `beta`는 11.10-beta.1입니다. 번호만 보고 "11.10이 더 최신 안정판"으로 오해하면 안 됩니다.

**⑥ 릴리스 검증 항목에 "npm Telegram beta E2E: not supplied"가 남아 있습니다.** 텔레그램 채널을 주 경로로 쓰는 구성이라면 베타 검증 범위가 온전하지 않다는 뜻이니, 직접 확인이 필요합니다.

---

## 7. 그래서 누가 먼저 봐야 하나

정리하면 이렇습니다.

- **노드를 두 대 이상 붙여 쓰고, 누가 어떤 권한으로 접근하는지 정리해야 하는 팀** → OpenClaw ID를 별도 인스턴스에서 먼저 평가해볼 만합니다. 특히 HTTP 기록·연결 앱 패널까지 권한이 일관되게 걸리는지가 이번 수정의 핵심입니다.
- **같은 업무 에이전트를 여러 사람에게 배포해야 하는 조직** → 템플릿이 가장 큰 절약입니다. 다만 Labs 스위치와 ClawHub 카테고리 변경(11월 18일)을 먼저 확인하세요.
- **크론잡으로 오래 도는 작업이 게이트웨이 재시작에 자주 끊기는 환경** → durable execution과 copy-and-swap 마이그레이션이 직접적인 해법입니다. macOS 비중이 높다면 더 그렇습니다.
- **11.5에서 업데이트가 꼬인 채 멈춰 있는 환경** → 베타가 아니라 **11.6 안정판**으로 먼저 복구하는 게 순서입니다.

업데이트 팁을 하나 더 붙이면, 베타를 볼 때는 **상태 디렉터리를 통째로 백업하고, `latest` 인스턴스와는 별도 경로에서** 돌리는 게 좋습니다. 이번 베타에 백업 진행률(단계·바이트) 표시가 들어왔지만, 그건 백업이 잘 도는지 보여주는 기능이지 백업을 대신해주는 기능은 아닙니다.

---

## 마무리 — 이번 주 OpenClaw는 '기능'보다 '운영'을 고쳤습니다

2026.11.10-beta.1을 한 문장으로 줄이면 **"에이전트를 여러 대 굴리는 사람을 위한 운영 계층"** 입니다. 신원(OpenClaw ID), 배포 단위(템플릿), 업데이트 안전장치(스케줄·예행·copy-and-swap), 실행 연속성(durable execution). 화려한 데모 기능은 없지만, 자동화를 오래 돌리는 입장에서 아픈 곳을 정확히 찌릅니다.

동시에 2026.11.6 안정판이 같은 날 나와 11.5의 업데이터 문제를 정리했습니다. 새 기능을 좇기보다 **지금 쓰는 채널을 먼저 안정화하고, 그 위에서 베타를 구경하는 순서**가 이번 주에는 맞습니다.

업무 자동화를 오래 굴리면서 "가끔씩 게이트웨이가 재시작되면 작업이 날아간다"는 문제를 안고 있었다면, 다음 마이너 라인의 durable execution은 충분히 기다릴 만한 변화입니다. 가성비 좋은 구성으로 자동화를 안정적으로 돌리고 싶은 분들께는, 당장 베타로 갈아타기보다 **11.6으로 기반을 다지고 11.10 정식판을 기다리는 쪽**을 권합니다.
