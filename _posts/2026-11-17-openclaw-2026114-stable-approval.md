## 크론잡에 일을 맡겨둔 구성이라면

에이전트에게 반복 잡을 맡기고, 게이트웨이를 서비스로 띄워두고, 잡 결과를 메신저로 받아보는 구성이라면 이번 릴리스는 "기능 추가"보다 **"조용히 사라지던 것들이 돌아오는 릴리스"** 로 읽는 게 맞습니다.

생각보다 무서운 건 대규모 장애가 아니라 **소리 없이 유실**되는 쪽입니다. 이번 체인지로그에 적힌 표현을 그대로 옮기면 이렇습니다.

- 설정을 다시 불러오는 사이 **WhatsApp 최종 답변이 사라진다**
- 연결이 끊겼다 붙는 순간 **버퍼에 쌓인 Signal 메시지가 건너뛰어진다**
- 게이트웨이가 첫 응답 전에 재시작되면 **이미 접수된 프롬프트가 대화 기록에서 사라진다**
- 스케줄러가 늦게 깨어나면 **반복 잡이 조용히 스킵된다**

네 가지 모두 2026.11.4에서 수정 항목으로 올라온 것들입니다. 잡이 "안 돌았다"는 걸 며칠 뒤에 알아차리는 상황을 줄여주는 패치라서, 릴리스 이름은 patch인데 체감은 그보다 큽니다.

## 바뀐 것 ① 위임된 변경은 이제 승인을 거친다

이번 릴리스에서 실무적으로 가장 중요한 변화는 승인 모델입니다. 체인지로그의 표현은 이렇습니다.

> "권한이 제한됐거나 검증되지 않은 상태에서 다른 승인이 없으면, **위임된 지속 변경(delegated persistent changes)** 에 승인을 요구한다. 허용된 위임 변경에 대한 **상시 승인(standing approval) 설정**을 추가한다."

읽어보면 구조가 이렇습니다.

| 구분 | 이전 동작 | 2026.11.4 이후 |
|---|---|---|
| 위임된 설정 변경 | 자동 승인 설정에 기대는 경로가 있었다 | 권한이 제한·미검증이면 **승인 요구** |
| 반복되는 위임 변경 | 매번 승인 | **상시 승인 설정**으로 한 번에 허용 가능 |
| 승인 취소 | 실행 중 설정이 바뀌어도 이전 판단을 따를 수 있었다 | **취소된 자동 승인은 실행 중에도 재확인** |
| Full Access / 상시 승인 | — | 직접 실행·편집 도구가 막혀 있어도 **호스트 코드 실행을 여는 변경을 승인할 수 있다** |

마지막 줄이 핵심입니다. 편의를 위해 상시 승인을 열어두면, **도구 권한을 막아둔 구성에서도 호스트 코드 실행 경로가 열릴 수 있다**는 뜻입니다. 자동화를 "사람 손을 덜 타게" 만들수록 이 설정 하나가 사실상 권한 경계가 됩니다.

같은 섹션에서 승인 우회와 관련된 수정도 함께 들어갔습니다.

- 재귀 평가되는 단독 대입문과 레거시 `$[...]` 산술 인자가 **allowlist 승인만으로 통과하지 못하게** 차단
- `NAME+=value` 형태의 환경변수 대입으로 시작하는 명령은 **별도 프롬프트** 표시
- Windows에서 POSIX 셸 페이로드에 대한 승인은 **1회성** 유지
- 남아 있던 레거시 exec 승인이 정상 정책과 노드 호스트 시작을 막던 문제 수정, **형식이 깨진 정책은 fail-closed**

업무 자동화 파이프라인을 운영한다면 이번 버전에서 **승인 프롬프트가 이전보다 자주 뜰 수 있습니다.** 특히 위임 변경을 자동 승인에 기대고 있었다면, 업데이트 직후 첫 실행에서 승인 요구가 늘어나는 게 정상 동작입니다.

## 바뀐 것 ② 정책 플러그인이 이미지를 먼저 본다

두 번째 추가 기능은 플러그인 쪽입니다.

> "정책 플러그인에 **이미지 검사**를 추가해, 해당 이미지가 모델에 도달하기 전에 실행을 차단할 수 있게 한다."

지금까지 정책 플러그인은 주로 도구 호출이나 텍스트를 검사했습니다. 이제 첨부 이미지를 모델에 보내기 전 단계에서 막을 수 있습니다. 사내 규정상 스크린샷을 외부 모델로 보내면 안 되는 경우, 혹은 이미지 첨부가 곧 비용인 파이프라인에서 유용한 지점입니다.

주의할 점은 **정책 플러그인을 따로 쓰는 구성에서만 의미가 있다**는 것입니다. 기본 설정만 쓰는 인스턴스에는 체감 변화가 없습니다.

## 자동화·스케줄링에서 달라진 것

이번 릴리스에서 크론·스케줄 관련 항목은 7건입니다. 잡을 돌리는 쪽에서 체감이 큰 순서로 정리했습니다.

| # | 수정 내용 | 왜 중요한가 |
|---|---|---|
| 1 | 세션을 지정한 크론잡·시스템 이벤트의 응답이 **에이전트 턴 종료 후 대화로 전달되지 않던 문제** (#196750, #196749) | 잡은 돌았는데 결과가 안 보이던 케이스 |
| 2 | 생성 대화에 묶인 예약 응답이 **메시지 편집·브랜치 전환·리셋 후 사라지던 문제**, 같은 대화로 예약된 인증 후속 요청이 거부되던 문제 | 대화를 손보는 순간 예약 잡이 끊기던 문제 |
| 3 | **실행 중인 크론잡이 크론 설정 재로드로 중단되던 문제** — 같은 스토어에서 크론이 켜져 있으면 끝까지 실행 후 결과 전달 (#197606, 이슈 #197591) | 설정 손보는 순간 잡이 잘리던 문제 |
| 4 | 스케줄러가 늦게 깨어날 때 **반복 잡이 조용히 스킵되던 문제** (`cron.skipMissedJobs` 사용 시, #197484) | 다운타임·시계 점프 이후에도 정상 슬롯은 실행 |
| 5 | **활성 크론잡이 쓰는 세션을 자동 정리가 아카이브·삭제하지 않도록** 변경 | 잡이 참조하던 세션이 사라지는 사고 방지 |
| 6 | 샌드박스 크론 세션이 **격리를 지킬 수 없는 호스트 CLI를 선택하지 못하게** 차단 | 보안 경계 유지 |
| 7 | 에이전트가 준비하는 동안 **스케줄 잡을 큐에 유지**, 준비된 에이전트는 바로 실행 (#174958) | 재시작 직후 잡 몰림 완화 |

특히 3번은 조건이 명확합니다. **"게이트웨이 정지·재시작은 여전히 실행 중 잡을 중단시킨다"** 는 단서가 붙어 있습니다. 설정 재로드는 견디지만 재시작은 못 견딘다는 뜻이라, 배포 타이밍은 그대로 신경 써야 합니다.

## 재시작·메시지 유실 쪽 수정

지난 글에서 "재시작 한 번에 운영이 흔들린다"고 정리했는데, 이번 릴리스는 그 지점을 정면으로 건드립니다.

| 상황 | 2026.11.4의 처리 |
|---|---|
| 첫 응답 전 게이트웨이 재시작 | **접수된 프롬프트가 대화 기록에서 사라지지 않음** (#187157) |
| 정상 종료(graceful restart) 중 | 승인된 큐 입력을 **취소로 처리하지 않음**, 원래 인증 주체가 같은 idempotency key로 재시도 가능 |
| 재시작 직후 에이전트 준비 중 | Control UI·TUI가 **최대 5분까지 대기**, 이미 전달된 전송·세션 생성 결과는 보존 (#174958) |
| 재시작 복구 검사 | 플러그인 서비스 로드 후 세션 DB 준비, 설정이 바뀌면 **오래된 복구 판단은 거부** |
| WhatsApp | 무관한 설정 재로드 때 **최종 답변이 사라지던 문제** 수정 (#168778) |
| Signal | 네이티브 HTTP 재연결 시 **버퍼 메시지가 건너뛰어지던 문제** 수정 (#187667) |
| Telegram | 응답 버튼이 선택을 잃거나 "This action is no longer available"로 뜨던 문제, 승인 카드가 비공개 토픽 대신 루트 DM에 뜨던 문제 수정 |
| Control UI | Safari에서 피커가 메뉴를 교체할 때 **화면이 멈추던 문제** 수정 (신고 #196820) |

여기에 메모리 쪽도 손봤습니다. 큰 SQLite 메모리 인덱스 재구축이 워커 메모리를 다 써서 **벡터 검색이 먹통이 되던 문제**, 재시작 복구 검사 때 **불러오는 대화 데이터 자체를 줄이는** 변경이 포함됐습니다.

개인정보 쪽도 한 줄 눈에 띕니다. **같은 세션을 보는 서로 다른 인증 프로필 사이에 Side chat 문답이 공유되던 문제**가 수정됐습니다. 단, **공용 게이트웨이 토큰처럼 개인 식별이 안 되는 연결은 여전히 스레드를 공유**한다는 단서가 붙습니다.

2026.11.4 공식 체인지로그(2026.11.4.md)에서 지난 글에 적었던 이슈 번호를 직접 검색해봤습니다.

## 같은 날 나온 2026.11.5-beta.4

베타 라인도 같은 날 갱신됐습니다. 안정판에 없는 항목 위주로만 적습니다.

- **Telegram 위젯**: 인터랙티브 위젯을 Telegram 메시지로 렌더링 (#196991)
- **자동화 연속성**: 부모 턴 종료 후 실패한 자식 결과 전달, 늦게 실행된 스케줄 잡 정상 처리, 설정 변경을 넘겨 **진행 중 잡 보존** (#197658, #197484, #197606, #197591, #188105)
- **자동화 프라이버시**: 큐에 있던 자동화 실행이 시작될 때 **소유자 전용 메모리 접근 권한을 재확인** (#198697, #198695)
- **첨부 처리**: 바이너리 첨부(SQLite DB 등)가 모델 프롬프트에 깨진 텍스트로 들어가지 않도록 수정 (#198309 등)

즉 안정판은 "유실·재시작" 쪽을, 베타는 "자동화 권한 재확인" 쪽을 더 다듬고 있는 모양새입니다. 권한 재확인 항목은 업무 자동화에 직접 영향이 있어서, 다음 안정판에 들어올 때 한 번 더 볼 만합니다.

## 마무리 — 업데이트 팁 세 줄

오픈소스라 구매 비용은 0원이지만, **업데이트 판단 자체가 비용**인 제품이라는 점은 이번에도 같습니다. 이번 버전 기준으로는 이렇게 정리됩니다.

> **① 상태 디렉터리를 먼저 복사하고, ② 위임 변경 자동 승인 설정을 확인한 뒤, ③ 업데이트 직후 첫 크론 결과 전달까지 눈으로 확인한다.**

세 줄 중 2번이 이번에 새로 생긴 항목입니다. 승인 모델이 바뀌었으니, 업데이트 후 첫 실행에서 승인 프롬프트가 뜨는 건 오작동이 아니라 **의도된 동작**입니다. 반대로 아무 프롬프트도 안 뜨고 위임 변경이 그대로 통과한다면, 그때가 오히려 설정을 확인해야 할 신호입니다.

업무 자동화 파이프라인을 운영하면서 "요즘 잡 결과가 며칠에 한 번씩 빠진다" 싶은 분들이라면, 버전부터 확인해 보세요. 11.3이라면 잡 로직을 의심하기 전에 이번 릴리스의 수정 목록을 먼저 보는 게 빠릅니다.
