> **📌 한줄 요약:** 11월 11일(한국시간) 배포된 OpenClaw **2026.11.3**은 새 기능이 없는 **보안 릴리스**였습니다. 그런데 배포 5일 만에 독립 추적 사이트가 **확인된 차단 이슈 19건, 그중 치명(critical) 6건**을 집계했고, 판정은 "신중하게 업데이트"였습니다. 게다가 11월 15일 나온 **2026.11.5-beta.3**의 릴리스 노트에는 이 치명 6건의 이슈 번호가 **하나도 등장하지 않습니다.** 즉 최신 안정판의 구멍은 아직 열려 있습니다.

## 업무 자동화 파이프라인을 돌리는 쪽이라면

에이전트에게 크론잡을 맡겨두고, 게이트웨이를 서비스로 띄워두고, 설정 파일을 손으로 고치는 구성이라면 이번 주는 좀 곤란한 상황입니다. 이런 경우가 실제로 벌어졌기 때문입니다.

- 재들여쓰기 한 번 한 설정 파일 때문에 **이후 모든 설정 쓰기가 영구히 막힌다**
- 와이파이가 잠깐 끊긴 사이 토큰이 만료되면 **ChatGPT 로그인이 통째로 날아간다**
- 산발 반복 크론잡 하나가 있으면 **게이트웨이가 SIGTERM에 죽지 않는다**
- 백업 크론잡이 도는 순간 **게이트웨이가 스스로 재시작하고, 백업은 "중단"으로 기록된다**

네 가지 모두 2026.11.3에서 재현 보고가 올라온 항목입니다. 그런데 이 버전은 일주일 전 글에서 "업데이트를 미루는 비용이 더 크다"고 정리했던 **바로 그 보안 릴리스**입니다. 그래서 이번에는 반대쪽 접시를 봐야 합니다. 보안을 위해 올린 버전이 운영을 어떻게 깨는지, 그리고 지금 시점에 선택지가 무엇인지 정리했습니다.

## 치명 6건 — 무엇이 어떻게 깨지는가

아래 등급은 OpenClaw 공식 발표가 아니라, 공개 이슈 트래커를 근거로 삼는 독립 추적 사이트(ClawStat.us)의 분류입니다. 다만 **이슈 자체는 전부 실제로 열려 있는 GitHub 이슈**이고, 본문에 재현 절차와 환경이 적혀 있습니다.

### 1) #198160 — 재들여쓰기 한 번에 설정 쓰기가 영구 차단

가장 위험한 항목입니다. OpenClaw는 설정 파일이 갑자기 절반 이하로 줄면 "덮어쓰기 사고"로 보고 백업에서 자동 복원합니다. 그런데 이 판정 기준이 **공백까지 포함한 원시 바이트 수**입니다. 마지막 정상 스냅샷이 들여쓰기가 깊은 상태로 승격된 적이 있으면, 그 뒤에 저장하는 **정상 설정도 전부 "50% 이상 축소"로 오인**됩니다.

결과는 이렇게 이어집니다. 게이트웨이 시작 시 설정이 백업으로 되돌아가고, 새 스냅샷은 정상 상태로 승격이 거부되며, 그다음부터 **모든 설정 쓰기가 막힙니다.** 보고서에는 이를 되돌릴 CLI 경로가 없다고 적혀 있습니다. Windows 11 + 비기본 상태 디렉터리(`OPENCLAW_STATE_DIR`) 조합에서 재현됐습니다.

### 2) #196958 — 오프라인 토큰 갱신 한 번에 ChatGPT 로그인 소실

ChatGPT(Codex) OAuth 액세스 토큰이 만료된 상태에서, 네트워크가 끊긴 사이 갱신이 돌면 `getaddrinfo EAI_AGAIN`으로 실패합니다. 문제는 이때 **저장된 리프레시 토큰이 "실패한 갱신" 표식으로 대체된다는 점**입니다. 네트워크가 돌아와도 재시도하지 않고, 프로필은 "설정되지 않음"으로 읽히며, 사용자는 다시 로그인해야 합니다. 리프레시 토큰은 기기 밖으로 나간 적이 없는데도요.

노트북을 들고 이동하거나, VPN이 끊기는 환경, 해외 출장 중인 게이트웨이라면 그냥 맞을 수 있는 조건입니다.

### 3) #196820 — Control UI가 100% CPU로 잠김

`Element.getAnimations()` 루프에서 Control UI가 100% CPU를 잡아먹는 회귀입니다. macOS 앱의 WebContent와 Edge 152, **서로 다른 두 엔진에서 독립 재현**됐습니다. 대시보드를 탭으로 띄워두는 습관이 있다면 노트북 팬이 먼저 알려줄 겁니다.

### 4) #197806 — macOS 앱이 Talk Mode 첫 사용에서 즉시 크래시

Talk Mode를 처음 켜는 순간 SIGTRAP으로 죽습니다. 권한 승인 다이얼로그가 뜨기도 전, `PermissionManager.ensureSpeechRecognition`의 Swift 동시성 단언에서 걸립니다. 음성으로 에이전트를 부르는 구성은 macOS 앱에서 사실상 막힌 상태입니다.

### 5) #198191 — 긴 받아쓰기가 조용히 사라짐

Control UI 받아쓰기에서 녹음을 멈추면 최종 전사본을 **8초만 기다리고 끊습니다.** 그보다 긴 녹음은 저장되지 않고 사라지는데, 사용자에게 실패로 보이지도 않습니다. 회의록을 음성으로 넘기는 워크플로라면 데이터가 소리 없이 새는 셈입니다.

### 6) #199614 — 대형 DB에서 게이트웨이 RPC가 굶음

11월 15일 저녁에 올라온 최신 치명 항목입니다. 업데이트 후 과거 트랜스크립트 백필이 돌면서, **약 9.9GB SQLite(페이지 240만 개), 활성 세션 1만 2천 개** 환경에서 게이트웨이 메인 스레드가 수 시간 100% CPU에 붙고 RPC가 타임아웃됐습니다. 백필 커서는 메모리에만 있어서 **게이트웨이를 재시작할 때마다 처음부터 다시** 돕니다.

세션 데이터가 몇 GB를 넘는 인스턴스라면, 업데이트 직후 며칠은 이 백필을 전제로 시간을 잡아야 합니다.

## 크론잡 운영자에게 직결되는 5건 — 이게 더 아플 수 있습니다

치명 등급은 아니지만 high로 분류된 항목 중, **자동화를 돌리는 사람에게 직접 영향**이 있는 것들입니다. 개인적으로는 이쪽이 실무 체감이 더 큽니다.

| 이슈 | 증상 | 실무 영향 |
|---|---|---|
| **#198050** | 툴 경고를 스스로 복구하고 리포트까지 전송한 크론 런이 "실패"로 기록되고 **다시 실행**됨 | 같은 리포트가 두 번 발송. 알림 피로·중복 결제·중복 등록 |
| **#197884** | 웹챗에서 만든 잡의 announce 전달이 채널을 못 찾는데도 런은 `delivered: true`로 기록 | 약 20시간·24회 동안 **아무 데도 안 갔는데 성공으로 표시** |
| **#197337** | 산발 반복 크론잡이 하나 있으면 게이트웨이가 SIGTERM에 응답하지 않음 (11.2·11.3 공통, systemd `KillMode=mixed`) | 재배포·재시작이 타임아웃. 잡 하나 지우면 정상 종료 |

## 2026.11.5-beta.3은 무엇을 고쳤고, 무엇을 못 고쳤나

11월 15일 배포된 베타의 하이라이트는 세 줄입니다.

- **대용량 세션 안정성** — 트랜스크립트 인덱싱·트리밍·압축 중 메모리 압력 완화, 선택된 하이드레이션 페이로드만 스트리밍, 요약 길이 상한 설정 가능
- **재시작·전달 안전성** — 재시작 중 큐잉된 메시지의 권한 상한과 수락된 인그레스 보존, 핸드오프 전 최종 채팅 쓰기 완료, 마지막 RPC까지 전달 소유권 유지
- **복구·설정** — 콜드 스타트 초기화, 중단된 워크스페이스 복구, 설치 프로그램 권한, iMessage Automation 상태 안내 개선

방향은 맞습니다. 그런데 릴리스 노트 전문을 뒤져보면 **#198160, #196958, #196820, #197806, #198191, #199614 중 어느 번호도 등장하지 않습니다.** 8192 출력 상한(#196544)이나 크론 이중 보고(#198050), 종료 멈춤(#197337)도 마찬가지입니다. 즉 beta.3은 "대용량 세션에서 메모리 터지는 문제"와 "재시작 중 메시지 유실" 계열을 눌렀지만, 위에 정리한 치명 6건은 **여전히 열린 상태**입니다.

여기서 한 가지 균형도 필요합니다. 추적 사이트의 버전 이력를 보면 8~9월 릴리스들도 **전부 60건 캡**에 걸려 있었습니다. 이 사이트가 이슈를 60개까지만 노출하는 구조라서, "11.3만 19건"이라는 숫자를 "역대급 사고"로 읽으면 과장입니다. 다만 **치명 등급 6건**은 등급 자체가 무겁고, 그중 다섯이 배포 후 사흘 안에 몰려 나왔다는 점은 눈여겨볼 부분입니다.

| **2026.11.3 유지** | 높음 (자격증명 유출 13종 수정 포함) | 낮음 (치명 6건 열림) | 외부 노출이 있는 게이트웨이. 단 아래 회피 수칙 필수 |
| **2026.11.2로 내리기** | 낮음 (보안 수정 미적용) | 상대적으로 높음 | 내부망 전용 + 시크릿 회전 가능 + exec 모드 조여둔 환경 |
| **2026.9.37 (확장 안정판)** | 중간~높음 (중요 보안 수정 포함 표기) | 9월 기능 수준 | 기능보다 무중단이 중요한 게이트웨이. **자동 적용 안 되므로 수동 배포** |
| **2026.11.5-beta.3** | 중간 (11.3 수정 승계) | 개선 중, 치명 6건 미해결 | 별도 인스턴스에서 검증할 여유가 있을 때 |

주의할 점 하나. 확장 안정판은 스스로를 "9월 말 버전 + 중요 보안 업데이트"라고 소개하지만, **11.3의 보안 수정 13종이 항목별로 동일하게 들어갔는지는 릴리스 노트에 명시돼 있지 않습니다.** 확장 안정판으로 갈 거라면 보안 항목을 하나씩 대조하는 게 안전합니다.

## 11.3에 남기로 했다면 — 오늘 바로 할 6가지

1. **설정 파일을 먼저 복사해 둔다.** #198160은 "설정 쓰기가 영구 차단"되는 문제라, 사본이 없으면 손쓸 방법이 줄어듭니다. `openclaw.json`과 상태 디렉터리를 통째로 백업.
2. **백업은 크론잡으로 돌리지 않는다.** #198256 때문에 `openclaw backup create` 자체가 게이트웨이를 재시작시킵니다. 수동·유지보수 창구에서 실행하고, 크론 백업 잡은 잠시 끕니다.
3. **설정 파일 재들여쓰기를 피한다.** 포매터·에디터의 자동 정렬이 설정 파일에 걸려 있다면 잠시 끕니다. 이게 #198160의 방아쇠입니다.
4. **Control UI 탭을 오래 열어두지 않는다.** #196820(100% CPU), #198191(긴 받아쓰기 유실) 둘 다 Control UI에서 나옵니다. 긴 음성 메모는 8초 안에 끝나는 짧은 단위로 나눕니다.
5. **크론 결과에 멱등 장치를 둔다.** #198050(이중 실행), #197884(거짓 성공) 때문에 "잡이 성공했다"는 기록만 믿으면 안 됩니다. 발송 대상 쪽에서 중복 키로 한 번 더 거르고, 결과물이 실제로 도착했는지 별도 확인을 붙입니다.
6. **재시작은 잡이 없는 시간대에.** #197337은 산발 반복 잡 하나로 종료가 멈추는 문제입니다. 배포·재시작 전에는 `openclaw cron list`로 반복 잡을 확인하고, 필요하면 잠시 지웠다가 다시 겁니다.

11.2로 내리기로 했다면 반대 순서입니다. **exec 모드를 `allowlist` 또는 `ask`로 조이고, 게이트웨이 외부 노출을 최소화하고, 노출됐던 키는 회전**시키는 걸 먼저 하세요. 보안 수정을 포기한 만큼 경계를 사람이 대신 세워야 합니다.

## 솔직히, 이번 건에서 아쉬운 점

- **CVE 번호가 없습니다.** GitHub 보안 권고의 최신 항목은 9월 11일자 medium 5건이고, 11.3의 회귀에 연결된 권고는 확인되지 않습니다. "CVE가 없으니 괜찮다"가 아니라, **등급 판단을 외부 추적 사이트와 이슈 트래커에 의존해야 한다**는 뜻입니다.
- **"보안 릴리스"라는 라벨이 만능이 아닙니다.** 자격증명 유출 경로를 막은 대신, 설정 쓰기·로그인·백업이라는 운영 핵심 경로에 구멍이 생겼습니다. 보안과 안정성이 같은 방향이라고 가정하면 이런 주에 크게 다칩니다.
- **수정이 베타에만 있습니다.** 안정판 사용자 입장에서 선택지는 "구멍 있는 최신" 아니면 "보안 낮은 이전" 둘뿐입니다. beta.3의 안정성 수정을 안정판에서 받으려면 한 번 더 기다려야 합니다.
- **숫자 읽기에 주의가 필요합니다.** 추적 사이트가 60건 캡으로 집계하기 때문에, "19건"이나 "60건" 같은 숫자만으로 버전 간 심각도를 비교하면 틀립니다. 등급과 재현 조건을 같이 봐야 합니다.

## 마무리 — 업데이트 팁 세 줄

오픈소스라 구매 비용은 0원이지만, **업데이트 판단 자체가 비용**인 제품입니다. 이번 주에 정리하면 이렇게 됩니다.

> **① 설정·상태 디렉터리를 먼저 복사하고, ② 백업 크론잡은 잠시 끄고, ③ 재시작은 반복 잡을 지운 뒤에 한다.**

세 줄이면 이번 회귀 6건 중 최소 4건(#198160, #198256, #197337, #199614의 재시작 루프)의 피해를 크게 줄일 수 있습니다. 보안을 위해 올렸다가 운영이 멈추는 건 순서가 뒤바뀐 결과니까, 올리는 것만큼 **되돌릴 준비**를 같이 해두는 게 남는 장사입니다.

업무 자동화 파이프라인을 운영하면서 "요즘 잡 결과가 이상하다" 싶은 분들이라면, 버전부터 확인해 보세요. 11.3이라면 잡을 의심하기 전에 이슈 목록을 먼저 보는 게 빠릅니다.
