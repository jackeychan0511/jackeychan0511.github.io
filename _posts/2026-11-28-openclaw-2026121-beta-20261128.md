## 11월 26일 정식판에서 이틀 만에 12월 라인이 열렸다

11월 26일 19시 06분(한국시간)에 **2026.11.10 정식판**이 올라온 지 이틀 만입니다. 그 사이 11월 26일 10시 37분에 **2026.10.34**(확장 안정판 계열), 11월 27일에는 일일 빌드 두 건이 지나갔고, 11월 28일 09시 21분에 **2026.12.1-beta.1**이 붙었습니다.

숫자와 성격부터 정리하면 이렇습니다.

| 항목 | 내용 |
|---|---|
| 버전 | 2026.12.1-beta.1 (**pre-release**) |
| 공개 시각 | 2026-11-28 00:21 UTC / 09:21 KST |
| 앞선 정식판 | 2026.11.10 (2026-11-26 10:06 UTC) |
| 성격 | 12월 라인 첫 빌드, 기능 묶음 + 수정 다수 |
| 운영 영향 | 무중단 업데이트, 프롬프트 캐시, 자동화 잡 동작, 프로젝트 권한 |

먼저 짚어야 할 건 **베타라는 점**입니다. 릴리스 페이지에도 Pre-release로 표시돼 있고, 태그는 `tideclaw-bot`이 서명해 올린 릴리스 형태입니다. 자동화 파이프라인을 운영하는 쪽이라면 "새 기능이 이렇게 온다"를 미리 보고, 실제 적용은 정식 채널(또는 확장 안정판)이 나온 뒤로 미루는 판단이 합리적입니다. 아래 내용은 그 판단을 위한 사전 정보다고 보시면 됩니다.

## 핵심 1 — 업데이트할 때 게이트웨이가 멈추지 않는다

이번 릴리스에서 실무 체감이 가장 큰 항목입니다. 릴리스 노트 첫 줄에 이렇게 적혀 있습니다.

- **Git 설치 방식**은 **준비된 릴리스(prepared releases)** 와 **상주 런처(resident launcher)** 를 씁니다.
- **패키지 업데이트**는 **서빙 중인 게이트웨이를 멈추지 않고** 미리 준비한 뒤 교체합니다.

지금까지는 업데이트가 곧 재시작이었습니다. 재시작하는 동안에는 채널 응답이 끊기고, 그 시점에 돌고 있던 세션은 중단을 겪습니다. 예약 실행을 걸어 두는 구조라면 "업데이트 시간대와 잡 실행 시간대가 겹치지 않게" 시간표를 짜야 했습니다.

이게 **준비 → 교체**로 바뀌면 그 시간표 설계 부담이 줄어듭니다. 다만 베타 릴리스 노트에도 관련 수정이 함께 붙어 있습니다. **업데이트 핸드오프** 항목에서 자기 업데이트가 첫 준비 신호까지 유지되게 하고, 교체 게이트웨이가 뜬 뒤에 플러그인 유지보수를 돌리고, 지연된 기동은 더 빨리 롤백하도록 손봤다고 적혀 있습니다. 즉 **"무중단"은 방향이고, 아직 다듬는 중**이라고 읽는 게 정확합니다.

> 운영 팁: 무중단 업데이트를 기대하고 잡 시간표를 대폭 앞당기려면, 최소한 확장 안정판에서 두세 번 릴리스가 지난 뒤에 하는 편이 안전합니다. 베타에서 구조를 바꾼 직후에는 핸드오프 관련 수정이 연달아 붙는 패턴이 반복돼 왔습니다.

## 핵심 2 — 프롬프트 캐시가 라우트를 넘어 재사용된다

두 번째는 비용과 지연에 직결되는 항목입니다.

- **컴팩션(compaction)** 이 **라우트를 넘어 데워진 프롬프트 캐시를 재사용**합니다.
- **읽기 전용 프리웜(prewarm)** 이 유휴 캐시를 따뜻하게 유지합니다.
- **자동 컴팩션이 컨텍스트 윈도의 85%** 지점에서 시작됩니다.

풀어서 설명하면 이렇습니다. 에이전트 세션이 길어지면 대화 이력을 요약해 압축하는데(컴팩션), 이때마다 프롬프트 앞부분이 새로 계산되면 캐시가 무효화됩니다. 캐시가 끊기면 토큰 단가가 그대로 올라가고 첫 응답도 느려집니다. 이번 변경은 **압축 과정에서도 앞부분 캐시를 살려 두는** 쪽으로 방향을 잡은 것입니다.

자동 컴팩션 시작 지점이 **85%** 로 명시된 것도 의미가 있습니다. 그동안은 세션이 길어질수록 "언제 잘릴지"가 불투명했는데, 기준선이 문서화된 셈입니다. 긴 문서를 물려 놓고 여러 턴을 돌리는 작업(리서치, 코드 리뷰, 로그 분석)에서 응답 품질 편차가 줄어드는 효과를 기대할 수 있습니다.

| 항목 | 이전 | 2026.12.1-beta.1 |
|---|---|---|
| 컴팩션 시 캐시 | 사실상 재계산 | 라우트 간 웜 캐시 재사용 |
| 유휴 세션 캐시 | 식음 | 읽기 전용 프리웜으로 유지 |
| 자동 컴팩션 시점 | 고정 기준 없음 | 컨텍스트 85% |

## 핵심 3 — 자동화 잡이 '제공자 압박'에 물러선다

자동화(Automations)를 돌리는 입장에서 이번 변경은 세 줄이 전부입니다.

- **제공자가 밀어내면 백오프**합니다. 즉 모델 제공자가 속도 제한이나 과부하 신호를 보내면 잡이 재시도로 밀어붙이지 않고 물러섭니다.
- **메모리가 허락하는 범위에서 최대 8회 추가 실행**을 허용합니다.
- **새 잡의 이름을 프롬프트에서 자동으로** 딴다.

두 번째 항목은 양날의 검입니다. 잡이 실패했을 때 조용히 끝나는 대신 최대 8번까지 더 시도한다는 뜻이라, **성공률은 올라가지만 실패 시 토큰 소모와 실행 시간도 함께 늘어납니다.** 8회 상한이 "메모리가 허락하는 범위"라는 조건부라는 점도 기억해 둘 부분입니다.

세 번째는 사소해 보이지만 목록이 길어지면 차이가 큽니다. 잡을 수십 개 굴리면 `job-7`, `job-12` 같은 이름이 쌓여서 무엇이 무엇인지 알 수 없게 되는데, 프롬프트 첫 줄에서 이름을 따면 관리 화면에서 바로 구분됩니다.

그리고 **Templates** 쪽에도 자동화 관련 변경이 있습니다. 템플릿을 **채팅 카드에서 계획된 자동화로 관리**할 수 있게 됐고, 파일을 채팅으로 펼치지 않고 템플릿을 미리 볼 수 있으며, 에이전트 메뉴에서 **템플릿 공유**가 가능해졌습니다. "이 세팅 그대로 다른 사람에게 넘긴다"는 흐름이 UI 안으로 들어온 셈입니다.

## 핵심 4 — 프로젝트 단위로 역할을 나눠 공유한다

관리자 기능이지만 팀 운영에는 영향이 큽니다.

- 관리자가 **특정 프로젝트만 제한된 역할로 공유**할 수 있습니다.
- **채팅에서 프로필 역할을 지정**할 수 있습니다.

그동안 권한은 "이 사람에게 이 게이트웨이 전체"에 가까웠습니다. 프로젝트 단위로 쪼갤 수 있게 되면, 예를 들어 마케팅 자동화 묶음은 A에게만, 사내 문서 인덱싱은 B에게만 열어 주는 식의 구성이 가능해집니다. 최소 권한 원칙을 적용하기 쉬워진다는 뜻입니다.

여기에 **신뢰 프록시 인증** 변경도 같이 왔습니다. 지금까지는 전달된 신원 헤더를 신뢰하는 방식이었는데, 이제 **Cloudflare Access JWT 검증을 옵트인**으로 켤 수 있습니다. 리버스 프록시 뒤에 게이트웨이를 두는 구성이라면 헤더 위조 가능성을 줄이는 쪽으로 한 칸 나아진 것입니다. 옵트인이라는 점은 주의해야 합니다. **켜지 않으면 이전과 동일하게 헤더 신뢰**입니다.

## 그 밖에 같이 온 것들

한 줄씩 정리하면 이렇습니다.

| 영역 | 변경 |
|---|---|
| 세션 공유 | 승인된 공유 세션을 **아웃바운드 WSS**로 당겨와 원본 Control UI에서 열기 |
| 린 게이트웨이 | 코어 워커 코드를 한 호스트에서 공유, 메모리 예산 안에서 워커 증설 (소형 장비 메모리 압박 완화) |
| 스킬 | **ClawHub 카탈로그를 카테고리로 탐색·검색**, 설치된 스킬을 다이얼로그가 아닌 전체 페이지로 열기 |
| Control UI | Sessions에 자체 레일 메뉴, **Code Mode·Tool Search·Templates가 Labs에서 졸업** |
| 모델 설정 | 기본·폴백 모델의 **하네스 선택**, 플러그인 도구를 설정에서 개별 제어 |
| 지식(Knowledge) | Slack 채널 목록 조회, 읽기 토큰 선택, Slack에서 지식 학습 |
| GBrain | 플러그인 설치 프로그램으로 연결, **애플 실리콘·x86-64 리눅스에서 Bun 없이 네이티브 설치** |
| OpenCode | OpenCode Console·OpenCode Go 브라우저 로그인 |
| Codex | `/codex review`가 브랜치·커밋·사용자 지시문을 대상으로 지정 |
| 제공자 | **Nano Banana 2.1** 이미지 생성 추가, 자격 갖춘 Bedrock Converse 스트림을 ClawRouter로 라우팅 |

## 정리 — 지금 할 일과 미룰 일

**지금 해도 되는 것**

- Control UI가 Labs 밖으로 옮긴 항목(Code Mode, Tool Search, Templates)의 위치 변경을 미리 파악해 두기. 정식판에서 메뉴가 바뀌면 헤매기 쉽습니다.
- 프롬프트 캐시·컴팩션 정책을 확인하고, 긴 세션을 쓰는 작업의 토큰 사용량을 평소에 기록해 두기. 비교 기준선이 있어야 85% 자동 컴팩션이 실제로 이득인지 판단할 수 있습니다.
- 리버스 프록시 뒤에서 돌리는 구성이라면 **Cloudflare Access JWT 옵트인**을 검토 목록에 올려 두기.

**미루는 게 나은 것**

- 무중단 업데이트를 전제로 잡 시간표를 다시 짜는 일. 베타이고 핸드오프 수정이 계속 붙고 있어, 확장 안정판에서 두어 번 릴리스가 지난 뒤가 적기입니다.
- 관리자 권한 체계(프로젝트 단위 역할) 개편. 권한 모델은 한 번 꼬이면 되돌리기 번거로우니 정식 릴리스 노트를 보고 적용하는 편이 낫습니다.
- Automations의 8회 추가 실행을 기본값으로 믿는 운영. 실패 루프에서 토큰이 최대 8배까지 나갈 수 있으니, 상한과 알림을 함께 설정해 두는 편이 안전합니다.

이번 빌드는 "12월 라인이 이 방향으로 간다"는 신호에 가깝습니다. 업데이트 무중단, 캐시 재사용, 자동화 잡의 안정화 — 셋 다 화려하진 않지만 오래 돌리는 자동화 파이프라인에서는 체감이 큰 축입니다. 자동화를 업무에 붙여 쓰는 분들이라면 정식 릴리스 노트가 나오는 시점에 다시 이 네 항목만 확인하시면 됩니다.
